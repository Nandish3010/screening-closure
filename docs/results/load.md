# Scheduler sweep load test

Generated by `make test-load` (`tools/load/time_sweep.py`). Do not edit by hand. All data are synthetic.

**Target: the 100,000-case sweep under 5 s. Single process (`SWEEP_WORKERS=1`): 8.72 s (not met). Through `POST /scheduler/sweep` with 4 workers (the API default): 3.93 s (met). Through `POST /scheduler/sweep` with 10 workers: 3.17 s (met).**

## Results

Scenario `daily`: the previous sweep ran one working day earlier, so the timed sweep emits only the breaches and escalation rungs that became due since then, and `cases.next_due_at` (migration 012, A20) is as the last append left it. Cases are spread over the eleven open states (main chain plus consent withdrawn, referral rejected and lost contact); about 40% are already overdue. Workers 1 is `run_sweep` in one process (`SWEEP_WORKERS=1`); workers N is `POST /scheduler/sweep` on the FastAPI app (A17) with `SWEEP_WORKERS=N`: the route's warm long-lived pool of N processes, each sweeping a disjoint slice of the cases. The route's default is min(4, cpus). Route timings include the service-token check and the JSON response, in process (no socket). "Read" is the number of cases the sweep selected, read and replayed; the rest were skipped because their stored due time is still in the future.

Re-sweep: the same sweep run again straight afterwards. It emits nothing (idempotency is asserted) so it is the cost of a sweep with nothing to do, which is what the 10-second loop mostly runs. After every sweep, untimed, a full scan (`full_scan=True`: read and replay every case) must also find nothing to do; that is the check that the due-time index skipped no case.

## Cold start (scenario `backlog`)

No sweep has run since the cases were created, for example after a long scheduler outage, so every breach and every rung is pending and the sweep must append all of them, so far more cases are due than in the daily scenario and the index skips only those with nothing due. Each case's append still locks the case, re-reads its log and re-verifies the replay (the engine's safety property); the sweep shares the transaction between up to 100 cases (A20).

## First sweep after migration 012 (scenario `unindexed`)

Migration 012 adds `cases.next_due_at`, NULL for every case that exists when it runs. NULL means "not computed", so the first sweep reads and replays every case once (as a sweep did before A20), writes each case's due time back, and the sweeps after it skip as in the first table. This is the one-off cost of switching the index on; it is paid once per database and again only if the calendar or the pathway's timings change (the stored fingerprint then differs).

## What changed (A20)

A20 added two things to `api/app/sweep.py` and `api/app/store_pg.py`; both are kept, each measured separately on a freshly seeded 100,000-case database (scenario `daily`) with the same seed, sweep time and machine. (1) The sweep index: `cases.next_due_at` (migration 012) holds the earliest instant at which the planner could plan anything for the case; it is derived from the replayed read model and written in the same transaction as every append, and the sweep selects only the cases whose due time has passed, plus those with no usable value (new cases, rows from before the migration, a changed calendar or pathway). (3) Batched writes: `PostgresEventStore.append_batches` appends the planned events of up to 100 cases in one transaction, with the per-case lock, re-read, replay and checks of `append_many`; a refused case is reported in its own slot and loses none of the others. Option (2), a cached read model per case in a JSONB column, was not built: (1) and (3) met the target. Each cell is sweep wall time / re-sweep wall time in seconds. The ablation rows switch one change off with an environment variable (`SWEEP_BATCH_CASES=1` appends one case per transaction; `SWEEP_FULL_SCAN=1` reads and replays every case), so they still maintain the column on each append. "Before" is the unchanged tree (main at 0a6ef53), run in the same half hour as the ablation rows.

|---|---|---|---|---|
| Before: full scan, one transaction per case (main) | 60.92 / 40.86 | 31.97 / 14.15 | 17.48 / 10.17 | 100,000 |

What the table says. The index removes the read and replay of the 91,196 cases that cannot be due (100,000 cases read before, 8,804 after) and makes a sweep that has nothing to do almost free (re-sweep 40.9 s to 0.04 s in one process), but alone it makes the appends slower: with one transaction per case, each append now also writes an indexed column, so the single-process sweep fell only from 60.9 s to 54.4 s (appends 48.8 s against 27.3 s). Batching alone removes the per-case round trips (appends 27.3 s to 7.8 s) but the full scan stays. Together they remove both: 8.72 s in one process, 3.93 s through the route with its default 4 workers and 3.17 s with 10, against 60.9 s, 32.0 s and 17.5 s. Run-to-run variation on this shared laptop is about 10 to 25% (the unchanged tree measured 47.3 s, 37.2 s and 21.0 s in an earlier quiet run), well inside the difference.

Cost that stays. The first sweep after migration 012 (the column is NULL) and the first after a calendar or pathway change read every case once; see "First sweep after migration 012" above (100,000 cases: 20.4 s with 4 workers, 15.9 s with 10). A sweep after a long outage appends everything that is pending whatever the index says ("Cold start" above). What remains in the 3.93 s: reading and replaying the 8,804 cases that are due, replaying them again under the lock when they are appended (the engine's safety property, not skipped), and the Postgres round trips. Option (2) would remove only the first of those; it was left out.

Safety. After every timed sweep the harness runs an untimed full scan (`full_scan=True`) and requires it to find nothing to do; a case the index wrongly skipped would show there. The same property is tested without a database over random logs (`api/tests/test_next_due.py`) and against Postgres (`api/tests/test_next_due_pg.py`).

## Optimisation history before A20

History of the first two rounds of work, before A20; the figures in this section are those of the tree then and are not the current ones (the current results are the tables above). Two optimisations, both in `api/app/sweep.py` and `api/app/store_pg.py`, no behaviour change (`make test` and `make test-db` pass unchanged). (1) The events the scheduler plans for one case (a breach and its first escalation rung) are appended in one transaction, `PostgresEventStore.append_many`: one row lock, one log read and replay and one commit instead of one of each per event; if the batch is refused for any reason the sweep falls back to appending one by one. (2) `run_sweep_parallel` / `shard=(k, n)`: the open cases are split into disjoint slices by a stable hash of the case id and swept by separate processes, each with its own connection pool, because replaying every case is CPU-bound Python. Measured then, single process, 100,000 open cases: 19.57 s before and 20.38 s after (the sharded route is the second change). Same machine, seed and sweep time. Timings varied by about 10% from run to run on a shared laptop.

A first run, on a busy machine and before the base had moved, measured 48 s for the 100,000-case single-process sweep. It did not reproduce on the quiet reruns (17 to 26 s) and is not used here. (The unchanged tree at the start of A20, with the later milestones and coalescing in the planner, measured 47 to 61 s in one process; see A20 above.)

A17 (this branch): `POST /scheduler/sweep` now runs `run_sweep_parallel` on a long-lived pool of worker processes (`SweepPool` in `api/app/sweep.py`, used by `api/app/routers/scheduler.py`). `SWEEP_WORKERS` sets the size, default min(4, cpus); `SWEEP_WORKERS=1`, or any store that is not Postgres, keeps the single-process `run_sweep`. The pool is created on the first sweep (about a second) and kept; the rows with Workers 4 and 10 in the first table are the route itself, called in process on a warm pool, so they include the service-token check and the JSON response. Idempotency and no duplicate events across shards are asserted on the route in `api/tests/test_sweep_parallel_pg.py`, and a sweep killed part-way is covered by `api/tests/test_chaos_kill_sweep.py`.

Before A20: Is 100,000 under 5 s now met in the real route? Not reliably, and not at the default of 4 workers. Five runs on this shared 10-core laptop (other jobs running most of the time; Postgres in Docker on the same machine; the last ran with a load average of about 2), full sweep with the day's 11,276 events, then the re-sweep that emits nothing and is what the 10-second loop mostly does: 4 workers 10.46 s / 5.58 s, 7.56 s / 3.59 s, 7.11 s / 3.92 s, 7.75 s / 4.63 s; 10 workers 8.51 s / 3.36 s, 5.34 s / 2.37 s, 4.99 s / 2.37 s (met once, by 0.01 s, in the run with synchronous_commit=off described below), 10.23 s / 4.34 s; and on the quiet run 6.76 s / 3.41 s at 4 workers and 5.21 s / 2.25 s at 10 (not met by 0.21 s). Neither the single process (20 to 26 s) nor the default pool (best 6.76 s) meets the target for a sweep that appends a day's events at once; 10 workers met it once in five runs. A steady-state sweep (nothing to append) of 100,000 cases takes 2.3 to 4.3 s with 10 workers and 3.4 to 5.6 s with 4, so the 10-second loop keeps up with 100,000 open cases on a quiet machine. The shortfall is CPU, not durability: setting `synchronous_commit=off` for the workers changed the 100,000-case figures by about 5% (inside the noise) and was not adopted.

Why more workers do not scale linearly: replaying every case and appending each event is Python CPU work plus one Postgres transaction per case, and with 10 workers the Python processes, the Postgres backends and the Docker VM share 10 cores. Ideal scaling from the single-process split (read and replay about 10 s, appends about 10.6 s) would give about 2.3 s at 10 workers; the measured best is 5.0 s. Lowering the figure further needed a cheaper append and skipping cases that cannot be due; both were done in A20 (above).

## Method

- `tools/load/seed_cases.py` creates the throwaway database `closure_load` on the compose Postgres (host port 5433), applies the engine's migrations through `app.db.run_migrations`, and bulk-inserts cases and their event logs with `COPY`. Every log is produced by the engine's own state machine and replayed once at seeding time. It refuses to touch any database not named `closure_load*`; the dev database is never used.
- `tools/load/time_sweep.py` times the sweep with a fixed sweep time (2026-03-10 08:00 UTC, a Tuesday), the real `PostgresEventStore` and the UAE working-day calendar; with Workers 1 by calling `run_sweep`, with more workers by calling `POST /scheduler/sweep` on the FastAPI app (`RouteSweep`, `SWEEP_WORKERS=N`, pool started before the clock). Seed 20261017, so the data and the emitted-event counts are reproducible; wall times vary with the machine. Postgres runs in Docker on the same machine, so every statement pays a local network hop.
- After each sweep it asserts: emitted events equal the pure planner's expectation; no errors or rejected events; a second sweep emits nothing; no `close` event exists; case logs are gap-free; the event row count grew by exactly the events emitted.
- `make check` runs the 1,000-case size only (no file written); `make test-load` runs all sizes and rewrites this file. The database is dropped at the end unless `KEEP_LOAD_DB=1`.
