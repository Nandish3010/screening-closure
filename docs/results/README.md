# Evaluation results

Generated by `make evaluate` (`python -m simulator.sim.cli evaluate`). Do not edit by hand. All data are synthetic.

| File | What it is |
|---|---|
| `results.json` | Machine-readable results. For each of the two arms and for the orchestrated-minus-baseline difference, every metric as `{mean, ci_low, ci_high, n_reps}` (percentile bootstrap 95% CI over replications; differences paired by replication). The top-level `meta`, `arms`, `difference`, `per_replication` and `parameters` describe the **upper-range** scenario (unchanged from before there were two scenarios). `scenarios` holds both side by side, `scenarios.upper_range` and `scenarios.literature_anchored`, each with `arms`, `difference`, `per_replication` (seed and event-log hash per arm per replication, so a rerun can be compared event for event), its parameter hash and file list and `overrides` (empty for the upper range; for the literature-anchored scenario every parameter the overlay changes, with its upper-range value, new value, source and status). `meta` has the seed, replications, cases, follow-up days, bootstrap resamples, SHA-256 of the effective parameters and of the pathway YAML, git commit and parameter status counts. Sorted keys, floats rounded to 6 places, no timestamps. Byte-for-byte reproducible for the same seed and parameters: `make evaluate-check`. |
| `metrics.md` | Precise definition of every metric in `results.json`: numerator, denominator, clocks (calendar versus working days, which events start and stop them), censoring, reopen handling, escalation precision, silent loss, the fairness gap statistic, a worked example, and the capacity caveat (escalations cost nothing in the model; a capacity model is future work). A test keeps it in step with the metric keys. |
| `results.md` | Human-readable report built from the same numbers. It leads with the headline table (baseline / orchestrated, literature anchored / orchestrated, upper range) and a plain-English paragraph: **quote the literature-anchored scenario**; the upper-range scenario shows the mechanism ceiling. Then a per-scenario summary and arm comparison with CIs, the calibration check against the published completion curves, fairness splits by language and channel, messy-case handling, and the full parameter table with sources and status. Its `generated_at` line is the only content that changes between runs. |

The two scenarios share one baseline arm (`evaluate` refuses to write results if the overlay changes it). The literature-anchored scenario is defined by [`simulator/params.conservative.yaml`](../../simulator/params.conservative.yaml); see the Scenarios section of [`simulator/README.md`](../../simulator/README.md).

Metric names in `results.json` are flat: for example `completion_180d`, `open_90d`, `time_to_closure_median`, `escalation_precision`,
`fairness.language.ar.completion_final`, `fairness.channel.completion_gap_max`, `messy.wrong_contact.handled_rate`. A `null` means the arm has no
such quantity by design (the baseline has no named owner and no escalations; the automation abstention rate waits for the AI cut) or the
follow-up window is shorter than the metric's horizon.

`git_commit` is the commit the code was at when the file was produced; the results file itself is committed afterwards, so it normally names the parent commit.

To reproduce: `make evaluate` (about 10 seconds on a laptop with 8-10 workers for both scenarios, about 1 minute single-process). To see the effect of a
parameter, edit `simulator/params.yaml` and rerun; see [`simulator/README.md`](../../simulator/README.md).
