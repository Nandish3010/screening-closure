# Automated-versus-human decision matrix

Who, or what, may take each action in the system, what evidence it needs, what it changes, and which test shows the restriction holds. One row per event type in the final vocabulary ([PLAN.md](../../project/PLAN.md) section 6), plus the routes that matter for control. This is a design record for reviewers and regulators, not a compliance claim.

Authority is the code: `api/app/policy.py` (who may try), `api/app/state_machine.py` and `config/pathways/colorectal_fit.yaml` (whether the event is valid). The state machine decides whether an event is valid; the policy table decides who is allowed to try. Checked against pathway v0.2 and `policy.py` at commit 21e96dd on the cut-e branch.

## How to read it

- **Automated actor** means an actor whose name starts with `system:`, `scheduler`, `watchdog` or `model:`. Automated actors cannot log in as users: `POST /auth/dev-login` refuses those role names, and a validly signed token still cannot carry one (ADR-012). The only automated identity that can call the API today is the scheduler service token, which maps to `system:scheduler` and may emit `mark_overdue`, `escalate` and `watchdog_flagged` only.
- **Who refuses an automated actor.** For events in the pathway's `human_only_events` list the state machine itself refuses any automated actor, and refuses `close` for any automated actor. For every other event, no automated identity is granted it by the policy table, so the API refuses it; the state machine alone would not. The "Automated actor?" column says which applies.
- **What it changes** uses three words. `state`: the main or side state moves. `flag`: a derived flag in the read model changes (`overdue`, `escalation_level`, `escalation_accepted`) and the state does not. `nothing`: an annotation that is recorded and changes neither the state nor a flag (it may still set the owner or feed a later step, as stated).
- **Test** cites the T-ID from [TEST-CASES.md](../../project/TEST-CASES.md) and, where one exists in the repository, the test name. "Pending A5 (T-A20)" means the test does not exist yet and names the ticket that will write it and its T-ID. Role names are in backticks only where they are part of the policy.
- Roles: `lab`, `primary_care_owner`, `specialist_owner`, `coordinator`, `patient`, `supervisor`, and the service role `scheduler`.

## What holds in structure

These four properties do not depend on a person following a procedure. Each has a test, and the matrix above is where a reviewer can see the exceptions.

1. **No closure without evidence and a human clinician.** The guard is in the state machine and runs inside the database transaction. No automated actor, and no role other than the two clinician roles, can emit `close` (T-A1, T-A3, T-A4, T-A26).
2. **Automated actors cannot log in as users.** The only automated identity that reaches the API is the scheduler service token, limited to three event types (T-A26).
3. **`message_sent` has no poster.** Nobody can post it through the events route. The approval-gated send path is the only writer, and it does not exist yet (pending D5, T-D1). Until it does, no message can be sent at all.
4. **Human-only events.** `escalation_accepted`, `handoff_accepted`, `consent_updated`, `message_approved`, `callback_requested` and `reopen` are refused for any automated actor by the state machine itself (T-A14, T-A19, T-A26).

## What the matrix does not yet cover

- Per-case scoping of owners. Any `primary_care_owner` or `specialist_owner` may act on any case (limitation L29, ADR-012). Pending A5.
- The full role-by-route denial matrix generated from the OpenAPI route list. Pending F7 (T-F9). Today's negative tests cover selected role and event pairs.
- The identity of the watchdog service, and a scheduler bounce of an unanswered referral (`handoff_rejected`). Both need a policy decision when A11 and A5 are built.
- An `erasure` marker event, if the implementing ticket for ADR-015 adds one. It is not in the vocabulary, so it is not in the matrix.

## Keeping it true

Completeness is meant to be checked by a test (T-E6, pending F1 docs-check): every event type in the pathway config and in `EVENT_POLICY` must have a row here, and the roles in the first column must equal the policy. When an event type, role or route is added or changed, update this file in the same commit.
