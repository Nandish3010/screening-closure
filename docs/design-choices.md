# Design choices

## Deterministic engine with human gates

Safety-critical state transitions are deterministic and replayable: every change to a case is an appended event, state is derived by replaying those events, and the same events always produce the same state, which can be explained line by line to a reviewer. A language model may draft a message or summarise a document, but it never moves a case between states or decides a closure; the model drafts, humans decide, and the architecture makes anything else structurally impossible rather than merely against policy.

## Transition check inside the database transaction

- The state-machine check runs inside the same transaction that locks the case row (`SELECT ... FOR UPDATE`) and inserts the event, because checking in the API process and then writing would let two concurrent requests both validate against the same old state and both commit; holding the lock makes validate-then-append atomic, so the closure invariant (evidence and a human sign-off) holds under concurrency and retries, not just in single-threaded tests.

## Comparison

Two architectures are compared for the same job: keeping every actionable screening result owned, timed and closed with evidence. The first is what this project builds, a deterministic engine in which state changes are decided by code and by people, with models confined to the edges (see "Where we do use a model" below). The second is an agentic orchestration in which a language model, or a group of model-driven agents, decides what happens next to a case (routes it, escalates it, judges whether evidence is sufficient, and closes it) using tools. Agentic designs are a reasonable choice for many problems, especially where inputs are unstructured and mistakes are cheap to reverse. The comparison below concerns this particular job, where a wrong closure is a patient treated as finished when they are not. The judgments are reasoning about architectures, not measurements of any specific product. Figures marked "illustrative" are assumptions chosen to show the shape of the difference and are not benchmarks.

| Dimension | Deterministic engine + human gates | Agentic orchestration |
|---|---|---|
| Auditability | Every change is an appended event with actor, time and evidence reference; the log is the audit trail. | The record shows model inputs and outputs; the reason for a decision is a generated explanation, not the rule that produced it. |
| Replayability | Replaying the event log reproduces the state exactly. | Replaying the same inputs may produce different decisions; replay needs recorded outputs, not re-execution. |
| Latency | A transition is one database transaction, typically milliseconds (to be measured by the load test, T-F8). | Each decision waits for one or more model calls, typically seconds, plus retries. |
| Cost per case | Compute and storage only; no per-decision charge. | Per-decision model charges that grow with events per case and with context length. |
| Failure modes | Fails closed: an invalid transition is refused; the main risk is a wrong rule, which is visible in the config and the tests. | Fails open or silent: a plausible but wrong decision, including a closure, looks like a correct one. |
| Model unavailable | No effect on state handling; drafting falls back to a template. | Decision-making stops or degrades, unless a deterministic path is built alongside it. |
| Regulator explainability | The rules are a short, versioned config and a pure function that can be read and walked through line by line. | Explanation rests on prompts, model versions and sampled behaviour, which change with each model update. |
| Testability | Properties can be tested over thousands of random event sequences (T-A1, T-A2), and the result is a yes or no. | Behaviour can be evaluated statistically on samples; an absolute guarantee cannot be tested. |

### Auditability

In the deterministic engine the audit trail is not a log written about the system; it is the system. The `events` table is the source of truth, each row names an actor, a time, an event type and, for closure, an `evidence_ref` and a `signed_by`, and database triggers reject updates and deletes (ADR-004). A reviewer asking "why is this case closed?" gets the exact sequence of events and the person who signed. In an agentic design the tool calls and messages can also be logged, and that log is useful, but the decision itself happened inside the model. What can be recorded is the input and the output, plus a rationale the model generated afterwards, which is a description of the decision rather than the rule that caused it. Two cases with the same facts can carry different rationales. That makes it harder to show a reviewer that the system treated like cases alike.

### Replayability

State here is derived by replaying the log, and every append replays the stored log and compares it with the stored `current_state`, raising `StateCorruption` on a mismatch (ADR-002). Replay determinism is a tested property (T-A2, T-A9), so an incident can be reconstructed by running the same code over the same events and getting the same state. A model-driven transition does not have this property: re-running the same prompt may give another answer, because of sampling, model updates or changed retrieval results, so reconstruction depends on having stored every model output and trusting that nothing else varied. That is workable for after-the-fact review but it is not a replay: nothing can be re-executed to check a fix, and a past model version may no longer be available.

### Latency

A transition in the engine is a single transaction that locks the case row, runs a pure function and inserts an event (ADR-003); the cost is dominated by the database round trip and the replay on append, which is acceptable at pilot scale and is to be measured by the 100,000-case sweep (T-F8). An agentic step adds at least one model call per decision, and a loop that plans, calls tools and checks its own work adds several, so a step that takes milliseconds in the engine takes seconds there, with a long tail when the provider is slow or the call is retried. For a pathway measured in weeks, seconds of latency per step do not change patient outcomes, so latency is not the strongest argument. It matters for the SLA sweep: evaluating tens of thousands of open cases against their clocks is a database scan in the engine and a very large number of model calls in an agent loop, and a sweep that cannot finish between runs is itself a way of missing overdue cases.

### Cost per case

In the engine the marginal cost of a transition is the compute and storage already provisioned, so cost per case is dominated by fixed items (hosting, support, integration), and falls as volume grows; the pilot cost script (`tools/pilot/cost_model.py`) shows this shape with every cost input marked assumed (the wage ratios of its wage-weighted section are the one sourced-adjacent exception). In an agentic design every event is a model call with its context, so cost per case is roughly events per case, times calls per event, times tokens per call, times the price per token. As an illustration only: a case with about a dozen state changes and two to three model calls for each, at a few thousand tokens per call, is dozens of calls per case; at 200,000 screened members and a positive rate near 7 percent (an assumption shared with the simulator, `simulator/params.yaml`), that is 14,000 cases and several hundred thousand model calls a year, before retries, re-checks and the periodic sweeps that must re-read open cases. The price per token is not asserted here and is to verify against the chosen provider's price list. The point is structural: a per-decision charge scales with activity, and the activity that matters most, the sweep over idle open cases, is the one that produces no new information.

### Failure modes

The engine's characteristic failures are rule errors (a wrong SLA, a missing transition) and bugs. Both are located in code and configuration that can be reviewed, and both fail closed: when the engine does not know what to do, it refuses the transition and the case stays where it is, as a task for a person. Silent failure, the absence of events, is covered by the watchdog and the scheduler heartbeat rather than being ignored. The characteristic failure of a model-driven design is a confident wrong answer. A hallucinated closure would mean a case moves to `closed` on the strength of an evidence reference that does not exist, or that does not show what the model said it shows, or on a sign-off the model inferred rather than received. The patient is then recorded as finished, the case leaves every worklist and every timer, and nothing in the system is left to notice. Because closure is the state that removes the safety net, the closure rule is where the architecture must not rely on a probability. Here it cannot happen by construction: `close` requires `evidence_ref` and `signed_by` from a non-automated actor, and a `model:` actor cannot emit state-changing events (ADR-001). Guardrails on an agent (validators, second-model checks) lower the rate of such errors, but a rate is not a guarantee, and a rare error in a population of tens of thousands of cases is still a patient.

### Model unavailable

When the model provider is down, slow or returns something that fails validation, the engine continues to work unchanged: ownership, timers, escalation and closure do not depend on it. The only affected function is message drafting, which falls back to a deterministic template that is also the default (`LLM_PROVIDER=template`, ADR-007); each fallback is counted as an abstention. An agentic design has to decide what to do with open cases when its decision-maker is unreachable: queue the decisions (and let clocks run out unobserved), fall back to rules (which means the deterministic engine exists anyway), or stop. The DoH Abu Dhabi AI policy lists graceful degradation among the minimum requirements for AI tools (see `docs/governance/regulatory-mapping.md`), and an engine whose core does not depend on the model meets it by design.

### Regulator explainability

A regulator or an auditor will ask three questions: what are the rules, who applied them to this patient, and how do you know they are applied every time. For the engine the answers are the pathway config (states, transitions, SLAs, escalation ladder, closure rule), the event log for the patient, and the property tests, respectively. They can be given on paper, and the config is short enough to read in one sitting. For an agentic design the first answer is a prompt and a set of tools, the second is a transcript, and the third is an evaluation on samples. Each can be right, but the answer to the third question is a statistical statement about behaviour at one model version, and it must be redone when the model changes, which for hosted models is outside the operator's control. The Abu Dhabi Responsible AI Standard asks for human oversight, traceability of inputs, outputs and versions, and clinician authority in AI-assisted decisions (see the regulatory mapping for references and what remains to verify). Confining models to a few edges, none of which can change a case, makes these requirements apply to a small surface.

### Testability

The closure invariant is tested by generating thousands of random event sequences over the full event alphabet and asserting that no sequence reaches `closed` without closure evidence and a human sign-off (T-A1), and that replay is deterministic (T-A2). These are properties of a pure function, so a failing example is shrunk to a minimal sequence and the suite gives a pass or fail. A transition driven by a model cannot be property-tested this way: the function under test is not a function, since the same input can give different outputs, and the input space (free text, documents, conversation history) cannot be enumerated or shrunk. It can be evaluated, by running sampled scenarios and counting errors, and that is valuable, but it estimates a rate with a confidence interval; it cannot establish that the rate is zero. For a rule such as "never close without evidence", zero is the requirement.

### Where each approach is the better fit

A model-driven component is a better fit where the input is unstructured and the outcome is reviewed by a person before it takes effect: summarising a discharge letter, drafting a message in Arabic and English in plain language, or classifying a free-text reply to route it to the right person. A deterministic engine is a better fit where the question has a definite answer that must be the same every time and the consequence of error is silent: is this case overdue, who is next to be told, may this case close. A hybrid with the model proposing and the engine disposing is what this project does. The reverse, where the model disposes, is what we avoid.

## The agency: agentic labour on a deterministic core

The comparison above is about who decides. It argues against a model deciding what happens to a case, and the engine does not let one. It does not argue against agents doing the work around a decision, and the section on where each approach fits already names that work: preparation, drafting, summaries. Coordinator labour is the scaling limit of the programme, and a coordinator's day is mostly that preparation, so the project builds it as an agency (A22, ADR-033, [agency.md](governance/agency.md)): one supervisor agent, five department heads (Outreach, Referral and Scheduling, Evidence and Closure, Patient Support, Quality and Operations) and fourteen executioners, one agent type per task, each with its own tool list and output schema. The agency is preparation only. Of all its tools, one causes anything: `create_draft`, which asks the existing drafting route for a message draft that then waits for the case owner. The rest read.

The two designs are reconciled by one rule: agents are labour, not authority. An agent finds who has not been contacted, drafts a first message, assembles the contact history before a call, works out which provider has not yet been asked and recommends it, queues a reply for a person, looks up whether a colonoscopy report exists in FHIR, and prepares what the signing clinician needs. It then hands the result to a person through an inbox, or, for a draft, through the approval the owner already gives. A rejected referral gets a recommendation in the coordinator's inbox, never a request, and a patient reply is queued for a person to read. The engine still disposes. Every agent acts only through the code paths a person uses (the API, the policy tables, payload validation, the consent rules, the approval gate and the closure invariant), and the state machine refuses any event from an agency actor, so the failure mode of the second architecture in the table, a plausible but wrong decision that looks right, has no place to occur: there is no decision for an agent to make.

What this costs and what it buys is stated in the same terms as the table. Auditability is kept and extended: every task is a ledger row with its inputs (ids and labels), its output, its tool calls and its provenance (provider, model, fallback, prompt hash), and the case's own log is untouched by the agency. Replayability of cases is unchanged, since the agency writes no case event; the ledger is a record of labour, and a run is idempotent per simulated instant. Failure fails closed: an agent whose tool is refused, whose output does not validate or whose time budget is gone fails its own task and the run goes on; a case simply waits for a person as it did before. The ordering of work may use a model (below) and falls back to rules, so the agency works with the model off.

### What agents can and cannot do

| Can | Cannot |
|---|---|
| Read a case as ids, references, labels, counts and times (`CaseFacts`), never its text. | Read a patient's reply, a note, a draft's text or a name; none of them is in the view an agent gets. |
| Ask the drafting route for a message draft, which is validated, falls back to the template and waits for the case owner. | Approve, reject or send a message. `message_approved`, `message_rejected` and `message_sent` are refused for every agency identity. |
| Prepare a call script that says only that the result is ready and the care team needs to talk, and a contact history for the caller. | Contact a patient, or say or hint at what the screening found. |
| Recommend which provider to refer a rejected case to, as an item in the coordinator's inbox. | Request a handoff, accept or reject a referral, reassign an owner, or route an exhausted reroute anywhere but to a person. |
| Look up whether a colonoscopy `Procedure` or `DiagnosticReport` resolves in FHIR (a read; the result goes only to the ledger), and assemble the closure pack. | Close a case, review a case, reopen it, complete the confirmatory test, or supply the evidence reference and signature. The pack says it does not close. |
| Queue a waiting reply for a person by its event id, with the classifier's labels when D13 has already written them. | Classify a reply, read it, or act on it. A person reads every reply. |
| Summarise the day, flag anomalies and fairness gaps by language and channel, and write one sentence on why a case ranks high. | Change a clock, an SLA, an escalation, a flag or the worklist order; no dispatch reads the risk score or its factors. |
| Skip a message draft where an automatic template for the same purpose was sent in the last 7 days. | Draft anything beyond a message draft, or cause any other event. |
| Order its own day's work and write a rationale (a model may do this; rules are the fallback). | Add, drop or change a work item, name a tool, or act on a model's reply that does not validate. |
| Write its own task rows in the ledger, once, then move their status along the permitted graph. | Append a case event of any type, edit or delete a ledger row, or run without a time budget (which covers its reading and planning) and a task cap. |

The line follows the one in the section above: the model proposes, the engine disposes. The difference from drafting is breadth. Drafting is one proposal for one approval. The agency is a larger amount of proposing, and so the same controls are applied at the boundary, in four layers that do not depend on one another: the state machine refuses the actor, the policy table lists what each agent may cause and what no agent may ever cause, the tool lists contain no tool that decides, and the drafting path keeps its own approval gate. The hazards this introduces (a runaway task loop, a wrong reroute, an instruction hidden in a reply, a draft that skips approval) are in the [hazard log](governance/hazard-log.md) with their tests.

## Where we do use a model and why it is safe

Models are used in four places, drafting patient messages for human approval, ordering the worklist by a calibrated risk score, planning the agency's work queue, and classifying inbound patient replies, plus automatic sending of clinician-pre-approved deterministic templates; no model and no agent can move a case between states, approve a message, change consent or close a case. All of them sit at the edge of the system (ADR-007).

1. **Drafting patient messages (Arabic and English).** From the state of a case, the model proposes the text of a reminder or an explanation of next steps. The draft is only a proposal until the case owner approves it.
2. **A single loss-to-follow-up risk score** (logistic regression on simulator features) used only to order the worklist. It is not a language model. It does not close, escalate or decide care. Without it the worklist is ordered by SLA breach.
3. **Planning the agency's work queue (A22, ADR-033).** A department head's rules produce its candidate tasks, and the planner may put them in priority order and write a short rationale, and do nothing else. It cannot add, drop or change a task or name a tool. It uses the drafting provider, its record/replay cache and its network switch, its reply is parsed strictly, and a cache miss, an error or an invalid reply gives the rule order, recorded in the ledger as a fallback with the reason. The default (`LLM_PROVIDER=template`) uses no model at all.
4. **Classifying inbound patient replies.** A small offline model labels a reply so that it reaches the right person. Low confidence, questions, opt-outs and anything unclear go to a person.

Automatic sending is separate from these: the system may send a deterministic template that a clinician approved in advance, within the consent, frequency and version rules enforced by the state machine. No model writes or chooses that text.

For drafting, the controls are these. The planner's limits are in [ai-boundary.md](governance/ai-boundary.md) section 1 and [agency.md](governance/agency.md).

- **Drafting behind approval.** A model-drafted message reaches a patient only through a prior `message_approved` from the owner (T-D1 is a property test, T-C13 tests the approval UI). The model has no tool that sends a message and no event type that moves a case. A `model:` actor has one row in the state machine's actor table, `message_drafted`, and nothing else is accepted from it, so an instruction smuggled into a patient reply or a document cannot make the model do anything, because there is nothing for it to do beyond returning text.
- **Pre-approved templates are sent automatically, without a model.** Since A21 (ADR-032) the fixed, reviewed templates are sent by the automation actor with no draft and no per-message approval, under a policy file (`config/outreach_policy.yaml`) that the clinical lead signs off; the sign-off is a placeholder until H1, so nothing in the repository claims it has happened. The property that replaces "no `message_sent` without an approval" is: **a `message_sent` is either an approved draft or an allow-listed template with consent and under the cap.** The cap counts every outbound message, automatic or approved, and an opt-out or wrong-number flag from triage stops the automation until a person clears it (T-A48, T-A49).
- **Validation.** Every draft is checked before the owner sees it (language, length, reading level, no clinical content such as a diagnosis or a prognosis, no placeholders left unfilled, only the fields the template allows). A draft that fails is discarded and the template is used. Exact validation rules are defined in the drafting ticket (D3) and tested there.
- **Fallback.** The deterministic template is the default (`LLM_PROVIDER=template`) and works with no network. If the provider is unavailable, slow, returns garbage or fails validation, the template is used and the event is counted as an abstention, which is reported with the evaluation (D11). Tests and the default configuration never call a real provider, and the demo uses cached outputs (D6).
- **Provenance.** For every draft the prompt (or its hash and template id), the model identifier, the draft, the approver and the timestamp are stored as a FHIR `Provenance` resource linked to the message, so a reviewer can see which text came from a model, who approved it and when (D4, D5). This corresponds to the traceability the Abu Dhabi Responsible AI Standard asks for (see the regulatory mapping).
- **Data minimisation.** The intended prompt contains only the fields needed to write the message (first name, language, next step, due date, contact channel), not the clinical record. The prototype contains synthetic data only; a deployment would need a model hosted in-country, to be confirmed in the governance mapping, before any real data is sent.
- **Disclosure.** The patient-facing text tells the patient the message is automated assistance reviewed by their care team, and a human contact route is always present ("I don't understand this" creates a task for a person).

What remains to verify: the validation rules in D3 are specified in the ticket, not yet implemented at the time of writing; the effect of the approval step on coordinator workload is an assumption in the pilot cost model; and the Arabic wording is subject to native-speaker review (T-E14).
