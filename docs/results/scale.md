## Local cluster

### Chart bugs found and fixed on apply

Applying the production chart to a real cluster exposed four defects, fixed in the chart (commits `f529e6e` and `b93af1e`):

1. **Scheduler liveness probe.** The probe required `/tmp/scheduler.json`, which only the leader writes, so a follower failed the liveness probe. A missing file now means follower and passes; a stale file (older than two minutes) still fails. The probe also gets `timeoutSeconds: 10` because Python start-up under the 250m CPU limit exceeds the 1 s default.
2. **NetworkPolicy, database CIDR.** The egress rule to the database must match the database's pod or private-endpoint address, not a Service ClusterIP (a policy is evaluated after the Service address is translated); the FHIR and IdP egress rules are now rendered only when a CIDR is set.
3. **NetworkPolicy, ingress CIDR.** There was no way to allow traffic from a node or host range, so a NodePort was unreachable from outside the cluster; the chart gained `networkPolicy.ingressCidrs`.
4. **Service `nodePort`.** The Service template could not set `nodePort`; the chart gained `api.service.nodePort` (only with `type: NodePort`).

## Failover drill (`failover.json`)

Tool `tools/k8s/failover_drill.py`. 5 force-delete runs, 3 graceful deletes and 3 hard kills, each over a 180 s window with the kill at 60 s. Per run the drill seeds 1,500 open cases whose reminder and escalation triggers fall due uniformly over the window, so the sweep always has work, and a client issues about 2 new-case flows per second (create, accept ownership, contact, acknowledge, read) through the NodePort, retrying a failed request with the same id. Lease TTL 30 s, scheduler interval 10 s, fencing true, 3 API and 2 scheduler pods.

How each mode kills: **force** = `kubectl delete pod --grace-period=0 --force` on the scheduler leader and the API pod holding the background lease (no lease release); **graceful** = ordinary delete (the processes release their leases on SIGTERM); **hard** = SIGKILL of both containers through the node's runtime, then the pods are force-deleted. The full method text is in `failover.json`.

## Findings that need `api/` changes (open items, owned by the API team)

These were found by the runs above. Nothing in `api/` was changed in this work; each item states the measured evidence, not a fix.

### 1. The watchdog scan replays every open case (O(N))

- A full replay of every case takes 224.0 and 230.4 s at 1,000,000 cases in `sweep.json` (`full_scan_seconds`; per size and worker count: 100,000 cases/1 worker(s): 9.9 s, 100,000 cases/4 worker(s): 10.8 s, 500,000 cases/1 worker(s): 74.2 s, 500,000 cases/4 worker(s): 94.1 s, 1,000,000 cases/1 worker(s): 230.4 s, 1,000,000 cases/4 worker(s): 224.0 s). The watchdog scan (`POST /watchdog/scan`) replays every open case too; `values-kind.yaml` records that it has no due-index, so a scan is O(open cases) and the cluster's own measurement of it at about 1.04M cases was 224-230 s (a comment in that file, consistent with the full-replay figures above).
- In the soak the watchdog client gave up after about 120 s in 8 of 8 scans ("timed out"); the API kept working on each, and the pod that held it rose by 181 to 255 MiB at peak and stayed more than 50 MiB above its earlier level in 3 to 7 of the 60 s samples.
- With the watchdog at its chart-default 10 s interval, scans pile up: no tested rate passes (at 50/s p99 is 2579.52 ms with the watchdog on and 124.51 ms with it off; the lowest rate tested with it on, 20/s, already fails), and requests fail from 40/s.
- Because of it the cluster runs the watchdog every 900 s instead of 10 s, which is a deviation from production (see Local cluster). At the interval of 10 s the production default is only safe while a scan is much shorter than the interval; the capacity plan below computes where that stops.

### 2. The agency pass reads the whole case table and OOMs a pod

- `values-kind.yaml` records that the agency layer's pass reads the whole case table every 6th sweep and OOM-kills an API pod at this population, which is why the cluster runs with it off; the further observation that the pass fails at its 400-order cap comes from the run's notes. None of this is captured in the four JSON files: the soak, the latency stages and the sweep cells all ran with `agencyEverySweeps` = `0` (off). It is an observation of the run, not a number in this report.

### 3. `GET /cases?state=` is unbounded

- One request for the 873,479 cases in `patient_acknowledged` ended in `RemoteProtocolError` after 17.4 s and an API pod was `OOMKilled` (memory limit 768 MiB); the other two pods did not restart. The endpoint answers the whole state in one response, so its cost grows with the number of cases in it; it needs pagination or a SQL-side filter (an `api/` change).
- Even bounded (the soak's worklist state held 300 cases), the worklist is the slowest endpoint: p50 154.51 ms and p99 1055.87 ms in the soak, against p99 86.04 ms for `GET /cases/{id}`.

### 4. Duplicate and unused indexes on `events`

- `events_case_id_seq_idx` duplicates `events_case_id_seq_key` (same columns, 294 MiB each at 1,000,000 cases). Experiment on the throwaway `closure_load` database: dropping it cut the 1,000,000-case sweep from 64.18 s to 52.77 s with 1 worker (the tuned repeats ranged 60.05 to 79.43 s).
- `events_genesis_patient_ref_idx` was never scanned during the sweep (see Index findings); other code paths were not measured.

### 5. API pod memory grows during the soak

- Anon memory of the three API pods grew at 30.2 to 130.6 MiB/h over 2.08 h (per pod in the Soak table); the worst pod, `closure-api-7b75d9d58c-v2n6v`, went from 97.5 to 302.4 MiB with a peak of 484.9 MiB against a 768 MiB limit. Extrapolating its fitted slope linearly (an extrapolation, not a measurement), it would reach the limit about 3.6 h after the end of the run. The growth is linked to the scan path: the watchdog scans and the pods they land on are the visible excursions; the slope's cause was not isolated by a separate run without the watchdog.

### 6. The `heartbeats` table accumulates a row per scheduler pod forever

- Each follower scheduler posts a heartbeat under `scheduler-follower-<pod>`; no row is removed when the pod goes away. Rows older than 120 s whose pod is not in the cluster's pod list: first sample of the soak 2 of 3 follower rows, last sample 2 of 3 (`scheduler-follower-closure-scheduler-866cb7dd5c-5wtkl` age 8375.9 s, `scheduler-follower-closure-scheduler-866cb7dd5c-c7gr2` age 9038.8 s). Every rollout or reschedule adds one.

### 7. The daily catch-up burst at 1,000,000 open cases does not fit in the 10 s loop on this host

- Best sweep at 1,000,000 cases: 33.64 s with 4 workers (`baseline`; with 1 worker 60.05 s to 87.30 s). The steady-state loop does fit: 0.09 to 0.22 s for the sweeps that follow the daily one, and an idle pass takes 0.10 to 1.13 s. This is a statement about the burst that follows the day's first sweep, not about every sweep.

## Capacity plan: the whole emirate

**What is measured and what is assumed.** Measured (read from the JSONs): sweep times at 100k, 500k and 1M open cases, the full-replay cost, events and bytes per case, the database size, the API's sustainable rate (3 pods, 1 CPU each), memory and CPU per pod. Assumed (`tools/k8s/capacity_inputs.yaml`): case volumes beyond FIT, how long a case stays open, events per case over its life, requests per event, the peak factor, the laptop-to-cloud safety factor, the availability zones, and every price. **All measurements were taken on a laptop-class shared VM (Apple M4, Docker Desktop 10 CPUs / about 8 GB, load generator on the same host); no Azure resource was measured.** Cloud sizing therefore divides measured throughput by, and multiplies measured times by, a safety factor of 2 (a judgement, not a measurement).

### Recommended deployment

Replicas and sizing rules: API replicas = max(zones, ceil(peak / derated per-pod rate) + 1) (N+1, one per zone, `topologySpread` on); scheduler 2 (one leader, one follower); watchdog 1. Nodes: the smallest VM size whose vCPU count covers the API CPU limit (one CPU per sweep worker), with the autoscaler's maximum of API pods (6) fitting on the remaining nodes after losing one node; 0.6 vCPU and 2.0 GiB per node reserved for system pods (assumed). Database: smallest GP Ddsv5 size whose RAM x 0.5 holds the retained database (5 years of cases), then raised to a per-scenario floor (judgement); storage = max(data x 3, floor) rounded up to a size step. Zone-redundant HA on (Burstable has none).

Notes on the estimate:

- AKS Standard tier ($0.10 per cluster-hour) is used; the Free tier is $0 at headline but the API lists a "FreeTierInfrastructureCost Uptime SLA" meter at $0.05 per hour effective 2026-10-01, which would be $36.50 a month: **unverified** whether it is charged on Free-tier clusters. Without the SLA tier, path A is lower by $73.00 (base) before that meter.
- AMD nodes (D2as_v5 / D4as_v5) would save $26.28 (small, base) and $50.37 (high) a month; the kind nodes ran on aarch64 (the Postgres build string in `sweep.json` says so), so the images measured here are arm64 and amd64 images must be built and re-measured for Azure.
- The gateway is WAF v2; Standard v2 without WAF would save $166 (small, base) and $179 (high) a month.
- Egress: first 100 GB free, then $0.181/GB (Microsoft network, the default) or $0.12/GB (internet routing); the egress volumes are assumptions. Internet routing would save $6.10 a month in the high scenario.
- PostgreSQL high availability: the standby is billed at the same rate as the primary, so compute and storage are counted twice (Microsoft reliability documentation, linked in `capacity_inputs.yaml`). Backup is billed only above a free allowance, taken as the provisioned storage (**unverified**); the backups here stay below it, so the line is $0.
- Path B charges every always-on Container Apps replica at the *active* vCPU rate, which overstates the cost of idle replicas (the lower idle rate was not part of the price inputs); the monthly free grant is shared with anything else in the subscription; the environment-hour meter is carried from `tools/pilot/inputs.yaml` (read 2026-10-25) and its applicability to this environment is unverified there. In the high scenario the 4-CPU API replicas are billed all month although the 4 workers matter only during the daily catch-up burst, so path B overstates the high scenario more than the others.
- `docs/commercial/business-case.md` section 9.1 prices a larger Container Apps build-up for the licence (with a FHIR server, observability stack, registry, private endpoints and a test environment) on prices read on 25 October 2026; the two are not meant to match: this plan prices only the closure workloads, the database, the gateway, logs and egress.

### What this plan does not show

- No Azure environment was built or measured. The safety factor, the zone count, every volume beyond FIT, the open duration, the events per case, requests per event and the peak factor are assumptions; changing them moves the open population, the load and the cost, and `capacity_inputs.yaml` is where to do it.
- The plan assumes the open items above are fixed or mitigated: the watchdog scan, the agency pass and the unbounded worklist are not safe at large populations as the code stands (findings 1 to 3). At the base scenario's population they are smaller problems, but they are not measured at that population in this report.
- HL7 ingestion, the FHIR projection, the web application and observability were not part of the load; their cost and load are not in this plan.
