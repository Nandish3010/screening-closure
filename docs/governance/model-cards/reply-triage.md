## Intended use

A patient answers a result-ready message by SMS or WhatsApp, in Arabic, English, Arabizi or a mixture. A coordinator records the reply (`POST /cases/{id}/replies`). The classifier labels it with one of nine intents (`confirm`, `reschedule`, `cannot_attend`, `dont_understand`, `wrong_number`, `already_done`, `opt_out`, `question`, `other`) and a calibrated confidence. When the intent is in the auto-handled set and the confidence reaches the threshold (0.553, `eval.json` `threshold`), it writes a `callback_requested` or `review_requested` flag on the case; otherwise it asks a person to read the reply. Flags move nothing: they are work for a person.

## Out-of-scope uses

- Any clinical decision, answering the patient, withdrawing or restoring consent, closing, reopening or moving a case. The actor `system:triage` has one row in the actor table (ADR-035 in `project/DECISIONS.md`); the state machine refuses the rest.
- Handling `opt_out`, `question` or `other` without a person: these always go to review, whatever the confidence.
- Languages it was not built for, voice, and replies longer than 600 characters (a longer reply always goes to a person; red-team notes in [red-team.md](../red-team.md) section 10).
- Counting as human activity: a reply does not reset the idle clock that makes the watchdog flag a neglected case.

## Data

Synthetic only. 3,069 messages generated by `tools/triage/generate_dataset.py` from 394 hand-written templates (plus nine emoji-only messages) with slot variation, typos, spelling variants, emojis, Arabizi and mixed script. Split by template into 2,147 train, 371 validation and 551 test messages (`docs/results/triage/eval.json`, `n.train`, `n.val`, `n.test`). The Arabic was written by developers, not by Arabic-speaking clinicians or coordinators. Gulf colloquial coverage is thin; other dialects are not represented. No real patient text, identifier or phone number is in the data (`tests/test_phi_scan.py`). A 100-line sample for native-speaker review is in `docs/results/triage/h2_review_sample.csv` (review not done).

## Limitations

- Synthetic test data written by the same people as the training data: the figures say little about real replies. Over-confidence on real data is expected and unmeasured.
- There is no deterministic opt-out backstop for replies of 600 characters or fewer; the model alone decides the label. A real opt-out read as `confirm` or `reschedule` is the most important unmeasured risk (HZ-25 in [hazard-log.md](../hazard-log.md)). One test opt-out was labelled `other` (still goes to a person).
- Weak intents: `dont_understand` recall 0.656 and `confirm` F1 0.800 (`per_intent`).
- Prompt injection can at worst produce a wrong label from nine; there is no free-text output (HZ-28).
- If the worker dies it is not restarted in this version; every later reply is `unavailable` and goes to a person.

## Human oversight

A person reads every reply the system does not handle, with its text, through `GET /cases/{id}/replies`, and the coordinator reads replies in the pilot regardless. A person clears every `opt_out` and `wrong_number` hold (`consent_updated`, `contact_updated`). Before any use on real replies: a shadow period where the output is shown but decides nothing, a labelled sample of real consented replies, per-language re-evaluation and DoH approval (reply-triage-card.md section 8).

## Monitoring

- Exists in code today: every classification is an event `reply_classified {intent, confidence, model_id, needs_human}`; HTTP metrics `http_server_request_duration_seconds` for the replies route; logs a warning "reply triage model unavailable" on load failure (`api/app/triage/classify.py`).
- No triage-specific Prometheus metric or alert exists yet. Proposed: needs-human rate, confidence distribution and per-language needs-human rate computed from `reply_classified` events, with the thresholds in [ai-incidents.md](../ai-incidents.md) section 5.

Incident handling: [ai-incidents.md](../ai-incidents.md).

## Kill switch

Set `TRIAGE_ENABLED=0` in the API's environment and restart the API (`api/app/triage/classify.py:202`; the result is latched for the process). Every reply is then `{intent: other, confidence: 0, model_id: unavailable, needs_human: true}` and goes to a person. The compose file does not pass this variable today; add it under the API service environment (to verify on the deployed stack).
