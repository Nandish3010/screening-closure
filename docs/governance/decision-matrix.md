# Automated-versus-human decision matrix

Who, or what, may take each action in the system, what evidence it needs, what it changes, and which test shows the restriction holds. One row per event type in the final vocabulary ([PLAN.md](../../project/PLAN.md) section 6), plus the routes that matter for control. This is a design record for reviewers and regulators, not a compliance claim.

Authority is the code: `api/app/policy.py` (who may try), `api/app/state_machine.py` and `config/pathways/colorectal_fit.yaml` (whether the event is valid). The state machine decides whether an event is valid; the policy table decides who is allowed to try. Pathway v0.2; every event type in `policy.py` has a row, which `tools/check/docs_check.py` (T-E6) checks.

## How to read it

- **Automated actor** means an actor whose name starts with `system:`, `scheduler`, `watchdog` or `model:`. Automated actors cannot log in as users: `POST /auth/dev-login` refuses those role names (`automation` and `agency` among them), and a validly signed token still cannot carry one (ADR-012). The automated identities that can call the API are four service tokens: the scheduler's, which maps to `system:scheduler` and may emit `mark_overdue`, `escalate` and the bounce form of `handoff_rejected`; the watchdog's, which maps to `system:watchdog` and may emit `watchdog_flagged` only (A11); the automation's (A21, ADR-032), which maps to `system:automation` and is **not allowed on the events route at all**: its only use is to call the two scan routes, and the automation writes its events in process (`acknowledge`, `assign_ownership`, `complete_confirmatory`, `closure_proposed`, a re-route `handoff_requested`, a pre-approved-template `message_sent`, an exhausted-reroute `review_requested`, nothing else); and the agency supervisor's, which is optional (`AGENCY_SERVICE_TOKEN`), maps to `system:agency:supervisor`, may call `POST /agency/run` and no other route, and may emit no event at all (A22, ADR-033). The notification mock (`system:notifier`), the consent ledger (`system:consent`), the reply triage (`system:triage`, D13, ADR-035) and the five department agents of the agency (`system:agency:<department>`) act in process and have no token or route.
- **Who refuses an automated actor.** One default-deny table in the state machine, `ACTOR_EVENTS`, maps each actor (a person by role, each named service, any `model:`, any `system:agency:`) to the event types it may write, and `step` applies it before anything else: an actor with no row, or an event type not in its row, is refused whatever the state or the payload. The agency's row is empty, and `step` refuses the `system:agency:` prefix by name first (section "Agency actors"). The pathway's `human_only_events` list is kept as documentation of the decisions only a person makes, and a test checks that no service row holds any of them except the one documented relay (`RELAYED_HUMAN_EVENTS`: `system:triage` passes on the patient's own `callback_requested`, D13); `close` is refused for any automated actor by the closure guard. The policy table (`EVENT_POLICY`) then decides which role may try over HTTP. The "Automated actor?" column says which applies. Tests: T-A51 (`api/tests/test_actor_table.py`, exhaustive over actors, event types and states, including a grid over every row after the M5 merge).
- **What it changes** uses three words. `state`: the main or side state moves. `flag`: a derived flag in the read model changes (`overdue`, `escalation_level`, `escalation_accepted`) and the state does not. `nothing`: an annotation that is recorded and changes neither the state nor a flag (it may still set the owner or feed a later step, as stated).
- **Test** cites the T-ID from [TEST-CASES.md](../../project/TEST-CASES.md) and, where one exists in the repository, the test name. "Pending A5 (T-A20)" means the test does not exist yet and names the ticket that will write it and its T-ID. Role names are in backticks only where they are part of the policy.
- Roles: `lab`, `primary_care_owner`, `specialist_owner`, `coordinator`, `patient`, `supervisor`, and the service roles `scheduler`, `watchdog` and `agency`.

## What holds in structure

These six properties do not depend on a person following a procedure. Each has a test, and the matrix above is where a reviewer can see the exceptions.

1. **No closure without evidence and a human clinician.** The guard is in the state machine and runs inside the database transaction. No automated actor, and no role other than the two clinician roles, can emit `close` (T-A1, T-A3, T-A4, T-A26).
2. **Automated actors cannot log in as users.** The only automated identities that reach the API are the four service tokens (scheduler, watchdog, automation, agency supervisor), each limited to its own routes and events (T-A26, T-A30, T-A46, T-A65).
3. **`message_sent`, `message_approved` and `message_rejected` have no poster.** Nobody can post them through the events route. `POST /drafts/{id}/approve` writes the approval (with its outbox row) and the notification mock writes `message_sent`, in that order, and nothing else can for a draft (the state machine refuses a send for a draft nobody approved, ADR-030); `POST /drafts/{id}/reject` writes the rejection (T-D1, T-D13, T-D5). The one other writer of `message_sent` is the automation, in process, for an allow-listed pre-approved template: a `message_sent` is either an approved draft or an allow-listed template with consent and under the cap (T-A43, T-A48, T-A49).
4. **Human-only events.** `escalation_accepted`, `handoff_accepted`, `consent_updated`, `contact_updated`, `message_approved`, `message_rejected`, `callback_requested` and `reopen` are in no service's row of the state machine's actor table, so they are refused for any automated actor by the machine itself (T-A14, T-A19, T-A26, T-A51). The one exception is `system:triage` relaying a callback the patient asked for in a reply (D13): the table lists it in `RELAYED_HUMAN_EVENTS`, and the state machine limits it to three reasons with the `source_event_id` of its classification (T-D19).
5. **The automation does the unit steps and nothing else (A21, ADR-032).** `system:automation` may emit only `acknowledge`, `assign_ownership`, `complete_confirmatory`, `closure_proposed`, a re-route `handoff_requested`, a template `message_sent` and an exhausted-list `review_requested`, each under its own conditions in the state machine, and it writes them in process: its token is refused on the events route for every event type. It can never emit `close`, a human-only event or a message that is not a listed template, and it sends nothing while an opt-out or wrong-number flag is open. People act at the final decisions only: accepting an escalation, approving a model-drafted message, signing a closure, handling an exhausted reroute list (T-A46, T-A49).
6. **No agency actor can emit any case event.** The state machine refuses every event, of every type and in every state, from any actor starting `system:agency:`; no agency role is in `EVENT_POLICY`; the agency token reaches `POST /agency/run` and no other route; and no tool the agents hold writes a case event or causes a decision. The agency is preparation only: the one thing an agent causes is a draft, which the drafting route writes as `model:<provider>` under that route's rules and which waits for the owner's approval. A handoff request, a reply label and every other decision stay with a person or the service that owns them (T-A60, T-A61).

## What the matrix does not yet cover

- Scoping of owners by organisation. Owners act only on cases they own (A5), but there is no per-organisation scoping beyond the provider claim (limitation L29).
- Nothing about role-by-route denial: [rbac-matrix.md](rbac-matrix.md) is generated from the OpenAPI route list, probes every role against every route and event type (own case and another's), and fails `make test-security` if it drifts or a route has no policy. It found one gap: `POST /cases/{id}/drafts` is not owner-scoped (G-1).
- An `erasure` marker event, if the implementing ticket for ADR-025 adds one. It is not in the vocabulary, so it is not in the matrix.

## Keeping it true

Completeness is meant to be checked by a test (T-E6, pending F1 docs-check): every event type in the pathway config and in `EVENT_POLICY` must have a row here, and the roles in the first column must equal the policy. When an event type, role or route is added or changed, update this file in the same commit.
