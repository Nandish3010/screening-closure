# Decisions

Architecture decision records, one per decision. Add new entries at the end with the next number; change a decision by adding a new entry that supersedes the old one, not by editing history. Status is `accepted` unless stated. Plan: [PLAN.md](PLAN.md).

## ADR-001: Deterministic engine with human gates

**Context.** The domain is safety-critical: a wrong or invented closure means a patient with a positive screening result is treated as finished. The brief asks for an auditable system and for a clear position on agentic approaches. Whatever decides a state change must be explainable line by line to a regulator and give the same answer when replayed.

**Decision.** State transitions are decided by deterministic code (a pure state machine over a pathway config) and by humans. A language model may draft a message or summarise a document but never moves a case between states, escalates, or decides a closure. The design is "the model drafts, humans decide". A model actor (`model:` prefix) is treated as automated and cannot emit state-changing events; a closure needs `evidence_ref` and `signed_by` from a non-automated actor.

**Consequences.**
- The closure invariant can be proved by property test (T-A1) rather than argued in prose.
- The system works unchanged when the model is unavailable; the template fallback covers drafting.
- We give up open-ended automation. Anything the engine cannot decide becomes a task for a person.
- The comparison with agentic orchestration is written up neutrally in `docs/design-choices.md` (auditability, replayability, latency, cost per case, failure modes, model unavailable).

## ADR-002: Event sourcing with derived current_state

**Context.** We need a full audit trail, replay for verification, and idempotent handling of retries and duplicates. A mutable "status" column would lose history and could drift from what actually happened.

**Decision.** The append-only `events` table is the source of truth. `cases.current_state` is a derived read model, never trusted without replay: every append replays the stored log, checks it against `current_state`, and raises `StateCorruption` on disagreement. Every event carries an `event_id` used as an idempotency key.

**Consequences.**
- Replay determinism is testable (T-A2, T-A9) and the timeline is the audit log.
- Reads of state are cheap but writes pay for a replay per append; fine at pilot scale, to be measured by the 100,000-case load test (T-F8).
- Schema changes need care because history is permanent. Migrations run at API startup from `api/migrations/*.sql`.

## ADR-003: Transition check inside the database transaction

**Context.** Checking a transition in the API process and then writing lets two concurrent requests both validate against the same old state and both commit, which could break the closure invariant under concurrency or retries.

**Decision.** The state-machine check runs in the same transaction that locks the case row (`SELECT ... FOR UPDATE`) and inserts the event. Validate-then-append is atomic; an invalid transition leaves nothing behind.

**Consequences.**
- Concurrency and atomicity are proved by integration tests (T-A5, T-A7).
- Writes to one case are serialised; cases are independent so this does not limit throughput across cases.
- The state-machine function must stay pure and fast because it runs while the lock is held.

## ADR-004: Append-only triggers in the database

**Context.** Application code can be correct and still be bypassed by a bug, a manual query, or a migration mistake. An audit log is only credible if it cannot be edited.

**Decision.** Database triggers reject `UPDATE`, `DELETE` and `TRUNCATE` on `events` (`events_forbid_mutation`).

**Consequences.**
- Immutability holds below the application layer (T-A8).
- A database superuser can still drop the triggers, so this is tamper-evidence in a pilot setting, not a defence against a malicious administrator. Production would add access controls and log shipping. This goes in the limitations table.
- Test cleanup cannot truncate `events`; tests use their own cases or a separate database (F2).

## ADR-005: Synthea for the cohort, and its US-geography limitation

**Context.** We need a realistic synthetic population in FHIR R4, with no real patient data, and a seed so it is reproducible. We have no access to UAE data and would not use it for a hackathon prototype.

**Decision.** Use Synthea v3.3.0 (pinned jar, sha256 checked, run only inside a container) with seed 20261017 and a fixed reference date, for 300 living patients aged 45 to 75. Synthea has no FIT screening for this pathway, so FIT results are generated by our own seeded script at an assumed positivity rate. Version, seed and parameters are recorded in `docs/data-provenance.md`.

**Consequences.**
- Fully synthetic and reproducible.
- Synthea needs a US state (we use Massachusetts), so names, addresses, facilities and care patterns are US. There are no Arabic names and no UAE demographics or health-system structure. Patient language and contact channel therefore come from the simulator as labelled assumptions, and the limitation is stated in the provenance and limitations documents.
- Which patients test positive is unrelated to their clinical history. The cohort demonstrates the pathway mechanics, not epidemiology.

## ADR-006: HAPI FHIR on the shared Postgres

**Context.** HAPI's default in-memory H2 database ran out of heap when loading the synthetic cohort (about 1 GB of FHIR JSON for 300 patients). We also want cases and FHIR resources to stay consistent after a reset.

**Decision.** HAPI FHIR R4 stores its data in the same Postgres database as the case store, in its own `hfj_*` and related tables, which do not collide with `cases` and `events`. The JVM heap is raised to 3 GB for large patient bundles.

**Consequences.**
- `make reset` (`docker compose down -v`) wipes cases and FHIR resources together, so they cannot disagree.
- One database to back up and size, but HAPI and the case store share load and a failure domain. Acceptable for a prototype; a pilot would separate them.
- The image tag was `latest`, which weakens reproducibility. F12 pinned it to `hapiproject/hapi:v8.12.0-2` (HAPI FHIR 8.12.0, digest `sha256:0ff86aac4c7bd13a1ee226444a70263bb46ed1c28ef543c30a44f865b80ca04e`, identical to what `latest` resolved to on 2026-10-18 and to the running container's `X-Powered-By: HAPI FHIR 8.12.0`). The tag `v8.12.0` does not exist; starter-image tags carry a build suffix (`-1`, `-2`), so the pinned tag was verified by pulling it. Upgrading is a deliberate edit of `docker-compose.yml` followed by `make reset && make demo-seed && make check`.

## ADR-007: AI only at the edges

**Context.** Language models are useful for drafting patient messages in Arabic and English, but they are non-deterministic, may be unavailable, and can produce wrong or unsafe text.

**Decision.** AI is allowed in exactly two places. (1) Drafting patient messages: the draft is validated, shown to the case owner, and not "sent" until the owner approves; prompt, draft, approver and timestamp are stored as Provenance; a deterministic template is the fallback and the default (`LLM_PROVIDER=template`). (2) A single calibrated loss-to-follow-up risk score (logistic regression) used only to order the worklist; it never closes, escalates or decides care. Model outputs used in the demo are cached so the demo needs no network.

**Consequences.**
- The approval gate is structural: there is no code path to `message_sent` without `message_approved` (T-D1).
- Fallbacks are counted as the automation abstention rate and reported in the evaluation.
- Jais and Azure OpenAI are optional adapters and are never called by tests or by the default configuration.
- The risk score is on the cut line; without it the worklist is ordered by SLA breach alone.

## ADR-008: FHIR as the data model, Malaffi as a stated target

**Context.** Interoperability is a judging concern and a real adoption barrier. Abu Dhabi's health information exchange, Malaffi, is the obvious integration target, but we have no access to it and cannot claim an integration.

**Decision.** Model every object as a FHIR R4 resource: `DiagnosticReport` (the FIT result), `Task` (the case and ownership), `ServiceRequest` (the referral), `Appointment`, `Communication` (patient messages), `Consent`, `Provenance` (audit). The event log remains the source of truth and FHIR resources are a projection of it. The documentation includes a one-page adapter plan for Malaffi worded as a target, not a claim, and the names are verified against official sources before they are cited.

**Consequences.**
- The projection can be validated against HAPI (T-A33).
- Two representations exist (events and resources); the projection must be rebuildable from events.
- No claim of integration appears anywhere; the wording is checked by review (T-E4).
- `Appointment` and `Communication` mapping is on the cut line and may be a stub.

## ADR-009: Working-day calendar, UAE default, configurable

**Context.** SLAs in the pathway are in working days (for example acknowledge within 2, book within 14, complete within 45). Counting calendar days would flag weekend breaches that are not breaches. The UAE weekend is Saturday and Sunday for the federal public sector and is not the same everywhere in the world.

**Decision.** SLA due dates are computed on a working-day calendar. The default is the UAE one: Monday to Friday are working days, Saturday and Sunday are the weekend. The weekend set and an optional holiday list are configuration, not code. The scheduler reads time only from the injectable simulation clock.

**Consequences.**
- Due dates are testable by table and by property (T-A12, T-A13).
- Public holidays that move with the lunar calendar are not predictable in advance, so the initial holiday list is empty and documented as an assumption until a source is chosen (A1).
- Verify the weekend convention against an official source before citing it in the submission; some private-sector employers and some emirates may differ, which is why it is configurable.

**Assumption recorded in A1 (holiday list).** `config/calendar.yaml` ships with `holidays: []` and the time zone `Asia/Dubai`. Reason: the dates of Eid al-Fitr, Eid al-Adha and the Islamic New Year depend on moon sighting and are announced days ahead, the fixed-date holidays (for example National Day on 2 and 3 December) can be added by any deployment, and we have no authoritative source in the repository, so a guessed list would be an unsourced number inside the SLA arithmetic. The consequence is that every due date in the prototype and in the evaluation assumes no public holidays, which can only make a due date earlier than reality (a conservative direction for a safety net) and is stated in the limitations table. Adding a holiday is a config edit and needs no code change (tested in `test_calendar.py`).

**Instant semantics (A1).** The calendar day of an instant is its date in the configured zone. A start on a non-working day counts from 00:00 of the next working day; the time of day of the (effective) start is kept, so a 2 working day SLA started Thursday 10:00 is due Monday 10:00. `add_working_days` always returns a working day and `working_days_between(start, add_working_days(start, n)) == n` holds for every start (property-tested, T-A13).

## ADR-010: No SNOMED CT; LOINC and plain text only

**Context.** Codes make resources interoperable, but SNOMED CT is distributed under licence terms. A public repository with a bundled synthetic dataset should not depend on checking licence status for each user.

**Decision.** Use LOINC for the one coded concept we need (the FIT result, LOINC `29771-3`) and plain text in `CodeableConcept.text` elsewhere. No SNOMED CT codes appear in code, data or documents.

**Consequences.**
- The repository is redistributable without licence review of the terminology.
- Results are less machine-interpretable than fully coded ones. The adapter plan notes that a deployment would map to the terminologies its exchange requires.
- The LOINC display name changed between releases while the code did not; the code is authoritative and the display is re-verified before external submission (see `docs/data-provenance.md`).

## ADR-011: Side states are real states; overdue and escalation are derived flags

**Context.** The first pathway file listed six "side states" (`overdue`, `escalated`, `referral_rejected`, `consent_withdrawn`, `reopened`, `lost_contact`) without transitions. Two kinds of thing were mixed in that list. Some change who must act next and what is allowed (a rejected referral, withdrawn consent, a patient we cannot reach, a reopened closure). Others describe the clock: a case can be overdue and in `patient_contacted` at the same time, and can sit at escalation rung two while still awaiting the patient. Modelling the second kind as states would force a product of states (`patient_contacted` x overdue x rung) or lose the main state while overdue.

**Decision.**
- `overdue` and `escalated` are not states. The main-state machine is unchanged and the read model carries `overdue`, `escalation_level` and `escalation_accepted`, derived by replay from `mark_overdue`, `escalate` and `escalation_accepted` events. They reset when the case changes state (a new state is a new obligation with a new clock), except across a consent-withdrawn excursion, which keeps them.
- `referral_rejected`, `consent_withdrawn`, `lost_contact` and `reopened` are real states with transitions in the YAML (list in PLAN.md section 6). Events that annotate a case without changing its state are listed under `annotations:` and are valid in every open state, never in `closed`. The loader refuses an annotation that is a closing or main-path event, a transition into `closed` from anywhere but `clinician_reviewed`, and any transition into `closed` that does not require `evidence_ref` and `signed_by`. The closure guard in the state machine is unchanged.
- `consent_updated{withdrawn:true}` is allowed from every open state and freezes outreach. The prior state is remembered by replay (`resume_state` in the read model) and restored by `consent_updated{withdrawn:false}`. It is deliberately not read from the client's payload: a client-chosen resume target would let a caller jump a case to any state, including past review. This departs from the original sketch ("tracked in payload `resume_state`"), and keeps the same observable behaviour.
- `reopen` takes `closed` to the side state `reopened` and needs a human actor and a `reason`. From `reopened` the only way on is `clinician_review` to `clinician_reviewed`, so a reopened case reaches `closed` again only through a fresh `close` with evidence and sign-off.
- `lost_contact` is entered from `patient_contacted` by `mark_lost_contact` with `failed_attempts` of at least 3 (the 3 is an assumption pending the clinician review, H1) and left by `contact_patient`. `referral_rejected` returns to `owner_accepted` through `handoff_accepted` or `reassign`; `reassign` is added to the vocabulary because the sketch named it but did not list it.
- Some events may not come from automation (`human_only_events`: `escalation_accepted`, `handoff_accepted`, `consent_updated`, `message_approved`, `callback_requested`, `reopen`).
- SLA obligations: a state's SLA is the SLA of its outgoing transition event (for example `patient_contacted` awaits `patient_acknowledge`, 7 working days). `lost_contact` and `reopened` inherit the SLA of the event that leaves them (`contact_patient`, `clinician_review`); `referral_rejected` and `consent_withdrawn` have none here because their timers belong to A5 (bounce) and A6 (human review). While consent is withdrawn the SLA clock is not paused: it keeps running and a breach is detected once the case resumes.

**Consequences.**
- Closure properties (T-A1, T-A2, T-A14) run over the whole alphabet with a stateful fuzzer and a hand-written oracle of allowed state changes.
- `GET /pathways` now serves the richer YAML (`any_open`, `to: resume_state`, `when`, `min`), which is expanded by the loader; clients that read the raw YAML should use the loaded transitions instead.
- Consent events after closure are not modelled (a closed case accepts only `reopen`).
- The audit trail shows `mark_overdue`/`escalate` as events with timestamps, so "why is this case overdue" is answered by the timeline alone.

## ADR-012: Identity from signed dev tokens; default-deny policy tables

**Context.** Until A8 the caller named its own `actor` in the request body, so any client could post `close` as a clinician. The closure guard stops automated actors by name, which is only meaningful if names cannot be forged. We also need roles for the interfaces (Cut C) and a story for the regulator: who was allowed to do what, enforced by code rather than by the UI.

**Decision.**
- Identity is established per request from a bearer token; the event `actor` is `role:name` derived from it. A body that carries `actor` is rejected (422). The only roles a token can carry are the six user roles; `system`, `scheduler`, `watchdog` and `model` cannot authenticate as users, even with a validly signed token.
- Development login (`POST /auth/dev-login {role, name}`) issues an HMAC-SHA256-signed token using `DEV_AUTH_SECRET`. The default secret exists only for local development: with `APP_ENV` other than `dev` the API refuses to start while the secret or the scheduler service token is still the built-in default. `DEV_LOGIN_ENABLED=false` removes the login route. Tokens do not expire, because the API never reads the wall clock (T-A17); a production deployment replaces `app/auth.py` with an OIDC verifier that yields the same `Identity`.
- The scheduler authenticates with a static service token (`SCHEDULER_SERVICE_TOKEN`), is `system:scheduler`, and may emit only `mark_overdue`, `escalate` and `watchdog_flagged`.
- Authorisation lives in `api/app/policy.py` as two default-deny tables: route (method + path template, enforced by an app-wide dependency) and event type (enforced in the event route). A route or event type with no entry is refused, and a test compares the table with the OpenAPI route list so a new route without a decision fails the build. The state machine still decides whether an event is valid; the policy decides who may try.
- Patients are limited to their own case (matched on the genesis `patient_ref`) and to `patient_acknowledge`, `consent_updated` and `callback_requested`. A patient asking for someone else's case gets 404, the same as for an unknown case.
- Extra hardening beyond the sketch: an event's `at` may not be later than the simulation clock. Without it a user could post an event dated in the future and push an SLA deadline out of reach, which is exactly the silent failure the product exists to prevent.

**Consequences.**
- T-A26 and the F7 RBAC matrix test can be generated from the tables.
- Roles are coarse (no per-organisation scoping: any `primary_care_owner` may act on any case). Scoping owners to their own cases comes with the A5 ownership model and is listed in the limitations table.
- `/docs` and `/openapi.json` stay open in development.
- The dev token is a convenience, not an authentication mechanism; the submission must say so.

## ADR-013: The sweep runs next to the event store; the scheduler is its heartbeat

**Context.** The scheduler must find every breached SLA on the simulation clock, emit `mark_overdue` once per breach, and never close a case. It is also the thing we kill on stage, so it must be a separate process with its own heartbeat. The load target (100,000 open cases, F6) rules out shipping every case's history to a client over HTTP on every sweep.

**Decision.**
- The sweep logic is a pure planner plus a runner in `api/app/sweep.py`. The planner takes (case read model, pathway, calendar, now) and returns events; it never reads a clock. The scheduler service calls `POST /scheduler/sweep` every interval with its service token (identity `system:scheduler`; the route is closed to every other caller) and writes the heartbeat. Killing the scheduler stops the sweeps and the heartbeat, which is what the watchdog (A11) checks.
- Due dates: the SLA of the case's current state (PLAN section 6, ADR-011) counted in working days from the event that entered the state (`clock_started_at` in the read model, which the replay sets). A case is late when sim time is strictly after the due time.
- Exactly once per breach: the event id is `uuid5(namespace, case | state | due_at | kind)`. A repeated or concurrent sweep re-plans the same id and the store treats it as a no-op; the state machine independently refuses a second `mark_overdue` for a case that is already overdue. If the planned event is refused because another writer moved the case first, the sweep counts it as `rejected` and re-plans on the next pass.
- The sim clock lives in `app/clock.py`, persisted in the `sim_clock` table (migration 002, one row per `clock_id`, the API uses `main`) so an API restart keeps the simulated date. It only moves forward through `advance`; `reset` is the single explicit rewind. Time is cached in process and the store is read only at start-up, so the API is single-replica by design here.
- `POST /clock/advance` and `POST /clock/reset` are supervisor-only. No code in `api/app` or `scheduler/` reads the wall clock for a decision; an AST test enforces it, with the two heartbeat timestamps as the only marked exceptions.
- The heartbeat file is refreshed every loop, even when the sweep fails, and says whether the last sweep succeeded (`sweep_ok`, `last_ok_wall_ts`), so a live-but-useless scheduler is visible to A11.

**Consequences.**
- The scheduler container stays standard-library only and never touches the database or the calendar config.
- The sweep reads and replays every open case on each pass (chunked, bounded memory); F6 measures whether that needs an index or a materialised due-date column.
- Integration tests pass `only=` so a sweep against the shared dev database touches only the test's own cases.
- Rewinding the clock with `reset` leaves earlier overdue events in the append-only log; `make reset` is the way to start a clean demo.

## ADR-014: Escalation rungs are `escalate` events; a human accepts one with `escalation_accepted`

**Context.** The ladder (reminder at the breach, supervisor after 3 working days, programme coordinator after 7) must never run away from a human who has taken responsibility, and an escalation by itself must not move work: "every rung needs a human to accept". The tracker left the name of the acceptance event to A4, and the earlier draft called the rung event `escalated`.

**Decision.**
- A rung is an `escalate` event with `rung` (`reminder`, `supervisor`, `coordinator`), `level`, `target` (`owner`, `supervisor`, `coordinator`), emitted by the scheduler or by hand by a coordinator or supervisor. The state machine raises `escalation_level` by exactly one and refuses a skipped, repeated or unknown rung, a rung on a case that is not overdue, and any rung after an accepted one. Event ids are `uuid5(case, state, due date, "escalate:<rung>")`, so each rung is emitted once per breach however often or concurrently the sweep runs.
- The acceptance event is named `escalation_accepted`. It is human-only and the actor's role must be in the rung's `accepted_by` list in the YAML (owner roles for the reminder, `supervisor` for the supervisor rung, `coordinator` for the coordinator rung). It may carry `rung`, which must name the latest rung. It sets `escalation_accepted` in the read model, which stops further rungs for that breach. It changes neither ownership nor state: taking the problem on is a separate, deliberate act (`accept_ownership`, `reassign`, or simply progressing the case).
- Timing: a rung is due `after_breach_days` working days after the case's due date, evaluated on the working-day calendar; the sweep emits it when sim time is at or after that instant. All due rungs are emitted in order in one sweep, so a scheduler that was down catches up without skipping. An unanswered rung moves to the next one only through this timing.
- A new obligation (any state change except a consent-withdrawn excursion) starts with a clean ladder: the flags reset and the next breach has new event ids.
- The regulator rung is on the cut line and is not built; the ladder in the YAML has three rungs and the loader checks they are unique and non-decreasing in time.

**Consequences.**
- "Who was told, when, and who took it" is answered from the timeline alone: `escalate` rows, then `escalation_accepted` with its actor.
- A rung accepted by the wrong person is refused by the engine (409), not just hidden in the UI.
- The notification text for a rung (A7) hangs off the `escalate` event; the event names here are what Cut C and the decision matrix (E5) should use.

## ADR-015: Integration tests use their own database, `closure_test`

**Context.** `make test-db` ran against the dev database. Every integration test creates cases and events that nothing can delete (the log is append-only by trigger), so after a few dozen runs the dev database held about 1,200 test cases next to the seeded cohort, and the demo worklist, the sweep and the metrics all saw them.

**Decision.**
- The compose postgres holds a second database, `closure_test`, owned by the same role. A fresh volume gets it from `docker/postgres-init/10-create-test-db.sh` (mounted into `docker-entrypoint-initdb.d`); `make test-db` creates it with the same SQL if it is missing, which covers volumes made before this change. One server, two databases: no extra container, and HAPI keeps using `closure`.
- `make test-db` sets `DATABASE_URL=postgresql://closure:closure_dev_password@localhost:5433/closure_test` (override with `TEST_DATABASE_URL`). `make test-db-reset` drops and recreates it, empty; the test session migrates it again.
- The guard lives in `api/tests/conftest.py` (`pytest_collection_finish`): if any selected test is marked `integration` and `DATABASE_URL` is set, the database name must end in `_test`, otherwise the session aborts with exit code 3 and a message naming the database and the fix. The rule is "marked as a test database" rather than "not named closure", so a typo or a staging URL fails closed. A session-scoped fixture runs the migrations on the test database.
- `make reset` wipes the dev stack, including the polluted test cases and the cohort; `make demo-seed` rebuilds the cohort. The dev database now holds only the seeded cohort.

**Consequences.**
- T-F2 is checked by a unit test of the guard, a real pytest subprocess pointed at the dev URL that must abort, an integration test asserting `current_database()` ends in `_test`, and a before/after row count of the dev database around `make test-db` (unchanged).
- The unit suite (`make test`) is unaffected; with `DATABASE_URL` unset nothing here runs.
- Running `pytest -m integration` by hand with the dev URL now fails on purpose.

## ADR-016: Referral handoff: ownership moves only on acceptance; the scheduler bounces silence

**Context.** A referral that nobody answers is how a positive result gets lost: the referrer thinks it is handled, the receiver never saw it. The contract has to say who owns the case at every moment, what an answer looks like, and what happens when there is none. A8 also left every clinician able to act on every case, which makes "who owns it" decorative.

**Decision.**
- `handoff_requested {to_provider}` (the owner, or a supervisor for them) records a pending request in the read model (`pending_handoff`) and changes nothing else. `handoff_accepted` by a clinician (human only; not the requester, not the owner it came from) makes the accepter the `owner`, sets `provider`, and clears the request. `handoff_rejected {reason}` clears it; ownership stays with the referrer. Both answers need a pending request, so an unsolicited acceptance cannot take over a case. One request may be pending at a time. A request needs an owner to hand over from.
- Taxonomy: `capacity`, `wrong_service`, `missing_info`, `patient_declined` (YAML `handoff_reject_reasons`). Anything else is a payload error: HTTP 422, nothing written. `timeout` is a fifth reason that only `system:scheduler` may use, with `bounced: true`; a human using it is a 422, and the scheduler using any other reason is a 422. This is the one `handoff_rejected` the scheduler is allowed to emit.
- The rejection moves the case to `referral_rejected` only from the referral states (`patient_acknowledged`, `confirmatory_booked`), as before. From any other open state it is an annotation that clears the request and leaves the state alone (so a bounce in `consent_withdrawn` cannot lose the remembered resume state). Both are logged with their reason.
- The bounce: the sweep plans `handoff_rejected {reason: timeout, bounced: true}` when sim time is strictly after `requested_at + handoff_response_working_days` working days (YAML, 3; the simulator's `handoff.response_sla_working_days` is also 3). The event id is a uuid5 of (case, request time), so repeated and concurrent sweeps insert it once, and answering first makes the sweep plan nothing. A bounce comes alone in a plan and the sweep re-plans from the new model, because a bounce can change the state.
- Escalation of a bounce: `referral_rejected` now has an SLA, `reassign: 2` working days (a state's SLA is the SLA of its outgoing event; both `reassign` and `handoff_accepted` leave it). The bounce starts that clock, so an un-rerouted case goes overdue and walks the existing ladder (reminder to the owner, supervisor, coordinator). No second mechanism.
- Per-owner scoping, in the API layer (`policy.authorize_owner_scope`): a `primary_care_owner` or `specialist_owner` acts only on a case whose `owner` is their `role:name`, except `accept_ownership` on an unowned case and `handoff_accepted` / `handoff_rejected` on a case whose pending request names their provider. A clinician's provider is a login claim (`provider`, default their name), because the identity had no organisation. Supervisors, coordinators, lab and patients are not owner-scoped.

**Consequences.**
- Passing a case to a specialist is now three events (request, accept, then the specialist acts), not an implicit change of hands. Existing tests that had a second clinician act on a case they did not own were rewritten to go through the handoff.
- A clinician who is not the owner now gets 403 where they used to get 409 or success (for example `close` on a case nobody owns yet). 403 is the right answer: the call is outside their scope before it is a question of state.
- The simulator is unaffected: it logs handoffs itself and validates only the main chain through `apply`.
- Limits: the provider claim is a dev-login convenience (a real deployment takes it from the identity provider); `handoff_accepted` does not check that the accepter's role is `specialist_owner` (the policy allows both clinician roles, so a referral to a primary care provider works).
- The new rules apply on replay. A log written before A5 to A7 that has, say, a `handoff_accepted` with no request, or a `message_sent` from another actor, no longer replays (the sweep reports it under `errors`, and an append to it is refused as corruption). That is acceptable before release; `make reset` and `make demo-seed` rebuild the dev database, and the seeded cohort only contains `case_created` events.
- Web mirror: `web/src/lib/pathway.ts` mirrors SLAs; the new `reassign: 2` row for `referral_rejected` is for Cut C to pick up.

## ADR-017: Consent is an append-only ledger by replay; withdrawal freezes outreach in the engine

**Context.** Patients must be able to say which channels may contact them, whether their data may go to the specialist, and "stop". A withdrawal that only hides buttons in the UI is not a withdrawal: the same API serves the coordinator app, the scheduler and (soon) the message approval path. We also need the history, not just the latest setting: who changed what, when, on whose instruction.

**Decision.**
- `consent_updated` carries any subset of six booleans: `channel_sms`, `channel_whatsapp`, `channel_phone`, `channel_letter`, `share_with_specialist`, `withdrawn`. The ledger is the event log itself. `read_model.consent` is the current value, `read_model.consent_history` is every change in order (`{at, actor, changes}`), both derived by replay (ADR-002); nothing is stored separately. A payload with no known key, or a non-boolean value (`1`, `"true"`, `null`), is a payload error (422). Unknown extra keys are tolerated and ignored.
- Defaults before the patient says anything: every channel allowed and sharing allowed (`updated_at` null tells a reader nothing was recorded). This is an opt-out model, an assumption for the clinician and consent reviews (H1) rather than a legal position; the alternative (nothing allowed until recorded) would make the notification mock refuse every message for the whole seeded cohort.
- `withdrawn: true` is the existing transition into `consent_withdrawn` (ADR-011). `consent.withdrawn` always equals "state is consent_withdrawn" (the state is the authority), and `consent_frozen` is that same fact.
- The freeze is enforced in the state machine, not in the router: while frozen, `contact_patient`, `message_drafted`, `message_approved`, `message_sent` and `handoff_requested` are refused with a message that starts "consent withdrawn" (HTTP 409 from the API, `InvalidTransition` from any store). It does not stop `callback_requested`, escalation, `watchdog_flagged` or channel changes, and it does not stop a human re-recording consent.
- Human review flag: when the API accepts a `consent_updated` that leaves the case frozen with no review flagged, it appends `review_requested {reason: consent_withdrawn, source_event_id}` as actor `system:consent`. The new event type is an annotation; no route can post it (EVENT_POLICY is empty for it) and the state machine accepts it only from `system:consent`, and `system:consent` may emit nothing else. The event id derives from the withdrawing event, so a client retry heals a flag that failed to write and never doubles it. The flag is two appends, not one transaction: if the second fails the withdrawal stands and is frozen (the safe side), the request errors, and the retry completes the flag. The flag clears (`review_reason` null) when consent is restored; the event stays in the log.
- Who may change consent: the patient on their own case and the coordinator recording the patient's instruction (existing event policy); every other role gets 403. Consent updates after closure are not modelled.
- Not decided here: the web client currently sends `{channel, share_with_specialist}` (web/src/api/contract.ts); the backend contract is the six booleans above, so the client needs to send `channel_*` flags.

**Consequences.**
- T-A24: history and derived value come from the same replay, so they cannot disagree; the append-only trigger on `events` makes the history tamper-evident.
- T-A23: nothing can be drafted, approved or sent for a frozen case by any caller; the notification mock (A7) also checks consent itself, so the guarantee does not rest on one layer.
- A frozen case has a reviewer-visible flag and sits in `consent_withdrawn`, which `GET /cases?state=consent_withdrawn` lists. The SLA clock keeps running (ADR-011); a breach is detected once the case resumes.

## ADR-018: The notification mock is the only outbound path, and it is a log

**Context.** The product must show that a message reaches a patient only after a human approved it, and that the system honours consent. The demo runs offline and uses synthetic data, so nothing may actually be sent. The same code path has to be the one D5 (approval) uses, so that "no other path to `message_sent`" is a fact about the code, not a convention.

**Decision.**
- `app/notify.py` has one entry point, `send(case_id, channel, language, purpose, body, ...)`, a Python function (no route). It reads the case's read model and, in order: refuses if consent is withdrawn or that channel is switched off (`blocked_consent`, reason says which), refuses if the case's `case_created` payload flags the contact invalid (`contact_valid: false`, or a per-channel map; `blocked_contact`), otherwise appends `message_sent` from `system:notifier` and logs the row as `sent`. It imports no module that can open a connection (an AST test enforces that, and a socket-blocking fixture proves it at run time).
- `message_sent` has an empty route policy (nobody can POST it) and the state machine refuses it from any actor but `system:notifier`; it is also refused while consent is withdrawn, so a forged call fails twice. `emit_message_sent` is a separate function in the same module for D5 if it needs the event without a log row; it carries the same actor.
- Table `notifications` (migration 003): id, case_id, channel, language, purpose, body, status, reason, event_id, created_at (simulation time), append-only by trigger like `events`. Status is `queued | sent | blocked_consent | blocked_contact`. A CHECK ties `status = 'sent'` to having a `message_sent` event; `event_id` names that event but is not a foreign key (the event is always written first, and a foreign key would make `TRUNCATE events` fail on the constraint before the append-only trigger can refuse it, which the existing integration test checks). `queued` is reserved for an approved-but-undelivered message and nothing writes it today, because the mock delivers at once.
- Blocked attempts are logged with their reason but write no event: nothing was sent, and the log is where a reviewer sees the refusal. This departs from the T-A25 wording "a withdrawn channel produces no row"; the intent (no outbound record) holds because only `sent` rows are outbound, and the test cases now say so.
- Two writes, not one transaction: `message_sent` is appended first, then the row. If the second fails the audit trail has the event and the log lacks the row (the safe side for a regulator), and the exception reaches the caller. A single transaction would need the notification table inside the event store's connection; not worth it for a mock. **Superseded by SEC-2 (ADR-030): the event and the row are now one transaction (the `within` hook), because a mock that can lose a row is a poor model of the real sender it stands in for.**
- `GET /cases/{id}/notifications` returns the log for owners (their own case only, as for events), coordinators and supervisors; patients and lab do not see it.
- The contact validity flag can be set when the case is created (`POST /cases {contact_valid}`). Marking a number wrong after creation is not modelled.

**Consequences.**
- T-A25 and the notification half of T-A23 are checked against both the in-memory log and Postgres.
- D5 only needs `notify.send(...)` after `message_approved`; the gate itself (an approved draft exists) is D5's.

## ADR-019: Opaque actors, a users table for names, and a strict payload schema per event type

**Context.** The event log is append-only by trigger (ADR-004), so anything written to it stays. Until now the `actor` was `role:name` with whatever name was typed at login, `reopen.reason`, `owner`, `signed_by` and `message_drafted` text were free strings, and an unknown payload key was tolerated and stored (ADR-017). That puts personal data in a place that cannot honour an erasure request, and in log files (assumption L24, hazard HZ-13).

**Decision.**
- Actors are `role:user_id`. The `user_id` is an opaque slug: the first 12 hex digits of a uuid5 over `role|name` in a fixed namespace, computed at login. The same person logging in as the same role gets the same id, so history stays coherent; the id is not readable and is not the name. Services keep `system:scheduler` and `system:watchdog`.
- The name typed at dev-login goes to a `users` table (migration 004: `user_id`, `role`, `display_name`, `provider`), upserted at login and lazily for any valid token whose row is missing (a database reset must not blank the UI). It is the one place names live: erasing a person is one row, and the log holds nothing to erase. `GET /me` returns `{user_id, role, display_name, provider?}`. The case routes return `owner` as `{actor, display_name, role}` and an `actors` map covering every actor in the log; `read_model.owner` stays the actor string. An id with no row resolves to itself, so the UI always has something to show.
- Every event type has a strict pydantic model in `api/app/payloads.py` (`extra="forbid"`, strict types). String values must match the shape of an id or code (references, uuids, hashes, short codes), not prose. `reason` fields take only a taxonomy (the existing four handoff reasons, plus new ones for `reopen`, `callback_requested`, `watchdog_flagged`, `review_requested`). The one deliberate free-text field is `note`, at most 200 characters, on the events a person posts; the documentation tells staff not to put identifiers or clinical detail in it. A reviewer can see exactly what may enter the log by reading one file.
- `message_drafted` carries `draft_id, provider, fallback_used, prompt_hash, language`. The text stays in the `drafts` table (erasable) and the web reads it with `GET /cases/{id}/drafts`. That router lives on the AI cut's branch and is not in main yet; PLAN.md section 6 and `web/src/api/contract.ts` record the expectation only.
- The schema is checked in the API (422 before anything is written) and by the in-process emitters (sweep, consent ledger, notification mock) before they append; the sweep reports and skips a planned event that fails instead of stopping for every case. The pure state machine and the simulator are not bound by it: the machine keeps its semantic rules (taxonomy membership, who may use `timeout`), and the simulator's synthetic logs are not production data.
- `watchdog_flagged` moves to a new `watchdog` service role with its own token (`WATCHDOG_SERVICE_TOKEN`) in preparation for A11; the scheduler no longer holds it.

**Consequences.**
- Supersedes the clause in ADR-017 that unknown extra keys in a `consent_updated` payload are tolerated: they are now 422.
- A log written before A14 keeps its old actors (`role:name`) and loose payloads; they still replay, because the machine does not apply the schema. `make reset` and `make demo-seed` rebuild the dev database. The seeded cohort only contains `case_created` events.
- Names in tokens: the dev token still carries the name (it is a development credential, ADR-012); only the log and the case responses are name-free. The opaque id is stable per (role, name), so anyone who knows a name and the namespace can recompute it: this protects the log from casual disclosure, not from a determined guesser. Production identity replaces dev login with an OIDC subject, which would be hashed the same way.
- Web: the client must stop sending `owner`, `owner_role` and free-text `reason` values and read names from `owner` and `actors` (contract.ts BACKEND comments).

## ADR-020: Every open state has a timer, and the confirmatory SLA runs from referral acceptance

**Context.** Two gaps in the first SLA table (assumptions L12 and L13). `close` had no SLA, so a case that had been clinician-reviewed but not signed off could sit for ever without going overdue; the simulator papered over it with its own 3-working-day sign-off SLA that the engine did not have. And the 31-working-day colonoscopy target was counted from the `confirmatory_booked` state, while the DoH standard counts it from referral, so a case booked late could meet our SLA and still miss the national measure.

**Decision.**
- `slas_working_days.close: 3` in the pathway YAML. `clinician_reviewed` now has a timer, a breach, and a ladder like every other open state. 3 is the value the simulator already assumed (`orchestration.signoff_sla_working_days`); it is still a design choice for the clinician review (H1), and because the engine now reads it from the YAML the simulator's `setdefault` is a no-op.
- A per-SLA clock start, in a separate YAML map so `slas_working_days` stays a plain event-to-days map for the simulator and the web mirror: `sla_clock_start: {complete_confirmatory: handoff_accepted}`. The default is `state_entry` (the event that entered the state). `handoff_accepted` means the latest `handoff_accepted` on the case, whichever state it happened in, and falls back to state entry when no handoff was ever accepted (a case with no formal referral keeps the old behaviour). The loader refuses a value outside `{state_entry, handoff_accepted}` and a key with no SLA.
- Read model: `clock_started_at` is now the effective start of the current state's SLA clock (it equals the entry time for every SLA but the confirmatory one); `referral_accepted_at` is new. The sweep is unchanged: `due_at_for` already counts working days from `clock_started_at`, so `breach_due_at` (taken from the `mark_overdue` payload) follows.
- A `handoff_accepted` that arrives while the current state's SLA runs from acceptance restarts the clock and clears `overdue`, `escalation_level`, `escalation_accepted` and `breach_due_at`: a new obligation, the same rule as a state change (ADR-011). The earlier `mark_overdue` and `escalate` events stay in the log.
- The simulator keeps arming the confirmatory timer on entering the step, because it models no referral acceptance at booking: that is the "no handoff occurred" fallback, so its numbers do not change. Only the pathway hash recorded in `results.json` changes with the YAML.

**Consequences.**
- Any handoff counts as a referral, including a primary-care to primary-care transfer; the effect is to start the clock early, which is the conservative side. The next ticket that models the specialist referral explicitly (a role or reason on the handoff) can narrow it.
- T-A34 and T-A35 test the rule. The assumption table entries L12 (no `close` SLA) and L13 (clock start) are closed by this change; those documents live on the docs branch and are updated at merge.

## ADR-021: Closure evidence must resolve, and the signer is the closer

**Context.** The closure guard proved a human clinician signed something and that `evidence_ref` and `signed_by` were non-empty strings (assumption L28). A meaningless reference ("x") passed, and `signed_by` could name someone else. A coordinator cannot sign, but a clinician could sign for a colleague.

**Decision.**
- `close` takes `evidence_ref` of the form `DiagnosticReport/<id>` or `Procedure/<id>` (the payload schema, always). With `FHIR_VERIFY_EVIDENCE=true` (set in compose; false by default so unit tests and no-docker runs need no server) the API asks HAPI `GET <base>/<ref>` before it appends: 200 resolves; 404 or 410 is a 422 "does not resolve"; any other answer or no answer is a 503, because a closure that cannot be checked must not be assumed good. Nothing is written in either case.
- `signed_by` must be the caller's own actor string (`role:user_id`) or `Practitioner/<user_id>`, the Practitioner resource the FHIR projection (A12) creates for that user id. Any other value is 403 and nothing is written. `clinician_review.signed_by`, when given, follows the same rule. The check order is payload shape, signer, then the FHIR lookup, so a forged signature never causes a lookup.
- The check lives in the API, not in the pure state machine: the machine and the simulator keep the presence-only guard (the simulator's synthetic closes use readable ids and no FHIR server). The database transaction still enforces the transition guard.

**Consequences.**
- "Resolves" proves the reference exists, not that it is the right document for this patient; adequacy of evidence (is it a colonoscopy report for this patient?) is for the clinician review (H1). A later ticket could check `DiagnosticReport.subject` against the case's `patient_ref`.
- With verification on, a demo closure needs a real report in HAPI: the synthetic cohort's FIT `DiagnosticReport`s resolve; the demo script must create (or the seeder load) a colonoscopy `DiagnosticReport` or `Procedure` to close with.
- The web's close dialog must send a resource reference, not free text, and the caller's own `user_id` (from `GET /me`) as `Practitioner/<user_id>`.

## ADR-022: Closure metrics are pure functions over the log, with the simulator's definitions

**Context.** The dashboard (C8) and the evaluation (B6) must quote the same numbers. If the API computes P90 one way and the simulator another, a judge who compares them finds the gap. Cut B already wrote its definitions down (docs/results/metrics.md).

**Decision.**
- `api/app/metrics.py` holds pure functions: `build_record(events, pathway)` folds one case's log into a small `CaseRecord`, and `time_to_closure`, `open_by_age_bucket`, `breaches_by_provider`, `bottleneck_by_transition`, `lost_cases` and `closure_metrics` take records, `now` and a calendar. Nothing reads a store or a clock; `GET /metrics/closure` loads every case in one batch read and calls them. The simulator can call the same functions on its logs (its overlay events are named `overdue` and `escalated`; `build_record` takes the surfacing event names as parameters).
- Where the definitions overlap with metrics.md they are the same: clock zero is the case's `case_created`; time to closure runs to the first `close` and is conditional on closing, so it is reported with the number measured; percentiles interpolate linearly at q x (n - 1); open means not currently closed, so a reopened case is open again; a lost case has no `complete_confirmatory` and either a lost-contact flag or no pathway progress for 30 days; "surfaced" means the log holds an overdue, escalation, watchdog flag or lost-contact event, and a lost case that was never surfaced is a silent loss.
- Differences, stated: the API reports **both** calendar days and working days for time to closure (metrics.md reports calendar days only); "safe" closure is checked on the event (human actor, evidence reference, signature) and an unsafe one is counted in `unsafe_closures` and left out of the percentiles; the open-case ages are as of the sim clock now, in whole days (0-30, 31-60, 61-90, 90+ meaning more than 90); the bottleneck rows are the median calendar and working days in each state before each transition, over completed visits only; `breaches_by_provider` counts each `mark_overdue` against the provider the case was with at that moment (`unassigned` before any acceptance); `cases_flagged` is the number of open cases with an open watchdog flag.
- The route is coordinator and supervisor only. The abstention counts come from the AI cut's `drafts` table (`abstention_reason` set means the template was used instead of the model); when the table or the column does not exist the field is null, so the route works on a database without that migration. This differs from metrics.md's `automation_abstention_rate`, which is a human-written-message share that the simulator leaves null.

**Consequences.**
- The numbers cover the whole database, including closed cases of any age; there is no time window yet.
- Bottleneck medians use completed visits only: a state where cases are currently stuck understates its delay. The age buckets and the open-case count show the stuck ones.

**Amendment (SEC-2).** `GET /metrics/closure` used to drop a case whose stored log no longer replays, silently, so the closure rate could be computed over fewer cases than exist. The response now carries `replay_failures: {count, cases: [{case_id, error}]}` (the count is exact, the list is capped at 50) and the route logs the failure at error level; `cases_total` still counts the cases that were measured. The simulator's evaluation reports the confidence interval of a metric with a single replication as `null` (`ci_low`, `ci_high`), not a zero-width interval around the mean; the markdown report prints "n/a" for it.

## ADR-023: The watchdog scans in the API with its own token; heartbeats and alerts are tables, not case events

**Context.** The failure we fear most is silence: a case nobody touches, and a scheduler that stopped, so no overdue flag or escalation is ever produced. The first stub had the watchdog reading a heartbeat file from a shared volume and logging. That is invisible to the API and to the dashboard, and a file is a poor fit for a service that may run on another host. We also want the watchdog to be able to do very little: if it were compromised it should not be able to close a case.

**Decision.**
- **Its own token and role.** `WATCHDOG_SERVICE_TOKEN` maps to the service role `watchdog` and the actor `system:watchdog` (the same pattern as the scheduler, ADR-012/013). It may emit `watchdog_flagged` and nothing else: the event policy lists it for that one type, the scheduler no longer holds it, and the watchdog cannot read cases or create them. It can read `/heartbeats` and `/alerts`. Outside `APP_ENV=dev` the API refuses to start with the default token.
- **The scan runs in the API.** `POST /watchdog/scan` (watchdog token only) is the same shape as the sweep (ADR-013): the work happens next to the event store, on the sim clock, and the service process is the clock that calls it every 10 seconds. It flags every open case with no real event for `WATCHDOG_IDLE_DAYS` of sim time (the watchdog passes its setting; the API default is 7).
- **Idle episodes.** The idle clock is `last_activity_at`, the time of the latest event that is not a watchdog flag, so a flag does not restart it. The flag's event id is a uuid5 of (case, `last_activity_at`): one flag per episode however often the scan runs or races. Any other event clears the flag in the read model (`watchdog_flag` null), including the scheduler's own `mark_overdue` and `escalate`, and the next quiet spell is a new episode. A closed case is never flagged. "N days" means at least N, so exactly 7 days is flagged and 7 days less a minute is not.
- **Heartbeats are rows, not events.** `heartbeats` (migration 005) holds one mutable row per service, upserted by `POST /scheduler/heartbeat` on every scheduler loop, including after a failed sweep, with `sweep_ok`, `consecutive_failures` and its interval; the watchdog's own heartbeat is written by the scan. The age is computed by the database (`now() - beat_at`), so the API reads no wall clock; heartbeats are in wall time because the sim clock stops exactly when nothing advances it. There is no heartbeat event on a case because there is no case to put it on, and a sentinel "system" case would pollute the worklist and the metrics.
- **Alerts are episodes in `system_alerts`.** The scan decides from the scheduler's heartbeat: older than 60 seconds is `down`; none at all is `down` only once the watchdog has itself been up 60 seconds (warm-up); alive but `consecutive_failures x interval >= 60 s` is `failing` (alive and useless). `down` and `failing` open an alert (at most one open per kind, a partial unique index), a fresh healthy heartbeat clears it, and the row is kept with `since` and `cleared_at`. `GET /alerts` (coordinator, supervisor) lists them newest first. Nothing is left to open an alert if the watchdog itself dies, so `GET /alerts` also derives a `watchdog_down` entry from the watchdog's heartbeat age; if both die together the compose healthchecks and restart policy are the remaining defence, which this ticket does not add.
- **The chaos test.** `make test-chaos` runs `api/tests/test_chaos.py` against the running stack: it stops the scheduler container, waits for the alert, restarts it and waits for the clear. Measured: the alert appeared 68 s after the container stopped (60 s limit plus up to one 10 s watchdog interval) and cleared about 10 s after the restart, against a 90 s budget. It creates no cases.

**Consequences.**
- The watchdog depends on the API: if the API is unreachable it can only log and retry. That is acceptable because everything it watches is behind the API.
- ~~Idle detection counts the scheduler's own events as activity, so an overdue case that the sweep keeps escalating is not idle; once the ladder is exhausted and nobody acts, it becomes idle 7 days later and is flagged.~~ Withdrawn by the SEC-2 amendment below: that made exactly the case the watchdog exists for, an overdue case nobody is acting on, invisible to it.
- Wall-clock times in `since` / `cleared_at` / heartbeat ages are real time, deliberately different from every other timestamp in the system (simulation time); the contract says so.

**Amendment (SEC-2, independent code review).** Two findings, both about the watchdog being less accurate than this ADR claimed.
- **The idle clock counts people only.** The read model keeps `last_human_activity_at` (and the id of that event): the time of the latest event written by a person. The scheduler's `mark_overdue` and escalation rungs, the notifier's `message_sent`, a drafting model's `message_drafted`, the consent service's `review_requested` and the watchdog's own flags are automated actors (`state_machine.is_automated`) and are not anyone looking at the case: they neither restart the idle clock nor clear an open flag. `last_activity_at` (any event but a flag) stays in the read model as it was. Idle detection (`plan_idle_flag`) uses the human clock, the flag's id is a uuid5 of (case, the id of the event the quiet stretch runs from), and the timeline's `cleared_at` follows the same rule. A case the sweep keeps escalating but nobody opens is flagged idle after `WATCHDOG_IDLE_DAYS` of sim time, not never. Limit: a draft is requested by a coordinator but recorded as the model's event, so requesting one is not counted as activity; approving or rejecting it is.
- **A long sweep is not a dead scheduler.** The scheduler used to post its heartbeat once per loop, after the sweep. A sweep over a large cohort that ran past 60 seconds therefore opened `scheduler_down` while the scheduler was working, and a false alarm teaches people to ignore the true one. The scheduler now posts a heartbeat first (before the sweep), every `SCHEDULER_HEARTBEAT_SECONDS` (15) from a thread while the sweep runs, and a closing one with the result; the body gains `sweeping: true` for the first two. The decision rule in `ops.scheduler_status` is unchanged (older than 60 s is down; alive but failing for 60 s is failing). The scheduler also drains the send outbox at the start of each loop (ADR-030).

## ADR-024: The FHIR projection runs in the API after the append, best effort, with a retry queue

**Context.** The event log is the source of truth, but a regulator, Malaffi or another system reads FHIR (ADR-008). HAPI is already in the stack. The projection must never be able to stop a clinical event from being recorded, must not duplicate on retries, and must not put free text or names where they cannot be erased.

**Decision.**
- **When.** `ProjectingStore` wraps the event store (`FHIR_PROJECTION=true`, set in compose). After a successful `create_case` or `append` it projects that event, synchronously, in the same process. Because it wraps the store, the writers that do not go through a route (the sweep, the consent ledger, the notification mock, the watchdog) are projected too. Reads and everything else are delegated untouched.
- **Never blocks the log.** The projection runs after the append has committed. Any failure (HAPI down, HAPI refuses, a bug in the mapping) is caught, logged, and the event id is written to `fhir_projection_queue` (migration 006: ids and the last error text, no clinical data); the request still succeeds. After a connection failure the projector stops trying for 15 seconds and queues directly, so a HAPI outage costs one timeout, not one per event. A background loop (every 20 s) drains the queue, oldest first, and stops early if HAPI is still down.
- **Idempotent by event id.** Every resource id is derived from the event (or the case) so a replay or retry PUTs the same resources: `Task/task-<case>`, `Consent/consent-<case>`, `ServiceRequest/sr-<request event>`, `Appointment/appt-<event>`, `Communication/comm-<event>`, `Provenance/prov-<event>`, `Practitioner/<user_id>`, `Device/system-<service>`. Resources are written in one transaction Bundle per event. The case-level ones (Task, Consent, and a ServiceRequest with its answer) are rebuilt from the *current* state of the log, so a queued old event never regresses a resource to an older state, and an unchanged PUT makes no new version in HAPI (tested).
- **Mapping.** Task status mirrors the state (`requested, received, accepted, in-progress, completed`; side states `on-hold`/`in-progress`) and `businessStatus` carries the exact state; `owner` is the owner's Practitioner, `focus` the screening DiagnosticReport, `for` the Patient, `restriction.period.end` the SLA due date, extensions the overdue flag, escalation level and consent freeze. ServiceRequest is `draft` while the receiving provider has not answered, `active` with the accepting Practitioner as performer once accepted, `revoked` with the taxonomy reason on the note when rejected or bounced (FHIR has no "awaiting acceptance" status; `draft` is the closest honest one). Appointment is a stub with status `proposed`: FHIR requires start and end for `booked`, and the engine models no slot time, so inventing one would be false. Communication records the channel, purpose, time and the notification id, not the text (that stays in the notifications log). Consent is one resource per case rebuilt from the consent ledger (`inactive` and `deny` after a withdrawal) with a policy rule, since FHIR requires a policy or policy rule; its history is HAPI's version history. Provenance, for every event: `agent.who` is the actor (Practitioner for staff, the Patient for the patient's own actions, Device for the scheduler, watchdog, notifier and intake), `entity.what` is an identifier reference to the event id, `target` is the resources the event touched.
- **References must resolve (HAPI enforces it).** Before writing, the projector probes whether the case's `Patient` and screening `DiagnosticReport` exist; if not, the reference is written as identifier-only. A case for a patient who is not in the store therefore still projects and the Task is still readable.
- **People.** Practitioner resources hold the display name (from the users table, ADR-019): the FHIR store is where personal data lives and where an erasure request is honoured, not the log. `Practitioner/<user_id>` is also the mapping A15 accepts for `signed_by`.
- **Identification.** Every resource carries `meta.tag` (`closure-engine` in production; the integration tests use their own tag so test resources can be found and removed).

**Consequences.**
- The projection is eventually consistent: between an append and its projection (or while HAPI is down) the FHIR copy lags the log; `GET /cases/{id}/fhir` reports `events_waiting`.
- The process is single-writer per event. Two API replicas would both project and both drain; idempotent ids make that safe but wasteful.
- Events that predate the projection are not back-filled. A rebuild is "project every event of every case", which the idempotent ids allow; no route does it yet.
- Hazard: a person who edits the HAPI copy changes the FHIR view but not the case; the log wins, and the next event rewrites the Task.

## ADR-025: Erasure versus the append-only log: the log holds opaque ids only

**Context.** The event log is append-only by design: database triggers reject `UPDATE`, `DELETE` and `TRUNCATE` on `events` (ADR-004), because an audit trail that can be edited is not credible. A data subject may ask for their personal data to be erased (a right described in secondary readings of the UAE PDPL, Federal Decree-Law 45 of 2021; whether the PDPL governs health data at all, and the minimum retention period for health records under Federal Law 2 of 2019, are both to verify, see `docs/governance/regulatory-mapping.md` items 1 and 2). Both cannot be satisfied if the log holds personal data. The regulatory mapping already named the option: keep direct identifiers in a separate erasable store and put only a pseudonymous key in events. This ADR makes that the rule.

**Decision.**
- The event log (`events`, `cases`) and the notifications store carry only opaque identifiers: case ids, event ids, FHIR resource references (for example `Patient/<system-assigned id>`, `DiagnosticReport/<id>`), draft ids and content hashes. They never carry names, phone numbers, addresses, national identifiers, MRNs, or free text about the patient. A FHIR reference in the log must be a system-assigned id, never a national identifier or MRN.
- Personal data lives in two erasable places only: the FHIR store (the `Patient` resource and the resources that hang off it) and a contact table (channels, numbers, preferred language, and the rendered text of drafted and sent messages, keyed by case id). Message text is stored there, not in the log; the log carries the draft id and a hash of the text.
- Erasure of a data subject is: delete the `Patient` resource and its dependent resources from the FHIR store (including expunge, because HAPI soft-deletes by default, to verify), delete the contact and message-text rows, and delete the id mapping from case to patient. The events remain. What remains identifies no one: case id, event types, timestamps, role-level actors, SLA flags.
- Staff are also data subjects. The `actor` of an event should be `role:<opaque staff id>`, with names held in a staff directory that can be edited, not `role:<name>`.
- Erasure is a human-run, logged procedure. It is recorded in an erasure register (request date, case ids, who performed it, what was deleted) that itself holds only opaque ids. Whether a human-only annotation event also marks the case as erased is left to the implementing ticket; it is not in the current vocabulary, so it is not in the decision matrix.
- Retention comes first: where a retention duty applies to the clinical record, erasure may be refused or restricted for that period. The legal position is to verify before a pilot.

**Consequences.**
- Append-only (ADR-004) and erasure can both hold, because the immutable part contains nothing erasable.
- "Cannot identify anyone" is a design target, not a proven property. A small pilot with few cases, exact timestamps and rare event sequences could let someone who knew when a patient was followed up single out a case. Whether that counts as anonymised is a legal question, to verify.
- Backups and the HAPI database (shared with the case store, ADR-006) must be covered by the procedure; a restore must not resurrect erased data. Not designed yet.
- The log must be checked for violations, not only designed against them. A scan for marker values in stored events and payloads extends the no-PHI-in-logs test (T-F10). No test enforces this rule today.

**What the current code does not yet enforce** (also in the limitations table, `docs/assumptions-limitations.md`, rows L23 and L24):
- `POST /cases/{id}/events` accepts any JSON object as `payload`. There is no per-event-type schema or allow-list, so `reason`, `evidence_ref`, `signed_by`, `owner` and any other key can hold names or free text, and they are stored forever.
- The `actor` is `role:name`, and the name is whatever string was given at login (letters, digits, space, `.`, `_`, `@`, `-`). A patient or clinician who logs in with their real name has it written into every event they cause.
- `signed_by` and `owner` carry a person's identifier chosen by the client.
- Draft text is not stored yet (D4 is not built). When it is, output validation requires the care owner's name inside the text (`missing_owner_name`), so draft text contains a staff member's name and, in an outreach message, the fact that a screening test found blood. It must go to the contact table, not into the `message_drafted` payload.
- The genesis event holds `patient_ref` and `result_ref` in its payload. They are references, which is allowed, but the id mapping is the log itself, so it cannot be deleted separately; erasure today would leave the reference pointing at a deleted `Patient`. This is acceptable only while the reference is an opaque system-assigned id.
- No contact table, notifications table, erasure procedure or erasure register exists. No ticket owns them yet.

**Status.** Accepted as the design rule. Implementation is not scheduled; a ticket for payload schemas, opaque actors and the erasure procedure should be added before any pilot.

## ADR-026: Hosting order of preference under ADHICS CM 4.2

**Context.** ADHICS v0.9 control CM 4.2 (category Basic) says a healthcare entity shall not use cloud services or infrastructure to store, process or share information that contains health information, shall ensure health information is not transmitted outside the UAE, and shall not share identified or de-identified health information with third parties unless authorised by the Abu Dhabi health sector regulator (`docs/governance/regulatory-mapping.md`, section 3). A US trade summary adds that DoH can grant case-by-case exceptions for cloud data-centre services. The current ADHICS version (V2, 2024) was not retrieved, so whether the rule is kept, relaxed or reworded is to verify. Federal Law 2 of 2019 adds a localisation rule for health data, and the DoH Responsible AI Standard asks that compute, storage, disaster recovery and remote access for development and support stay in the UAE (section 6 of the mapping). Azure UAE North and Core42 are documented as in-country options, but DoH acceptance of either for health information is not established.

**Decision.** For any deployment that holds real patient data, host in this order of preference, and move to the next only when the earlier option is unavailable:
1. **A provider-approved environment.** The participating provider's own data centre or private cloud, already approved for health information under the provider's own ADHICS compliance. This is the first choice because it adds no new cloud authorisation.
2. **A DoH-authorised cloud.** A UAE-located cloud that DoH has authorised in writing for health information, using the exception route that CM 4.2 describes. Azure UAE North and Core42 Sovereign Public Cloud belong here, and only after that written authorisation exists. Disaster recovery, backups and remote administration must also be in the UAE.
3. **Nothing else.** A cloud without DoH authorisation, any region outside the UAE, or a vendor-run tenancy that has not been approved by the provider, is not an option for real data. The synthetic prototype is exempt, because it holds no real data (`docs/data-provenance.md`); it can run on a laptop or any host.

The model provider for drafting is bound by the same order. If no in-country, approved model host exists, the template fallback is used (ADR-007).

**Consequences.**
- The stack stays portable: containers, Postgres, and no cloud-managed service in the engine, so the same compose-derived deployment runs under option 1 or 2 (`docs/governance/regulatory-mapping.md`, section 6).
- Option 1 shifts operations to the provider and may lengthen onboarding, since the provider's team must run the stack. The pilot plan therefore keeps hosting approval as a gate (G0) and lists "hosting not approved for health information" as a risk (`docs/pilot-plan.md`).
- Nothing in this ADR claims that any provider or cloud is acceptable. It records the order in which we would ask.
- If ADHICS V2 or a DoH decision changes the rule, this ADR is superseded by a new one.
- Malaffi connectivity is independent of this order and stays optional in the pilot (`docs/governance/malaffi-adapter-plan.md`).

## ADR-027: A backdated event is flagged; a user's is refused, a service's is accepted

**Context.** T-F4 (clock skew) asked that events with times before the last event or far in the future be "refused or flagged". An event `at` in the future is already refused: the events route returns 422 when `at` is later than the simulation clock, and the scheduler takes its time from the API, not from the caller (F3, `test_chaos_faults.py`). An event dated before the previous one is the other half. The sim clock can be reset for the demo (`POST /clock/reset`), a client can be slow to deliver an event that happened earlier, and the pathway already contains legitimate cases (a result recorded after the colonoscopy it describes). The log is ordered by `seq`, assigned at insertion, never by `at`, and a replay is a pure function of that order, so an out-of-order `at` cannot corrupt the state. Refusing it would drop a real clinical fact.

**Decision.**
- Accept an event whose `at` is earlier than the previous event's `at` (the event just before it in `seq` order, whatever its type), but flag it. Equal times are not backdated.
- The flag is derived, not stored (the log is append-only and the event is not edited): the case timeline gets a derived item `kind: "backdated"` with `event_id`, `event_type`, `at`, `previous_event_id`, `previous_at` and `behind_seconds`, and the read model carries `backdated_events`, the count of such events (`CaseModel.backdated_events`, computed in `state_machine._finish`).
- An `at` later than the simulation clock stays refused (422). No other check changes.
- The flag changes nothing else: not the state, the SLA clocks (which read `at` as before), the escalation ladder or the watchdog. Nobody is blamed by it; it is for the reviewer who reads the timeline or audits the log.

**Consequences.**
- Replays are unchanged in every field except the new counter, and are still deterministic (`test_chaos_faults.py::test_t_f4_a_service_actors_late_event_is_accepted_flagged_and_replays_deterministically`; `test_state_machine.py` ADR-027 tests; `test_read_routes.py::test_t_f4_a_service_actors_late_event_is_accepted_flagged_in_the_timeline_and_counted_in_the_read_model`).
- The comparison is with the previous event only: a sequence at 10, 5, 7 flags the 5 and not the 7. This keeps the timeline item and the count identical by construction.
- The simulator's cases use the same state machine and may carry a nonzero counter; no result reads it.
- A dashboard or audit report can list cases with `backdated_events > 0`. None is built.

**Amendment (SEC-2, independent code review).** "Accepted and flagged" was right for the scheduler and wrong for people. A user token could post `close` (or any event) dated before the case's latest event, and the flag was the only trace: the SLA clocks, which read `at`, were moved by a client-chosen time, and a signed closure could be placed earlier in the case's history than the review it depends on. The review also found that the deterministic ids the sweep and the watchdog derived from timestamps could collide (below).

- **User tokens (the six user roles): an `at` earlier than the case's latest event (`model.last_event_at`) is refused, 422 `backdated`.** The comparison is inclusive (an `at` equal to the latest event's is accepted), is made on the model replayed **inside** the append's transaction under the case's row lock (`guard` argument of `append` / `append_many`, called before the state machine sees the event), so two requests cannot both pass on a stale read, and it is not applied to a repeated `event_id` (an idempotent retry). Nothing is written. A future `at` stays refused as before.
- **Service tokens (scheduler, watchdog) and the in-process emitters (`system:notifier`, `system:consent`) keep ADR-027's behaviour.** They legitimately post late: a sweep reads `now` once and appends for the length of the sweep, while people keep acting on the same case at a later sim time. Their late event is accepted in `seq` order, counted in `backdated_events` and shown as a `backdated` timeline item, so the flag remains reachable and meaningful. It no longer applies to anything a person does.
- **After `POST /clock/reset` a user's event is refused until the sim clock passes the case's latest event again.** That is the correct reading of the rule (the log runs forward). The demo reset (`make demo-reset`) restores the database snapshot and resets the clock together, so the demo is unaffected; resetting the clock alone on a database that holds later events is what now fails, loudly.
- **Deterministic ids no longer contain a timestamp.** `mark_overdue` and escalation rung ids derive from the `event_id` of the event that started the SLA clock (`CaseModel.clock_started_event_id`), the bounce id from the `event_id` of the handoff request (`pending_handoff.requested_event_id`), the watchdog's idle-flag id from the event the quiet stretch runs from. Two clocks that start at the same instant (a state entered, left and entered again; a handoff requested, bounced and requested again at the same time) used to share an id, and the second breach or bounce was swallowed as a repeat of the first: the case then waited for an alert that could not come. They are distinct obligations now and get distinct ids; one clock still gets one id, so sweeps stay idempotent (`test_event_time_and_ids.py`, including a hypothesis test that every re-entry gets a fresh `mark_overdue` id).

## ADR-028: Milestones: the national timelines are clocks of their own, and the pre-referral SLAs fit inside the referral one

**Context.** Two published timelines apply to a positive FIT: referral to secondary care within 15 working days of releasing the result (DoH IFHAS standard V10, July 2025, via `docs/evidence.md` section 8), and colonoscopy within 31 working days of referral (UAE National Guideline for Colorectal Cancer Screening and Diagnosis, 3rd ed. 2022, **Appendix 2**). ADR-020 modelled only the second, as a per-state SLA (`slas_working_days.complete_confirmatory` plus `sla_clock_start`), and the YAML comment called it an IFHAS KPI, which it is not: the 31 is the guideline's KPI table, and IFHAS has the 15. The per-state SLAs before the referral (2, 2, 5, 7 working days, then 14 to book) added up to 16 working days before a referral could even be requested, so a case that met every one of them could miss the 15-working-day referral timeline. This entry supersedes the confirmatory-SLA part of ADR-020 (the `close` SLA and the clock-start mechanism of A13 stand).

**Decision.**
- A `milestones:` section in the pathway YAML: `{from_event, until_event, working_days, source}` per milestone. `referral_requested`: `case_created` to `handoff_requested`, 15 working days, source "DoH IFHAS standard July 2025 via docs/evidence.md section 8". `confirmatory_completed`: `handoff_accepted` to `complete_confirmatory`, 31 working days, source "National Guideline Appendix 2 via evidence.md". `from_event` is `case_created` or a pathway event; the loader refuses an unknown event, a non-positive allowance, an unknown key and a missing source. `slas_working_days` keeps the per-state SLAs only: `complete_confirmatory` leaves it, and `sla_clock_start` is no longer used by the shipped YAML (the loader still accepts it).
- Per-state SLAs tightened so the four steps before the referral sum to 11 working days, inside the 15: acknowledge 2, accept_ownership 1 (was 2), contact_patient 3 (5), patient_acknowledge 5 (7), book_confirmatory 5 (14); clinician_review 5, close 3 and reassign 2 unchanged. These are design values (assumed, not sourced), still for clinician review (H1); the point of the change is the arithmetic, not the individual numbers.
- Read model: `milestones: {name: {started_at, met_at, overdue, breach_due_at, escalation_level, escalation_accepted, void}}`, replayed like everything else. A milestone starts at its `from_event` (the latest occurrence until it is met, as A13), or, if that never happens, when the case enters the state that awaits its `until_event` (so a case with no formal referral keeps a colonoscopy clock, ADR-020); the `until_event` meets it and clears its breach and ladder; a met milestone never changes again; closing a case with a milestone unmet voids it. `overdue` on the milestone is its own flag: the state-level `overdue`, `escalation_level` and ladder are untouched. The worklist `overdue` is true if the state or any milestone is breached; `due_at` is the earliest running deadline; `GET /cases/{id}` adds a top-level `milestones` with the due dates; the timeline gets derived `milestone_started`, `milestone_breached` and `milestone_met` items.
- The sweep evaluates milestones after the state SLA. A breach is `mark_overdue {milestone, due_at, sla_working_days}` from `system:scheduler`; the payload schema takes exactly one of `state` and `milestone` (`escalate` and `escalation_accepted` likewise name a milestone when the rung is on a milestone's ladder). The ladder runs for it exactly as for a state breach (ADR-014), with its own position. Idempotency is `uuid5(case, "milestone:<name>", due_at, kind)`: the prefix keeps a milestone from colliding with a state of the same name (`confirmatory_completed` is both). Nothing is planned while consent is withdrawn (the clock keeps running and the breach follows when the case resumes). `escalation_accepted` without a milestone accepts the state's ladder if it has a rung, else the one milestone ladder that has one.
- The simulator reads the milestones from the YAML. A `case_created` milestone is a timer armed at the start, met by its `until_event`, whose breach opens the ladder for whatever step the case is in; a `handoff_accepted` milestone is armed on entering the step that awaits its `until_event`, which for the engine is the same instant as the referral acceptance, so the colonoscopy clock behaves as the per-state SLA did. The baseline arm has no timers and ignores both.

**Consequences.**
- The 15 and the 31 now have the right sources, in the YAML, the clinician pack, the pilot plan (K4, K5) and assumption L13. The evidence register (`evidence.md` section 8) still carries its older paragraph about a 45-working-day SLA; it belongs to the register's owner.
- Meeting the referral milestone means a referral was **requested**, not accepted, and any handoff counts (a transfer between primary care owners as well). This starts and stops the clocks on the conservative side for the colonoscopy and the lenient side for the referral; narrowing it needs a role or reason on the handoff (H1).
- Both clocks are per case. The standards are programme-level shares (above 90% acceptable); no metric yet reports the share within either limit.
- Two ladders can run at once on one case (a state's and a milestone's). In the API that is two sets of notifications to the same owner, supervisor and coordinator; in the simulator the ladder also re-contacts a patient who is awaiting a reply, so a second ladder on the same step doubles the reminders to that patient. Measured in a scratch ablation, not committed (seeds 20261017 to 20261020, 2,000 cases each, upper range): the tighter SLAs alone cost about 0.3 points of 180-day completion and raise escalations from 99 to 150 per 100 cases; the referral milestone alone costs about 1.5 points and adds about 60 escalations per 100; together completion at 180 days goes from 83.0% to 79.3% and escalations from 99 to 212 per 100 cases (literature-anchored: 66.2% to 64.9%). Suppressing a milestone rung while the state's ladder is already at the same level would remove most of that and is not done: it is a product choice, not a modelling one.
- Two ladders running at once meant the same role could be told twice on one working day. That was not suppressed here; ADR-031 (A19) coalesces them per role per working day.
- `programme_reach` in `simulator/params.conservative.yaml` was fitted to 0.50 so the literature-anchored 180-day ratio equals the navigation risk ratio 1.27. With the milestones (this entry) it was 1.25 (inside the interval, 1.10 to 1.46) and was left unfitted. **Refit on 2026-10-18, after A18 and A19 (ADR-031):** binary search on two-decimal values, target 1.27 (rounds to 1.27), ratio read unrounded from `results.json` (20 replications of 2,000 cases, seed 20261017, 360 days): 0.50 gives 1.2480, 0.55 gives 1.2721, 0.53 gives 1.2628, 0.54 gives 1.2677, 0.56 gives 1.2759. **0.55 is the closest** (66.3% against 52.1%; 0.54 is 0.0023 off, 0.55 is 0.0021 off). Its sweep range for the sensitivity analysis follows the default rule from the new value (0.275 to 0.825). The procedure is in `simulator/README.md`.
- The loss-to-follow-up risk score was retrained on the new simulator data (`make risk-report`): its inputs include overdue and escalation counts, which changed.

## ADR-029: Production fails closed, and the API runs with least privilege

**Context.** An independent review of the hackathon build found that every safety guarantee rested on development conveniences being switched off by good behaviour: a passwordless login that mints a supervisor token, a published HMAC secret that signs any user, clock routes that rewind a clinical safety clock, compose ports open to the whole network, an API that connected to Postgres as a superuser (so a bug or injection could `ALTER TABLE events` or drop the append-only triggers), HAPI sharing the application's database, an image that shipped its tests and ran as root, a migration runner that would silently accept an edited migration, and an output validator and reference parser with bypasses (invisible characters, look-alike letters, `050/123/4567`, an owner named "Om" hiding `evil.com`, `Patient/..` in a URL, a retry queue starved by 100 poison rows).

**Decision.**
- **Fail closed outside `APP_ENV=dev`** (compared exactly: `Dev` is not dev). The API refuses to start if `DEV_LOGIN_ENABLED` is true; if `DEV_AUTH_SECRET`, `SCHEDULER_SERVICE_TOKEN` or `WATCHDOG_SERVICE_TOKEN` is the built-in default, empty or under 32 bytes; or if the two service tokens are equal. `verify_token` rejects a user token signed with the built-in secret whatever the configuration (the secret is public), `issue_token` will not mint one, an empty service token never matches, and `/auth/dev-login` is 404 outside dev. All problems are reported at once.
- **The demo clock exists only in dev.** `app.main` registers the `/clock/*` router only when `APP_ENV=dev`; elsewhere those paths are 404. `POST /clock/reset` answers 409 when any event is dated after the clock's start (`has_events_after` on both stores): the clock may not be rewound past recorded events. Undoing a demo is restoring the snapshot.
- **A least-privilege database role.** Migration `009_app_role.sql` creates `closure_app`: not a superuser, owns nothing, no DDL, INSERT and SELECT only on the append-only tables (`events`, `notifications`, `prompts`), SELECT/INSERT/UPDATE where the application changes rows, and its own bookkeeping read-only. Tables stay owned by the superuser, so `ALTER TABLE`, `DISABLE TRIGGER`, `TRUNCATE` and `session_replication_role` are all denied to it, as a second wall behind the append-only triggers (ADR-004). The API (compose `DATABASE_URL`) connects as it. The schema is applied by a one-shot `migrate` service (`python -m app.migrate`) that holds the owner's credentials and sets the role's password from `APP_DB_PASSWORD`; the API still runs the migration check at start-up (read-only when nothing is pending, a clear error pointing at `app.migrate` when something is). The scheduler and watchdog have no database connection at all (they speak HTTP to the API), so they needed no role. A new table in a later migration must grant to `closure_app` itself (010 does).
- **Compose.** Every published port is `127.0.0.1:` (`tools/check/compose_lint.py`, in `make test-security`, fails on any other, including the offline overlay's `edge`). HAPI keeps the superuser but moves to its own database `hapi`, created by `docker/postgres-init/10-create-databases.sh` (fresh volume, and the `db-init` one-shot for an old one); `CONNECT` on it is revoked from everyone but the owner. `tools/demo/snapshot.sh` saves and restores both databases. The API image is a `runtime` stage (production dependencies, no tests, uid 10001) with a separate `test` stage behind the `api-test` service, which `make test` uses without a venv.
- **FHIR references.** `patient_ref` is `^Patient/[A-Za-z0-9-]{1,64}$` and `result_ref` `^DiagnosticReport/[A-Za-z0-9-]{1,64}$`; no reference may contain a dots-only or empty path segment (evidence, signer and appointment references included); the HTTP client refuses anything that is not `Type/id` before building a URL and quotes each part, and the projection writes an unsafe legacy reference as an identifier without looking it up. `complete_confirmatory.result_ref` is a `Procedure/` or `DiagnosticReport/` reference of the same shape, because the recorder returns the Procedure there (E8). The projection retry queue has `next_attempt_at` with exponential backoff (first retry at the next pass, then 30 s doubling to 1 h), drains in that order, and after 12 attempts moves the event to `fhir_projection_dead_letter` (migration 010); `GET /alerts` shows a derived `fhir_projection_dead_letter` alert with the count. The background loop respects the schedule; a drain you call yourself retries everything queued.
- **The output validator** rejects any Cf/Cc/Co character (also Cs, Cn, Zl, Zp), with the line feed as the single exception because the vetted templates use it; requires every letter to be from the language's script (no ratio); matches the English forbidden phrases on a confusables skeleton (a small Latin/Cyrillic/Greek homoglyph map, hidden characters dropped); counts `/` and `,` as digit separators and every script's decimal digits as digits; and masks the request's own values only where they stand alone as a token.
- **The migration runner** creates `schema_migrations` inside the advisory lock, stores each file's sha256 and stops with `MigrationChecksumError` (file, recorded and current hash) if an applied file changed, before applying anything else. A table from before checksums is filled in once from the current files.
- **`reassign.owner`** must be a staff-role actor (`lab`, `primary_care_owner`, `specialist_owner`, `coordinator`, `supervisor`), never a patient or an automated actor.

**Consequences.**
- A non-dev deployment has no way to log a person in until the OIDC verifier exists; that is deliberate (L19). A deployment that needs the demo behaviours sets `APP_ENV=dev`.
- **Token expiry is not implemented and stays a pilot-hardening item.** The API reads no wall clock by design (T-A17), so an `exp` based on the simulation clock would be meaningless and one based on the wall clock would break that rule. The OIDC verifier brings its own `exp`, revocation and key rotation.
- An existing volume keeps HAPI's old `hfj_*` tables in the application database, unused; the FHIR store starts empty in `hapi` and `make demo-seed` fills it again. `make demo-snapshot` must be taken again.
- A database fault on the Postgres server still takes the case store and HAPI down together; only the databases are separate (L20).
- An event dead-lettered after a long HAPI outage is no longer retried; `InMemoryProjectionQueue.revive_dead` and `PostgresProjectionQueue.revive_dead` put the rows back, and an admin route for it is not built.
- `LLM_CACHE_MODE=record` writes into the image's cache directory, which the non-root user cannot; record from a checkout, as the docs already say.
- The scheduler and watchdog images still run as root (the heartbeat volume is root-owned); the API is the exposed one.
- The closure of the review's findings does not change any state-machine rule, SLA or event vocabulary.

## ADR-030: The approval gate lives in the state machine, and approval writes an outbox row

**Context.** The independent review found that "a message goes out only after a human approved it" (ADR-018, D5) was a property of the call graph, not of the engine: `message_sent` was accepted from `system:notifier` whatever had been approved. The test that scans the source for callers of `notify.send` protects against a careless edit, not against a bug in the one allowed caller, a second caller added later, or a replay of the notifier. The consent check had the same shape: it ran in `notify.send` on a read model, and the machine looked at consent only when the case was frozen, so a channel switched off between the approval and the send was caught only if `send` happened to read the new model. And approval and send were two separate steps with nothing between them: a crash after the approval committed left an approved draft that nothing would ever send, silently. The notification row and its `message_sent` event were two writes that a failure could separate (the draft row and `message_drafted` had the same flaw).

**Decision.**
- **The gate is a rule of the machine.** `CaseModel.approved_unsent` is the set of draft ids a human approved (`message_approved`) whose `message_sent` has not been written. `_precheck` accepts a `message_sent` only if its `draft_id` is in that set, and only if the patient's consent for its `channel` is true in the model it is applied to (`channel_consent`, the same function `consent.channel_allowed` and the notifier use). Applying it removes the draft from the set, so a draft is sent once; approving a draft that is already in the set is refused. Nothing that reaches the store, from any caller, can write a send for a draft nobody approved, send it twice, or send it past an opt-out. The check is made under the case's row lock on the replayed model: a withdrawal or an opt-out that commits between the approval and the send is seen.
- **Approval writes an outbox row in the same transaction** (`outbox`, migration `011_outbox.sql`): the draft's approval, the `message_approved` event and the row commit together or not at all. The row holds ids and the approval time, no text (the drain reads the text from `drafts`, so erasing a draft erases the message).
- **A drain sends from the outbox, idempotently.** `notify.drain_outbox` is called at the end of `POST /drafts/{id}/approve` and by the scheduler loop (`POST /scheduler/outbox/drain`, scheduler token only). For each pending row it calls `notify.send` with a notification id that is a function of the draft, so the `message_sent` event id is too. The event, the notification row and the outbox mark are written in **one transaction** (the store's `within` hook); a drain that dies at any point leaves the row pending and the next one finishes it; two at once send once (the case lock plus the deterministic event id). A row the machine or the consent/contact checks refuse is marked `blocked` with its reason and never retried: consent withdrawn or the channel off (`blocked_consent`), contact details flagged invalid (`blocked_contact`), the case closed or frozen in the instant between (`case_state`). Nothing is sent in any of them. A failure that may pass (the database) is counted and leaves the row pending. The approve response reports `sent`, `blocked_reason` (`consent`, `contact`, `case_state`) or `pending`, in which case the approval stands and the scheduler will send it.
- **The notification row and `message_sent` are one transaction** (above). A blocked notification has no event, so its row is written alone. **The draft row and `message_drafted` are one transaction too:** `POST /cases/{id}/drafts` runs the draft insert (and its prompt) in the event store's `within` hook, so a failure between them leaves neither; before, the event was appended first and a failed insert left a `message_drafted` for a draft that did not exist.

**Consequences.**
- The approval is no longer something the notifier takes on trust: the invariant "no `message_sent` without a prior approval of that draft on that case, none after an opt-out of its channel, none twice" holds for every replay of every log the machine accepted (`test_outbox.py`; `test_approval_gate.py` property test).
- A reviewer reading the log sees the same events as before (`message_drafted`, `message_approved`, `message_sent`); the read model gains `approved_unsent_drafts`. The approval of a draft can now be complete with its message still `pending` for up to one scheduler interval (10 s by default) if the API process dies between the commit and the drain.
- Cost: one more table, one more route, one more scheduler call per loop. A drain scans only `pending` rows (partial index).
- Not changed: the notification mock is still a log (ADR-018), nothing leaves the process, and a rejected draft is still final.
- Known limit: the in-memory store (unit tests, no-database runs) has one lock but no rollback, so the "same transaction" guarantees are proven against Postgres only; the in-memory store keeps the same ordering and the same idempotency.

## ADR-031: Concurrent ladders coalesce per role per working day

**Context.** Since A18 a case can have the state's SLA ladder and one or more milestone ladders running at once (ADR-028), and each rung is an `escalate` event to the rung's target role (ADR-014). The same role could therefore be escalated twice on one case on one working day: the owner reminded for the late step and again for the late referral, the supervisor and the coordinator likewise. In the simulator the second ladder also re-contacted a patient who was already waiting for a reply. ADR-028 measured what the second ladder added (about 212 escalations per 100 cases in the upper-range scenario) and left suppressing it as a product choice; this decision takes the narrow part of it that is not a choice: the same role is not told twice on one working day.

**Decision.** One escalation per role per case per working day, while an earlier one to that role is unaccepted.
- **What a ladder remembers.** Each ladder (the state's in `CaseModel`, each milestone's in `MilestoneState`) records `escalation_event_id` (the `escalate` event its current rung is recorded on) and `escalation_at` (that event's `at`). They reset wherever `escalation_level` resets: a new state, a milestone restart, met or void, and a restart of the state clock by a referral acceptance.
- **Same sweep (`also_for`).** `plan_case` plans the breaches first, then the rungs: the state's ladder first, then the milestones in pathway order. A rung whose `target` equals that of an earlier rung of the plan from another ladder is not emitted. It is added to that earlier event's payload as `also_for: [{state|milestone, rung, level, due_at, rung_due_at}]`, one entry per attached ladder. The primary keeps its own id, derived from its own clock, so the id of a ladder's rung never depends on another ladder. The escalations are ordered so each ladder's levels stay increasing; the plan is dry-run through the state machine, and if the machine would refuse it the plain plan (the pre-A19 behaviour) is returned instead.
- **Later sweep, same working day (`attached_to`).** When a ladder's rung to a role is due and another ladder of the case has an unaccepted current rung to that role whose `escalation_at` falls on the same working day as `now` (`calendar.local_date`), the sweep emits the rung with its normal payload and its own deterministic id plus `attached_to: <event id of that escalation>`. It notifies nobody and is not a new escalation: `app.metrics.build_record` and the risk score's `prior_escalations` skip it, and the timeline item carries `attached_to`. The ladder's position moves as usual and it shares the other's `escalation_event_id`.
- **State machine.** `_escalate` validates `also_for` (each named ladder must be another ladder of the case, overdue, unaccepted, entry level equal to its current level plus one, its rung aimed at the primary's target, the state entry naming the case's current state) and applies it (each ladder's level, `escalation_event_id` and `escalation_at` become this event's). `attached_to` must name the current, unaccepted escalation of another ladder of the case whose rung has the same target; the machine has no calendar, so the same-day test is the sweep's. The two keys are exclusive. `escalation_accepted` on any ladder also accepts every other ladder whose current rung is recorded on the same escalation: one human acceptance covers the coalesced escalation. Without a named milestone and with the state's ladder empty, acceptance picks the milestone ladder when all running ones share one escalation. The payload schema (`payloads.Escalate`, `AlsoFor`) is strict: exactly one of `state` and `milestone` per entry, no extra keys, `attached_to` an event id, never both.
- **Simulator.** `start_ladder` carries the ladder's source (`state` or the milestone name) into the rung event data. `on_rung` keeps, per case and notify role, the last emitted rung (working day `floor(t)`, the step token, the event, the source). A rung for the same role on the same day and token from a different source emits nothing and takes no action (no outreach, no staff reaction draw); it appends `{"step": ...}` or `{"milestone": ...}` to the earlier event's `also_for` and counts `escalations_coalesced`. The per-case random draws are pre-drawn arrays except the outreach response index, so cases that never coalesce are unchanged.
- **FHIR.** There is one Task per case, so an attached escalation creates no second Task; the Task's `escalation-level` extension is now the highest rung on any ladder (as the worklist), and the event keeps its Provenance.

**Consequences.**
- A role gets one message per case per working day for any number of concurrent breaches; the timeline shows which ladders an escalation stands for. The numbers are in `docs/results/results.md`; against the pre-A19 run at `programme_reach` 0.50: upper range 211.6 to 205.2 escalations per 100 cases and 79.3% to 79.6% completion at 180 days; literature anchored 111.5 to 108.5 escalations per 100 cases and 64.9% to 65.0% (ratio 1.246 to 1.248). Coalescing removed about 6 events per 100 cases in the upper range, so it is a small change to the headline; its value is that nobody is told twice, not a shift in completion. `programme_reach` was refitted afterwards (ADR-028).
- **Known limit.** A ladder keeps only its current rung. After a scheduler outage one sweep emits two rungs of one ladder on the same day (say the owner's and the supervisor's); a third ladder whose owner rung falls due later that same day finds the ladder at the supervisor rung and is not attached, so the owner is told twice that day. It needs an outage longer than the rung spacing; the property test therefore sweeps at least every two days, and the outage itself is tested separately (every rung coalesces, levels in order).
- A rung that rides on another's `also_for` has no event of its own, so a consumer reading the rungs of a ladder must read both `escalate` events with its `milestone` or `state` and the `also_for` entries naming it (`tests/test_coalesce.py`, `ms_rungs`). The worklist and case page read the model, which is unaffected.
- The escalation acted-on rate in the simulator is computed over fewer events, because the removed ones were mostly second, redundant escalations.
- Not changed: the ladder, its offsets, who accepts, the acceptance event, the idempotency rule (ids from the clock-starting event, never a time), and that nothing in the API sends a message on an `escalate` (notification of a rung is still the web's and the notifier's job; an `attached_to` event is the signal not to send one).


## ADR-032: The sweep reads only the cases that can be due, and writes many cases per transaction

**Context.** The scheduler sweep read and replayed every open case on each pass (ADR-013) and appended each case's events in a transaction of its own. At 100,000 open cases that is one Python replay and one locked transaction per case whether or not anything was due, and the 5 s target (F6, T-F8) was missed by the single process and by the default four-worker pool. About nine in ten cases have nothing to plan at a given sweep.

**Decision.**
- **A derived due time per case.** `cases.next_due_at` (migration 012) holds the earliest instant at which `plan_case` could plan anything for the case: the state SLA, each running milestone, the escalation rung that would be next, or the close of a pending handoff's response window (`app.sweep.next_due_at`, a pure function of the read model, the pathway and the calendar). `PostgresEventStore.append_many` and `append_batches` recompute it from the replayed model in the same transaction as the events, so a committed event and its due time cannot disagree. `events` stays the only source of truth: the column is never read as fact, only as a reason to skip a case.
- **NULL means "not computed", never "nothing due".** A case with nothing left to watch holds 9999-12-31. A new case, a row from before the migration, or a case whose value was written under another timing fingerprint (`cases.next_due_basis`: a hash of the working-day calendar and the pathway's SLAs, ladder, milestones and handoff window) is always read and replayed by the sweep, and its value is written back under the row lock, only if no event arrived since the read. A changed holiday list or SLA therefore cannot leave a stale due time that hides a breach. If computing the value fails the column stays NULL: a bug costs time, never a breach.
- **What the sweep selects.** `next_due_at <= now`, plus every case with no usable value. The bound is exact up to the boundary (the planner needs `now > due`, the column holds `due`), so the events a sweep emits are those of a sweep of every case. `SWEEP_FULL_SCAN=1` (or `run_sweep(full_scan=True)`) reads every case as before, for an operator who distrusts the index; `only=` also does.
- **Batched writes.** `PostgresEventStore.append_batches` appends the planned events of up to 100 cases (`SWEEP_BATCH_CASES`) in one transaction. Per-case semantics are those of `append_many`: the case row is locked (`FOR UPDATE`, in id order, so overlapping batches cannot deadlock), its stored log is re-read, replayed and checked against `cases.current_state`, an event already stored with the same content is a no-op, one with different content is `EventContentConflict`, and every event must be a valid step from the state before it. A case that is refused returns its exception in its slot and writes nothing; the others commit together. If the batch as a whole fails (a lost connection, an id taken by a concurrent writer between the check and the insert) nothing is written and the sweep appends each case on its own, which finds each in a known state. A bounce (`handoff_rejected`) is never batched.

**Consequences.**
- Measured on 100,000 seeded open cases (docs/results/load.md, one sweep that emits a day's 14,110 events): the unchanged tree took 60.9 s in one process, 32.0 s through the route with 4 workers and 17.5 s with 10; with the index and batching 8.7 s, 3.9 s and 3.2 s. Each change alone: the index only, 54.4 s, 14.0 s and 12.2 s (it removes the read of 91,196 of the 100,000 cases but makes one-transaction-per-case appends dearer, because every append now writes an indexed column); batching only, 60.8 s, 20.2 s and 10.3 s. Both are kept. A sweep with nothing to do takes 0.02 to 0.14 s instead of 10 to 41 s.
- The first sweep after the migration reads every case once (the column is NULL), as the old sweep did, and writes the values back. A sweep after a calendar or pathway change does the same. `docs/results/load.md` ("First sweep after migration 012") measures it.
- Every writer of `cases` goes through `PostgresEventStore`, which is the only place that sets the column; a case written by raw SQL (tests, seeding) has NULL or a value that `tests/test_next_due_pg.py` shows is the function of the log. A wrong value stored by hand is trusted until the case's next append; `SWEEP_FULL_SCAN=1` ignores it.
- Not built: caching the replayed read model per case in a JSONB column (the second option in the ticket). It would remove the replay on read for the cases the sweep still selects, but not the replay the append repeats under the lock (the engine's safety property), and it adds a second derived copy of the log to keep in step. It was left out because the index and batching met the target at the route's default of four workers (3.9 s) and the cost that remains is partly that second replay.
- Two things stay as they were: the planner (`plan_case`) is unchanged, and the sweep never closes a case.
