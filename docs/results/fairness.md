**All data are synthetic.** The triage replies are developer-written templates, the risk-score cohort is simulated and the red-team set is self-authored. These numbers show how the shipped models and rules behave on those sets, split by language. They are not evidence about real patients. No native Arabic speaker and no clinician has reviewed the data yet (H1, H2).

**Proposed mitigation for ar_gulf (not shipped).** The deployed threshold already meets the 97% target on this group's validation replies (70), so a stricter threshold fitted the same way changes nothing: the test shortfall is a generalisation gap between templates. No threshold fix is proposed; the mitigation is real replies of this group in the next training set (H2), and until then sending the group's replies to a person.

**Proposed mitigation for arabizi (not shipped).** A threshold of 0.918 for this group (deployed: 0.553), chosen on the validation split (71 replies) for 97.0% precision, gives 100.0% auto-handled precision (84.5% to 100.0%) on the test split at 21.2% coverage (21 replies). It needs the API to tell this group apart at run time, which it does not do today; the alternative is to send every reply of the group to a person.

Always-human replies acted on without a person (ar, label->read as): other->confirm, other->confirm, other->confirm.

Always-human replies acted on without a person (arabizi, label->read as): question->reschedule.

## What this does not show

- Performance on real patients' replies, real dialect spread (Emirati, Levantine, Egyptian, South Asian English) or real Arabizi spelling.
- Intersectional groups (for example Arabizi on WhatsApp, or age by language) for the risk score.
- Whether the Arabic templates read naturally: that is the native-speaker review (H2), not a metric.
