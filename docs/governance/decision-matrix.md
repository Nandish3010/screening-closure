# Automated-versus-human decision matrix

Who, or what, may take each action in the system, what evidence it needs, what it changes, and which test shows the restriction holds. One row per event type in the final vocabulary ([PLAN.md](../../project/PLAN.md) section 6), plus the routes that matter for control. This is a design record for reviewers and regulators, not a compliance claim.

Authority is the code: `api/app/policy.py` (who may try), `api/app/state_machine.py` and `config/pathways/colorectal_fit.yaml` (whether the event is valid). The state machine decides whether an event is valid; the policy table decides who is allowed to try. Pathway v0.2; every event type in `policy.py` has a row, which `tools/check/docs_check.py` (T-E6) checks.

## How to read it

- **Automated actor** means an actor whose name starts with `system:`, `scheduler`, `watchdog` or `model:`. Automated actors cannot log in as users: `POST /auth/dev-login` refuses those role names (`agency` among them since A22), and a validly signed token still cannot carry one (ADR-012). The only automated identities that can call the API are three service tokens: the scheduler's, which maps to `system:scheduler` and may emit `mark_overdue`, `escalate` and the bounce form of `handoff_rejected`; the watchdog's, which maps to `system:watchdog` and may emit `watchdog_flagged` only (A11); and the agency supervisor's, which is optional (`AGENCY_SERVICE_TOKEN`), maps to `system:agency:supervisor`, may call `POST /agency/run` and no other route, and may emit no event at all (A22, ADR-033). The notification mock (`system:notifier`) and the consent ledger (`system:consent`) act in process and have no token or route, and so do the five department agents of the agency (`system:agency:<department>`).
- **Who refuses an automated actor.** For events in the pathway's `human_only_events` list the state machine itself refuses any automated actor, and refuses `close` for any automated actor. For every other event, no automated identity is granted it by the policy table, so the API refuses it; the state machine alone would not. The "Automated actor?" column says which applies. The agency is the third case: the state machine refuses every event from an actor starting `system:agency:`, whatever the policy table says (section "Agency actors").
- **What it changes** uses three words. `state`: the main or side state moves. `flag`: a derived flag in the read model changes (`overdue`, `escalation_level`, `escalation_accepted`) and the state does not. `nothing`: an annotation that is recorded and changes neither the state nor a flag (it may still set the owner or feed a later step, as stated).
- **Test** cites the T-ID from [TEST-CASES.md](../../project/TEST-CASES.md) and, where one exists in the repository, the test name. "Pending A5 (T-A20)" means the test does not exist yet and names the ticket that will write it and its T-ID. Role names are in backticks only where they are part of the policy.
- Roles: `lab`, `primary_care_owner`, `specialist_owner`, `coordinator`, `patient`, `supervisor`, and the service roles `scheduler`, `watchdog` and `agency`.

## Agency actors

The agency (A22, ADR-033, [agency.md](agency.md)) is one supervisor, five department heads and fourteen executioners. The agency is preparation only. Its agents are labour, not authority, and the only thing any of them causes is a message draft (Outreach, through the drafting route): no agency actor appears in `EVENT_POLICY`, the events route refuses the `agency` role for every event type, and `step()` in `api/app/state_machine.py` refuses any event whose actor starts with `system:agency:` before it looks at anything else. This table has the same six columns as the Events table. Here "Roles that may emit it" is the events the actor may emit (none), and "Evidence or payload required" is what the actor may cause through another actor's own path (`AGENCY_CAUSES` in `api/app/policy.py`), checked on every tool call by `authorize_agency`. `AGENCY_NEVER` (`close`, `clinician_review`, `reopen`, `message_approved`, `message_rejected`, `message_sent`, `escalation_accepted`, `handoff_accepted`, `handoff_rejected`, `reassign`, `consent_updated`, `accept_ownership`, `callback_requested`, `handoff_requested`, `complete_confirmatory`, `reply_classified`) is refused for every agent even if an entry were edited.

## What holds in structure

These five properties do not depend on a person following a procedure. Each has a test, and the matrix above is where a reviewer can see the exceptions.

1. **No closure without evidence and a human clinician.** The guard is in the state machine and runs inside the database transaction. No automated actor, and no role other than the two clinician roles, can emit `close` (T-A1, T-A3, T-A4, T-A26).
2. **Automated actors cannot log in as users.** The only automated identities that reach the API are the scheduler and watchdog service tokens, each limited to its own events (T-A26, T-A30).
3. **`message_sent`, `message_approved` and `message_rejected` have no poster.** Nobody can post them through the events route. `POST /drafts/{id}/approve` writes the approval (with its outbox row) and the notification mock writes `message_sent`, in that order, and nothing else can (the state machine refuses a send for a draft nobody approved, ADR-030); `POST /drafts/{id}/reject` writes the rejection (T-D1, T-D13, T-D5).
4. **Human-only events.** `escalation_accepted`, `handoff_accepted`, `consent_updated`, `message_approved`, `message_rejected`, `callback_requested` and `reopen` are refused for any automated actor by the state machine itself (T-A14, T-A19, T-A26).
5. **No agency actor can emit any case event.** The state machine refuses every event, of every type and in every state, from any actor starting `system:agency:`; no agency role is in `EVENT_POLICY`; the agency token reaches `POST /agency/run` and no other route; and no tool the agents hold writes a case event or causes a decision. The agency is preparation only: the one thing an agent causes is a draft, which the drafting route writes as `model:<provider>` under that route's rules and which waits for the owner's approval. A handoff request, a reply label and every other decision stay with a person or the service that owns them (T-A60, T-A61).

## What the matrix does not yet cover

- Scoping of owners by organisation. Owners act only on cases they own (A5), but there is no per-organisation scoping beyond the provider claim (limitation L29).
- Nothing about role-by-route denial: [rbac-matrix.md](rbac-matrix.md) is generated from the OpenAPI route list, probes every role against every route and event type (own case and another's), and fails `make test-security` if it drifts or a route has no policy. It found one gap: `POST /cases/{id}/drafts` is not owner-scoped (G-1).
- An `erasure` marker event, if the implementing ticket for ADR-025 adds one. It is not in the vocabulary, so it is not in the matrix.

## Keeping it true

Completeness is meant to be checked by a test (T-E6, pending F1 docs-check): every event type in the pathway config and in `EVENT_POLICY` must have a row here, and the roles in the first column must equal the policy. When an event type, role or route is added or changed, update this file in the same commit.
