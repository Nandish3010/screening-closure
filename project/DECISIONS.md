# Decisions

Architecture decision records, one per decision. Add new entries at the end with the next number; change a decision by adding a new entry that supersedes the old one, not by editing history. Status is `accepted` unless stated. Plan: [PLAN.md](PLAN.md).

## ADR-001: Deterministic engine with human gates

**Context.** The domain is safety-critical: a wrong or invented closure means a patient with a positive screening result is treated as finished. The brief asks for an auditable system and for a clear position on agentic approaches. Whatever decides a state change must be explainable line by line to a regulator and give the same answer when replayed.

**Decision.** State transitions are decided by deterministic code (a pure state machine over a pathway config) and by humans. A language model may draft a message or summarise a document but never moves a case between states, escalates, or decides a closure. The design is "the model drafts, humans decide". A model actor (`model:` prefix) is treated as automated and cannot emit state-changing events; a closure needs `evidence_ref` and `signed_by` from a non-automated actor.

**Consequences.**
- The closure invariant can be proved by property test (T-A1) rather than argued in prose.
- The system works unchanged when the model is unavailable; the template fallback covers drafting.
- We give up open-ended automation. Anything the engine cannot decide becomes a task for a person.
- The comparison with agentic orchestration is written up neutrally in `docs/design-choices.md` (auditability, replayability, latency, cost per case, failure modes, model unavailable).

## ADR-002: Event sourcing with derived current_state

**Context.** We need a full audit trail, replay for verification, and idempotent handling of retries and duplicates. A mutable "status" column would lose history and could drift from what actually happened.

**Decision.** The append-only `events` table is the source of truth. `cases.current_state` is a derived read model, never trusted without replay: every append replays the stored log, checks it against `current_state`, and raises `StateCorruption` on disagreement. Every event carries an `event_id` used as an idempotency key.

**Consequences.**
- Replay determinism is testable (T-A2, T-A9) and the timeline is the audit log.
- Reads of state are cheap but writes pay for a replay per append; fine at pilot scale, to be measured by the 100,000-case load test (T-F8).
- Schema changes need care because history is permanent. Migrations run at API startup from `api/migrations/*.sql`.

## ADR-003: Transition check inside the database transaction

**Context.** Checking a transition in the API process and then writing lets two concurrent requests both validate against the same old state and both commit, which could break the closure invariant under concurrency or retries.

**Decision.** The state-machine check runs in the same transaction that locks the case row (`SELECT ... FOR UPDATE`) and inserts the event. Validate-then-append is atomic; an invalid transition leaves nothing behind.

**Consequences.**
- Concurrency and atomicity are proved by integration tests (T-A5, T-A7).
- Writes to one case are serialised; cases are independent so this does not limit throughput across cases.
- The state-machine function must stay pure and fast because it runs while the lock is held.

## ADR-004: Append-only triggers in the database

**Context.** Application code can be correct and still be bypassed by a bug, a manual query, or a migration mistake. An audit log is only credible if it cannot be edited.

**Decision.** Database triggers reject `UPDATE`, `DELETE` and `TRUNCATE` on `events` (`events_forbid_mutation`).

**Consequences.**
- Immutability holds below the application layer (T-A8).
- A database superuser can still drop the triggers, so this is tamper-evidence in a pilot setting, not a defence against a malicious administrator. Production would add access controls and log shipping. This goes in the limitations table.
- Test cleanup cannot truncate `events`; tests use their own cases or a separate database (F2).

## ADR-005: Synthea for the cohort, and its US-geography limitation

**Context.** We need a realistic synthetic population in FHIR R4, with no real patient data, and a seed so it is reproducible. We have no access to UAE data and would not use it for a hackathon prototype.

**Decision.** Use Synthea v3.3.0 (pinned jar, sha256 checked, run only inside a container) with seed 20261017 and a fixed reference date, for 300 living patients aged 45 to 75. Synthea has no FIT screening for this pathway, so FIT results are generated by our own seeded script at an assumed positivity rate. Version, seed and parameters are recorded in `docs/data-provenance.md`.

**Consequences.**
- Fully synthetic and reproducible.
- Synthea needs a US state (we use Massachusetts), so names, addresses, facilities and care patterns are US. There are no Arabic names and no UAE demographics or health-system structure. Patient language and contact channel therefore come from the simulator as labelled assumptions, and the limitation is stated in the provenance and limitations documents.
- Which patients test positive is unrelated to their clinical history. The cohort demonstrates the pathway mechanics, not epidemiology.

## ADR-006: HAPI FHIR on the shared Postgres

**Context.** HAPI's default in-memory H2 database ran out of heap when loading the synthetic cohort (about 1 GB of FHIR JSON for 300 patients). We also want cases and FHIR resources to stay consistent after a reset.

**Decision.** HAPI FHIR R4 stores its data in the same Postgres database as the case store, in its own `hfj_*` and related tables, which do not collide with `cases` and `events`. The JVM heap is raised to 3 GB for large patient bundles.

**Consequences.**
- `make reset` (`docker compose down -v`) wipes cases and FHIR resources together, so they cannot disagree.
- One database to back up and size, but HAPI and the case store share load and a failure domain. Acceptable for a prototype; a pilot would separate them.
- The image tag is currently `latest`, which weakens reproducibility; pin it before the fresh-clone verification (F12).

## ADR-007: AI only at the edges

**Context.** Language models are useful for drafting patient messages in Arabic and English, but they are non-deterministic, may be unavailable, and can produce wrong or unsafe text.

**Decision.** AI is allowed in exactly two places. (1) Drafting patient messages: the draft is validated, shown to the case owner, and not "sent" until the owner approves; prompt, draft, approver and timestamp are stored as Provenance; a deterministic template is the fallback and the default (`LLM_PROVIDER=template`). (2) A single calibrated loss-to-follow-up risk score (logistic regression) used only to order the worklist; it never closes, escalates or decides care. Model outputs used in the demo are cached so the demo needs no network.

**Consequences.**
- The approval gate is structural: there is no code path to `message_sent` without `message_approved` (T-D1).
- Fallbacks are counted as the automation abstention rate and reported in the evaluation.
- Jais and Azure OpenAI are optional adapters and are never called by tests or by the default configuration.
- The risk score is on the cut line; without it the worklist is ordered by SLA breach alone.

## ADR-008: FHIR as the data model, Malaffi as a stated target

**Context.** Interoperability is a judging concern and a real adoption barrier. Abu Dhabi's health information exchange, Malaffi, is the obvious integration target, but we have no access to it and cannot claim an integration.

**Decision.** Model every object as a FHIR R4 resource: `DiagnosticReport` (the FIT result), `Task` (the case and ownership), `ServiceRequest` (the referral), `Appointment`, `Communication` (patient messages), `Consent`, `Provenance` (audit). The event log remains the source of truth and FHIR resources are a projection of it. The documentation includes a one-page adapter plan for Malaffi worded as a target, not a claim, and the names are verified against official sources before they are cited.

**Consequences.**
- The projection can be validated against HAPI (T-A33).
- Two representations exist (events and resources); the projection must be rebuildable from events.
- No claim of integration appears anywhere; the wording is checked by review (T-E4).
- `Appointment` and `Communication` mapping is on the cut line and may be a stub.

## ADR-009: Working-day calendar, UAE default, configurable

**Context.** SLAs in the pathway are in working days (for example acknowledge within 2, book within 14, complete within 45). Counting calendar days would flag weekend breaches that are not breaches. The UAE weekend is Saturday and Sunday for the federal public sector and is not the same everywhere in the world.

**Decision.** SLA due dates are computed on a working-day calendar. The default is the UAE one: Monday to Friday are working days, Saturday and Sunday are the weekend. The weekend set and an optional holiday list are configuration, not code. The scheduler reads time only from the injectable simulation clock.

**Consequences.**
- Due dates are testable by table and by property (T-A12, T-A13).
- Public holidays that move with the lunar calendar are not predictable in advance, so the initial holiday list is empty and documented as an assumption until a source is chosen (A1).
- Verify the weekend convention against an official source before citing it in the submission; some private-sector employers and some emirates may differ, which is why it is configurable.

**Assumption recorded in A1 (holiday list).** `config/calendar.yaml` ships with `holidays: []` and the time zone `Asia/Dubai`. Reason: the dates of Eid al-Fitr, Eid al-Adha and the Islamic New Year depend on moon sighting and are announced days ahead, the fixed-date holidays (for example National Day on 2 and 3 December) can be added by any deployment, and we have no authoritative source in the repository, so a guessed list would be an unsourced number inside the SLA arithmetic. The consequence is that every due date in the prototype and in the evaluation assumes no public holidays, which can only make a due date earlier than reality (a conservative direction for a safety net) and is stated in the limitations table. Adding a holiday is a config edit and needs no code change (tested in `test_calendar.py`).

**Instant semantics (A1).** The calendar day of an instant is its date in the configured zone. A start on a non-working day counts from 00:00 of the next working day; the time of day of the (effective) start is kept, so a 2 working day SLA started Thursday 10:00 is due Monday 10:00. `add_working_days` always returns a working day and `working_days_between(start, add_working_days(start, n)) == n` holds for every start (property-tested, T-A13).

## ADR-010: No SNOMED CT; LOINC and plain text only

**Context.** Codes make resources interoperable, but SNOMED CT is distributed under licence terms. A public repository with a bundled synthetic dataset should not depend on checking licence status for each user.

**Decision.** Use LOINC for the one coded concept we need (the FIT result, LOINC `29771-3`) and plain text in `CodeableConcept.text` elsewhere. No SNOMED CT codes appear in code, data or documents.

**Consequences.**
- The repository is redistributable without licence review of the terminology.
- Results are less machine-interpretable than fully coded ones. The adapter plan notes that a deployment would map to the terminologies its exchange requires.
- The LOINC display name changed between releases while the code did not; the code is authoritative and the display is re-verified before external submission (see `docs/data-provenance.md`).

## ADR-011: Side states are real states; overdue and escalation are derived flags

**Context.** The first pathway file listed six "side states" (`overdue`, `escalated`, `referral_rejected`, `consent_withdrawn`, `reopened`, `lost_contact`) without transitions. Two kinds of thing were mixed in that list. Some change who must act next and what is allowed (a rejected referral, withdrawn consent, a patient we cannot reach, a reopened closure). Others describe the clock: a case can be overdue and in `patient_contacted` at the same time, and can sit at escalation rung two while still awaiting the patient. Modelling the second kind as states would force a product of states (`patient_contacted` x overdue x rung) or lose the main state while overdue.

**Decision.**
- `overdue` and `escalated` are not states. The main-state machine is unchanged and the read model carries `overdue`, `escalation_level` and `escalation_accepted`, derived by replay from `mark_overdue`, `escalate` and `escalation_accepted` events. They reset when the case changes state (a new state is a new obligation with a new clock), except across a consent-withdrawn excursion, which keeps them.
- `referral_rejected`, `consent_withdrawn`, `lost_contact` and `reopened` are real states with transitions in the YAML (list in PLAN.md section 6). Events that annotate a case without changing its state are listed under `annotations:` and are valid in every open state, never in `closed`. The loader refuses an annotation that is a closing or main-path event, a transition into `closed` from anywhere but `clinician_reviewed`, and any transition into `closed` that does not require `evidence_ref` and `signed_by`. The closure guard in the state machine is unchanged.
- `consent_updated{withdrawn:true}` is allowed from every open state and freezes outreach. The prior state is remembered by replay (`resume_state` in the read model) and restored by `consent_updated{withdrawn:false}`. It is deliberately not read from the client's payload: a client-chosen resume target would let a caller jump a case to any state, including past review. This departs from the original sketch ("tracked in payload `resume_state`"), and keeps the same observable behaviour.
- `reopen` takes `closed` to the side state `reopened` and needs a human actor and a `reason`. From `reopened` the only way on is `clinician_review` to `clinician_reviewed`, so a reopened case reaches `closed` again only through a fresh `close` with evidence and sign-off.
- `lost_contact` is entered from `patient_contacted` by `mark_lost_contact` with `failed_attempts` of at least 3 (the 3 is an assumption pending the clinician review, H1) and left by `contact_patient`. `referral_rejected` returns to `owner_accepted` through `handoff_accepted` or `reassign`; `reassign` is added to the vocabulary because the sketch named it but did not list it.
- Some events may not come from automation (`human_only_events`: `escalation_accepted`, `handoff_accepted`, `consent_updated`, `message_approved`, `callback_requested`, `reopen`).
- SLA obligations: a state's SLA is the SLA of its outgoing transition event (for example `patient_contacted` awaits `patient_acknowledge`, 7 working days). `lost_contact` and `reopened` inherit the SLA of the event that leaves them (`contact_patient`, `clinician_review`); `referral_rejected` and `consent_withdrawn` have none here because their timers belong to A5 (bounce) and A6 (human review). While consent is withdrawn the SLA clock is not paused: it keeps running and a breach is detected once the case resumes.

**Consequences.**
- Closure properties (T-A1, T-A2, T-A14) run over the whole alphabet with a stateful fuzzer and a hand-written oracle of allowed state changes.
- `GET /pathways` now serves the richer YAML (`any_open`, `to: resume_state`, `when`, `min`), which is expanded by the loader; clients that read the raw YAML should use the loaded transitions instead.
- Consent events after closure are not modelled (a closed case accepts only `reopen`).
- The audit trail shows `mark_overdue`/`escalate` as events with timestamps, so "why is this case overdue" is answered by the timeline alone.

## ADR-012: Identity from signed dev tokens; default-deny policy tables

**Context.** Until A8 the caller named its own `actor` in the request body, so any client could post `close` as a clinician. The closure guard stops automated actors by name, which is only meaningful if names cannot be forged. We also need roles for the interfaces (Cut C) and a story for the regulator: who was allowed to do what, enforced by code rather than by the UI.

**Decision.**
- Identity is established per request from a bearer token; the event `actor` is `role:name` derived from it. A body that carries `actor` is rejected (422). The only roles a token can carry are the six user roles; `system`, `scheduler`, `watchdog` and `model` cannot authenticate as users, even with a validly signed token.
- Development login (`POST /auth/dev-login {role, name}`) issues an HMAC-SHA256-signed token using `DEV_AUTH_SECRET`. The default secret exists only for local development: with `APP_ENV` other than `dev` the API refuses to start while the secret or the scheduler service token is still the built-in default. `DEV_LOGIN_ENABLED=false` removes the login route. Tokens do not expire, because the API never reads the wall clock (T-A17); a production deployment replaces `app/auth.py` with an OIDC verifier that yields the same `Identity`.
- The scheduler authenticates with a static service token (`SCHEDULER_SERVICE_TOKEN`), is `system:scheduler`, and may emit only `mark_overdue`, `escalate` and `watchdog_flagged`.
- Authorisation lives in `api/app/policy.py` as two default-deny tables: route (method + path template, enforced by an app-wide dependency) and event type (enforced in the event route). A route or event type with no entry is refused, and a test compares the table with the OpenAPI route list so a new route without a decision fails the build. The state machine still decides whether an event is valid; the policy decides who may try.
- Patients are limited to their own case (matched on the genesis `patient_ref`) and to `patient_acknowledge`, `consent_updated` and `callback_requested`. A patient asking for someone else's case gets 404, the same as for an unknown case.
- Extra hardening beyond the sketch: an event's `at` may not be later than the simulation clock. Without it a user could post an event dated in the future and push an SLA deadline out of reach, which is exactly the silent failure the product exists to prevent.

**Consequences.**
- T-A26 and the F7 RBAC matrix test can be generated from the tables.
- Roles are coarse (no per-organisation scoping: any `primary_care_owner` may act on any case). Scoping owners to their own cases comes with the A5 ownership model and is listed in the limitations table.
- `/docs` and `/openapi.json` stay open in development.
- The dev token is a convenience, not an authentication mechanism; the submission must say so.

## ADR-013: The sweep runs next to the event store; the scheduler is its heartbeat

**Context.** The scheduler must find every breached SLA on the simulation clock, emit `mark_overdue` once per breach, and never close a case. It is also the thing we kill on stage, so it must be a separate process with its own heartbeat. The load target (100,000 open cases, F6) rules out shipping every case's history to a client over HTTP on every sweep.

**Decision.**
- The sweep logic is a pure planner plus a runner in `api/app/sweep.py`. The planner takes (case read model, pathway, calendar, now) and returns events; it never reads a clock. The scheduler service calls `POST /scheduler/sweep` every interval with its service token (identity `system:scheduler`; the route is closed to every other caller) and writes the heartbeat. Killing the scheduler stops the sweeps and the heartbeat, which is what the watchdog (A11) checks.
- Due dates: the SLA of the case's current state (PLAN section 6, ADR-011) counted in working days from the event that entered the state (`clock_started_at` in the read model, which the replay sets). A case is late when sim time is strictly after the due time.
- Exactly once per breach: the event id is `uuid5(namespace, case | state | due_at | kind)`. A repeated or concurrent sweep re-plans the same id and the store treats it as a no-op; the state machine independently refuses a second `mark_overdue` for a case that is already overdue. If the planned event is refused because another writer moved the case first, the sweep counts it as `rejected` and re-plans on the next pass.
- The sim clock lives in `app/clock.py`, persisted in the `sim_clock` table (migration 002, one row per `clock_id`, the API uses `main`) so an API restart keeps the simulated date. It only moves forward through `advance`; `reset` is the single explicit rewind. Time is cached in process and the store is read only at start-up, so the API is single-replica by design here.
- `POST /clock/advance` and `POST /clock/reset` are supervisor-only. No code in `api/app` or `scheduler/` reads the wall clock for a decision; an AST test enforces it, with the two heartbeat timestamps as the only marked exceptions.
- The heartbeat file is refreshed every loop, even when the sweep fails, and says whether the last sweep succeeded (`sweep_ok`, `last_ok_wall_ts`), so a live-but-useless scheduler is visible to A11.

**Consequences.**
- The scheduler container stays standard-library only and never touches the database or the calendar config.
- The sweep reads and replays every open case on each pass (chunked, bounded memory); F6 measures whether that needs an index or a materialised due-date column.
- Integration tests pass `only=` so a sweep against the shared dev database touches only the test's own cases.
- Rewinding the clock with `reset` leaves earlier overdue events in the append-only log; `make reset` is the way to start a clean demo.

## ADR-014: Escalation rungs are `escalate` events; a human accepts one with `escalation_accepted`

**Context.** The ladder (reminder at the breach, supervisor after 3 working days, programme coordinator after 7) must never run away from a human who has taken responsibility, and an escalation by itself must not move work: "every rung needs a human to accept". The tracker left the name of the acceptance event to A4, and the earlier draft called the rung event `escalated`.

**Decision.**
- A rung is an `escalate` event with `rung` (`reminder`, `supervisor`, `coordinator`), `level`, `target` (`owner`, `supervisor`, `coordinator`), emitted by the scheduler or by hand by a coordinator or supervisor. The state machine raises `escalation_level` by exactly one and refuses a skipped, repeated or unknown rung, a rung on a case that is not overdue, and any rung after an accepted one. Event ids are `uuid5(case, state, due date, "escalate:<rung>")`, so each rung is emitted once per breach however often or concurrently the sweep runs.
- The acceptance event is named `escalation_accepted`. It is human-only and the actor's role must be in the rung's `accepted_by` list in the YAML (owner roles for the reminder, `supervisor` for the supervisor rung, `coordinator` for the coordinator rung). It may carry `rung`, which must name the latest rung. It sets `escalation_accepted` in the read model, which stops further rungs for that breach. It changes neither ownership nor state: taking the problem on is a separate, deliberate act (`accept_ownership`, `reassign`, or simply progressing the case).
- Timing: a rung is due `after_breach_days` working days after the case's due date, evaluated on the working-day calendar; the sweep emits it when sim time is at or after that instant. All due rungs are emitted in order in one sweep, so a scheduler that was down catches up without skipping. An unanswered rung moves to the next one only through this timing.
- A new obligation (any state change except a consent-withdrawn excursion) starts with a clean ladder: the flags reset and the next breach has new event ids.
- The regulator rung is on the cut line and is not built; the ladder in the YAML has three rungs and the loader checks they are unique and non-decreasing in time.

**Consequences.**
- "Who was told, when, and who took it" is answered from the timeline alone: `escalate` rows, then `escalation_accepted` with its actor.
- A rung accepted by the wrong person is refused by the engine (409), not just hidden in the UI.
- The notification text for a rung (A7) hangs off the `escalate` event; the event names here are what Cut C and the decision matrix (E5) should use.

## ADR-015: Integration tests use their own database, `closure_test`

**Context.** `make test-db` ran against the dev database. Every integration test creates cases and events that nothing can delete (the log is append-only by trigger), so after a few dozen runs the dev database held about 1,200 test cases next to the seeded cohort, and the demo worklist, the sweep and the metrics all saw them.

**Decision.**
- The compose postgres holds a second database, `closure_test`, owned by the same role. A fresh volume gets it from `docker/postgres-init/10-create-test-db.sh` (mounted into `docker-entrypoint-initdb.d`); `make test-db` creates it with the same SQL if it is missing, which covers volumes made before this change. One server, two databases: no extra container, and HAPI keeps using `closure`.
- `make test-db` sets `DATABASE_URL=postgresql://closure:closure_dev_password@localhost:5433/closure_test` (override with `TEST_DATABASE_URL`). `make test-db-reset` drops and recreates it, empty; the test session migrates it again.
- The guard lives in `api/tests/conftest.py` (`pytest_collection_finish`): if any selected test is marked `integration` and `DATABASE_URL` is set, the database name must end in `_test`, otherwise the session aborts with exit code 3 and a message naming the database and the fix. The rule is "marked as a test database" rather than "not named closure", so a typo or a staging URL fails closed. A session-scoped fixture runs the migrations on the test database.
- `make reset` wipes the dev stack, including the polluted test cases and the cohort; `make demo-seed` rebuilds the cohort. The dev database now holds only the seeded cohort.

**Consequences.**
- T-F2 is checked by a unit test of the guard, a real pytest subprocess pointed at the dev URL that must abort, an integration test asserting `current_database()` ends in `_test`, and a before/after row count of the dev database around `make test-db` (unchanged).
- The unit suite (`make test`) is unaffected; with `DATABASE_URL` unset nothing here runs.
- Running `pytest -m integration` by hand with the dev URL now fails on purpose.

## ADR-016: Referral handoff: ownership moves only on acceptance; the scheduler bounces silence

**Context.** A referral that nobody answers is how a positive result gets lost: the referrer thinks it is handled, the receiver never saw it. The contract has to say who owns the case at every moment, what an answer looks like, and what happens when there is none. A8 also left every clinician able to act on every case, which makes "who owns it" decorative.

**Decision.**
- `handoff_requested {to_provider}` (the owner, or a supervisor for them) records a pending request in the read model (`pending_handoff`) and changes nothing else. `handoff_accepted` by a clinician (human only; not the requester, not the owner it came from) makes the accepter the `owner`, sets `provider`, and clears the request. `handoff_rejected {reason}` clears it; ownership stays with the referrer. Both answers need a pending request, so an unsolicited acceptance cannot take over a case. One request may be pending at a time. A request needs an owner to hand over from.
- Taxonomy: `capacity`, `wrong_service`, `missing_info`, `patient_declined` (YAML `handoff_reject_reasons`). Anything else is a payload error: HTTP 422, nothing written. `timeout` is a fifth reason that only `system:scheduler` may use, with `bounced: true`; a human using it is a 422, and the scheduler using any other reason is a 422. This is the one `handoff_rejected` the scheduler is allowed to emit.
- The rejection moves the case to `referral_rejected` only from the referral states (`patient_acknowledged`, `confirmatory_booked`), as before. From any other open state it is an annotation that clears the request and leaves the state alone (so a bounce in `consent_withdrawn` cannot lose the remembered resume state). Both are logged with their reason.
- The bounce: the sweep plans `handoff_rejected {reason: timeout, bounced: true}` when sim time is strictly after `requested_at + handoff_response_working_days` working days (YAML, 3; the simulator's `handoff.response_sla_working_days` is also 3). The event id is a uuid5 of (case, request time), so repeated and concurrent sweeps insert it once, and answering first makes the sweep plan nothing. A bounce comes alone in a plan and the sweep re-plans from the new model, because a bounce can change the state.
- Escalation of a bounce: `referral_rejected` now has an SLA, `reassign: 2` working days (a state's SLA is the SLA of its outgoing event; both `reassign` and `handoff_accepted` leave it). The bounce starts that clock, so an un-rerouted case goes overdue and walks the existing ladder (reminder to the owner, supervisor, coordinator). No second mechanism.
- Per-owner scoping, in the API layer (`policy.authorize_owner_scope`): a `primary_care_owner` or `specialist_owner` acts only on a case whose `owner` is their `role:name`, except `accept_ownership` on an unowned case and `handoff_accepted` / `handoff_rejected` on a case whose pending request names their provider. A clinician's provider is a login claim (`provider`, default their name), because the identity had no organisation. Supervisors, coordinators, lab and patients are not owner-scoped.

**Consequences.**
- Passing a case to a specialist is now three events (request, accept, then the specialist acts), not an implicit change of hands. Existing tests that had a second clinician act on a case they did not own were rewritten to go through the handoff.
- A clinician who is not the owner now gets 403 where they used to get 409 or success (for example `close` on a case nobody owns yet). 403 is the right answer: the call is outside their scope before it is a question of state.
- The simulator is unaffected: it logs handoffs itself and validates only the main chain through `apply`.
- Limits: the provider claim is a dev-login convenience (a real deployment takes it from the identity provider); `handoff_accepted` does not check that the accepter's role is `specialist_owner` (the policy allows both clinician roles, so a referral to a primary care provider works).
- The new rules apply on replay. A log written before A5 to A7 that has, say, a `handoff_accepted` with no request, or a `message_sent` from another actor, no longer replays (the sweep reports it under `errors`, and an append to it is refused as corruption). That is acceptable before release; `make reset` and `make demo-seed` rebuild the dev database, and the seeded cohort only contains `case_created` events.
- Web mirror: `web/src/lib/pathway.ts` mirrors SLAs; the new `reassign: 2` row for `referral_rejected` is for Cut C to pick up.

## ADR-017: Consent is an append-only ledger by replay; withdrawal freezes outreach in the engine

**Context.** Patients must be able to say which channels may contact them, whether their data may go to the specialist, and "stop". A withdrawal that only hides buttons in the UI is not a withdrawal: the same API serves the coordinator app, the scheduler and (soon) the message approval path. We also need the history, not just the latest setting: who changed what, when, on whose instruction.

**Decision.**
- `consent_updated` carries any subset of six booleans: `channel_sms`, `channel_whatsapp`, `channel_phone`, `channel_letter`, `share_with_specialist`, `withdrawn`. The ledger is the event log itself. `read_model.consent` is the current value, `read_model.consent_history` is every change in order (`{at, actor, changes}`), both derived by replay (ADR-002); nothing is stored separately. A payload with no known key, or a non-boolean value (`1`, `"true"`, `null`), is a payload error (422). Unknown extra keys are tolerated and ignored.
- Defaults before the patient says anything: every channel allowed and sharing allowed (`updated_at` null tells a reader nothing was recorded). This is an opt-out model, an assumption for the clinician and consent reviews (H1) rather than a legal position; the alternative (nothing allowed until recorded) would make the notification mock refuse every message for the whole seeded cohort.
- `withdrawn: true` is the existing transition into `consent_withdrawn` (ADR-011). `consent.withdrawn` always equals "state is consent_withdrawn" (the state is the authority), and `consent_frozen` is that same fact.
- The freeze is enforced in the state machine, not in the router: while frozen, `contact_patient`, `message_drafted`, `message_approved`, `message_sent` and `handoff_requested` are refused with a message that starts "consent withdrawn" (HTTP 409 from the API, `InvalidTransition` from any store). It does not stop `callback_requested`, escalation, `watchdog_flagged` or channel changes, and it does not stop a human re-recording consent.
- Human review flag: when the API accepts a `consent_updated` that leaves the case frozen with no review flagged, it appends `review_requested {reason: consent_withdrawn, source_event_id}` as actor `system:consent`. The new event type is an annotation; no route can post it (EVENT_POLICY is empty for it) and the state machine accepts it only from `system:consent`, and `system:consent` may emit nothing else. The event id derives from the withdrawing event, so a client retry heals a flag that failed to write and never doubles it. The flag is two appends, not one transaction: if the second fails the withdrawal stands and is frozen (the safe side), the request errors, and the retry completes the flag. The flag clears (`review_reason` null) when consent is restored; the event stays in the log.
- Who may change consent: the patient on their own case and the coordinator recording the patient's instruction (existing event policy); every other role gets 403. Consent updates after closure are not modelled.
- Not decided here: the web client currently sends `{channel, share_with_specialist}` (web/src/api/contract.ts); the backend contract is the six booleans above, so the client needs to send `channel_*` flags.

**Consequences.**
- T-A24: history and derived value come from the same replay, so they cannot disagree; the append-only trigger on `events` makes the history tamper-evident.
- T-A23: nothing can be drafted, approved or sent for a frozen case by any caller; the notification mock (A7) also checks consent itself, so the guarantee does not rest on one layer.
- A frozen case has a reviewer-visible flag and sits in `consent_withdrawn`, which `GET /cases?state=consent_withdrawn` lists. The SLA clock keeps running (ADR-011); a breach is detected once the case resumes.

## ADR-018: The notification mock is the only outbound path, and it is a log

**Context.** The product must show that a message reaches a patient only after a human approved it, and that the system honours consent. The demo runs offline and uses synthetic data, so nothing may actually be sent. The same code path has to be the one D5 (approval) uses, so that "no other path to `message_sent`" is a fact about the code, not a convention.

**Decision.**
- `app/notify.py` has one entry point, `send(case_id, channel, language, purpose, body, ...)`, a Python function (no route). It reads the case's read model and, in order: refuses if consent is withdrawn or that channel is switched off (`blocked_consent`, reason says which), refuses if the case's `case_created` payload flags the contact invalid (`contact_valid: false`, or a per-channel map; `blocked_contact`), otherwise appends `message_sent` from `system:notifier` and logs the row as `sent`. It imports no module that can open a connection (an AST test enforces that, and a socket-blocking fixture proves it at run time).
- `message_sent` has an empty route policy (nobody can POST it) and the state machine refuses it from any actor but `system:notifier`; it is also refused while consent is withdrawn, so a forged call fails twice. `emit_message_sent` is a separate function in the same module for D5 if it needs the event without a log row; it carries the same actor.
- Table `notifications` (migration 003): id, case_id, channel, language, purpose, body, status, reason, event_id, created_at (simulation time), append-only by trigger like `events`. Status is `queued | sent | blocked_consent | blocked_contact`. A CHECK ties `status = 'sent'` to having a `message_sent` event; `event_id` names that event but is not a foreign key (the event is always written first, and a foreign key would make `TRUNCATE events` fail on the constraint before the append-only trigger can refuse it, which the existing integration test checks). `queued` is reserved for an approved-but-undelivered message and nothing writes it today, because the mock delivers at once.
- Blocked attempts are logged with their reason but write no event: nothing was sent, and the log is where a reviewer sees the refusal. This departs from the T-A25 wording "a withdrawn channel produces no row"; the intent (no outbound record) holds because only `sent` rows are outbound, and the test cases now say so.
- Two writes, not one transaction: `message_sent` is appended first, then the row. If the second fails the audit trail has the event and the log lacks the row (the safe side for a regulator), and the exception reaches the caller. A single transaction would need the notification table inside the event store's connection; not worth it for a mock.
- `GET /cases/{id}/notifications` returns the log for owners (their own case only, as for events), coordinators and supervisors; patients and lab do not see it.
- The contact validity flag can be set when the case is created (`POST /cases {contact_valid}`). Marking a number wrong after creation is not modelled.

**Consequences.**
- T-A25 and the notification half of T-A23 are checked against both the in-memory log and Postgres.
- D5 only needs `notify.send(...)` after `message_approved`; the gate itself (an approved draft exists) is D5's.

## ADR-020: Every open state has a timer, and the confirmatory SLA runs from referral acceptance

**Context.** Two gaps in the first SLA table (assumptions L12 and L13). `close` had no SLA, so a case that had been clinician-reviewed but not signed off could sit for ever without going overdue; the simulator papered over it with its own 3-working-day sign-off SLA that the engine did not have. And the 31-working-day colonoscopy target was counted from the `confirmatory_booked` state, while the DoH standard counts it from referral, so a case booked late could meet our SLA and still miss the national measure.

**Decision.**
- `slas_working_days.close: 3` in the pathway YAML. `clinician_reviewed` now has a timer, a breach, and a ladder like every other open state. 3 is the value the simulator already assumed (`orchestration.signoff_sla_working_days`); it is still a design choice for the clinician review (H1), and because the engine now reads it from the YAML the simulator's `setdefault` is a no-op.
- A per-SLA clock start, in a separate YAML map so `slas_working_days` stays a plain event-to-days map for the simulator and the web mirror: `sla_clock_start: {complete_confirmatory: handoff_accepted}`. The default is `state_entry` (the event that entered the state). `handoff_accepted` means the latest `handoff_accepted` on the case, whichever state it happened in, and falls back to state entry when no handoff was ever accepted (a case with no formal referral keeps the old behaviour). The loader refuses a value outside `{state_entry, handoff_accepted}` and a key with no SLA.
- Read model: `clock_started_at` is now the effective start of the current state's SLA clock (it equals the entry time for every SLA but the confirmatory one); `referral_accepted_at` is new. The sweep is unchanged: `due_at_for` already counts working days from `clock_started_at`, so `breach_due_at` (taken from the `mark_overdue` payload) follows.
- A `handoff_accepted` that arrives while the current state's SLA runs from acceptance restarts the clock and clears `overdue`, `escalation_level`, `escalation_accepted` and `breach_due_at`: a new obligation, the same rule as a state change (ADR-011). The earlier `mark_overdue` and `escalate` events stay in the log.
- The simulator keeps arming the confirmatory timer on entering the step, because it models no referral acceptance at booking: that is the "no handoff occurred" fallback, so its numbers do not change. Only the pathway hash recorded in `results.json` changes with the YAML.

**Consequences.**
- Any handoff counts as a referral, including a primary-care to primary-care transfer; the effect is to start the clock early, which is the conservative side. The next ticket that models the specialist referral explicitly (a role or reason on the handoff) can narrow it.
- T-A34 and T-A35 test the rule. The assumption table entries L12 (no `close` SLA) and L13 (clock start) are closed by this change; those documents live on the docs branch and are updated at merge.

## ADR-019: Opaque actors, a users table for names, and a strict payload schema per event type

**Context.** The event log is append-only by trigger (ADR-004), so anything written to it stays. Until now the `actor` was `role:name` with whatever name was typed at login, `reopen.reason`, `owner`, `signed_by` and `message_drafted` text were free strings, and an unknown payload key was tolerated and stored (ADR-017). That puts personal data in a place that cannot honour an erasure request, and in log files (assumption L24, hazard HZ-13).

**Decision.**
- Actors are `role:user_id`. The `user_id` is an opaque slug: the first 12 hex digits of a uuid5 over `role|name` in a fixed namespace, computed at login. The same person logging in as the same role gets the same id, so history stays coherent; the id is not readable and is not the name. Services keep `system:scheduler` and `system:watchdog`.
- The name typed at dev-login goes to a `users` table (migration 004: `user_id`, `role`, `display_name`, `provider`), upserted at login and lazily for any valid token whose row is missing (a database reset must not blank the UI). It is the one place names live: erasing a person is one row, and the log holds nothing to erase. `GET /me` returns `{user_id, role, display_name, provider?}`. The case routes return `owner` as `{actor, display_name, role}` and an `actors` map covering every actor in the log; `read_model.owner` stays the actor string. An id with no row resolves to itself, so the UI always has something to show.
- Every event type has a strict pydantic model in `api/app/payloads.py` (`extra="forbid"`, strict types). String values must match the shape of an id or code (references, uuids, hashes, short codes), not prose. `reason` fields take only a taxonomy (the existing four handoff reasons, plus new ones for `reopen`, `callback_requested`, `watchdog_flagged`, `review_requested`). The one deliberate free-text field is `note`, at most 200 characters, on the events a person posts; the documentation tells staff not to put identifiers or clinical detail in it. A reviewer can see exactly what may enter the log by reading one file.
- `message_drafted` carries `draft_id, provider, fallback_used, prompt_hash, language`. The text stays in the `drafts` table (erasable) and the web reads it with `GET /cases/{id}/drafts`. That router lives on the AI cut's branch and is not in main yet; PLAN.md section 6 and `web/src/api/contract.ts` record the expectation only.
- The schema is checked in the API (422 before anything is written) and by the in-process emitters (sweep, consent ledger, notification mock) before they append; the sweep reports and skips a planned event that fails instead of stopping for every case. The pure state machine and the simulator are not bound by it: the machine keeps its semantic rules (taxonomy membership, who may use `timeout`), and the simulator's synthetic logs are not production data.
- `watchdog_flagged` moves to a new `watchdog` service role with its own token (`WATCHDOG_SERVICE_TOKEN`) in preparation for A11; the scheduler no longer holds it.

**Consequences.**
- Supersedes the clause in ADR-017 that unknown extra keys in a `consent_updated` payload are tolerated: they are now 422.
- A log written before A14 keeps its old actors (`role:name`) and loose payloads; they still replay, because the machine does not apply the schema. `make reset` and `make demo-seed` rebuild the dev database. The seeded cohort only contains `case_created` events.
- Names in tokens: the dev token still carries the name (it is a development credential, ADR-012); only the log and the case responses are name-free. The opaque id is stable per (role, name), so anyone who knows a name and the namespace can recompute it: this protects the log from casual disclosure, not from a determined guesser. Production identity replaces dev login with an OIDC subject, which would be hashed the same way.
- Web: the client must stop sending `owner`, `owner_role` and free-text `reason` values and read names from `owner` and `actors` (contract.ts BACKEND comments).
