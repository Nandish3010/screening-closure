# Web (Cut C: interfaces)

Vite + React + TypeScript. Three surfaces on one typed API client:

| Route | Surface |
|---|---|
| `/coordinator`, `/coordinator/:caseId` | Coordinator / owner app: worklist (most overdue first, then risk), filters, case timeline, actions |
| `/patient/:caseId` (and `/patient`) | Patient PWA, Arabic + English, installable, last case renders offline |
| `/dashboard` | Closure dashboard: P50/P90, open by age, breaches by provider, bottleneck by transition (live: computed by `GET /metrics/closure` from the cases in the database; mock adapter: fixed fixture values, see below) |

Every page shows a permanent **SIMULATED TIME** badge in the header (from `sim_time` in `GET /metrics/closure`).
All data is synthetic. Nothing here diagnoses anyone; the AI draft flow is draft -> human approval, and the risk score only orders the worklist.

## Run

```
make web-install        # npm install
make web-dev            # http://localhost:5173, mock adapter by default
make web-build          # tsc + vite build -> web/dist
make web-test           # vitest: unit + React Testing Library
make web-e2e            # Playwright (headless, mock adapter via `vite preview`)
make test-e2e-live      # Playwright against the REAL stack (http adapter on :4175; skips with a message if the stack is down)
```

### Mock vs http adapter

`VITE_API_ADAPTER=mock|http` (build/dev time; default `mock`). See `.env.example`.

- **mock**: the whole API in the browser, seeded from `src/api/fixtures.ts` (16 synthetic cases, sim clock fixed at 2026-11-04 09:00 UTC). It mirrors the engine's rules (state transitions, closure needs `evidence_ref` + `signed_by`, no automated closer, the referral handoff contract with owner scoping, the consent ledger and freeze, the draft approval gate and the notification mock's consent/contact blocks) and persists to `localStorage`, so the coordinator and patient views in two tabs see each other. `login()` records who is acting, because the real API decides who may approve a draft from the bearer token. Header button "Reset demo" restores the seed. This is the offline demo fallback. **Its dashboard numbers are fixture data, not results**: `SEED_METRICS` in `src/api/fixtures.ts` is a hand-typed object (median time to closure P50 38 days, P90 79 days, open-by-age 41/23/11/6, breaches by provider, bottleneck days per transition); nothing derives it from the cases, and the mock returns it unchanged for `GET /metrics/closure`. Against the real API the P50 and P90 are calendar days from result to first safe close over the closed cases (`api/app/metrics.py`, `time_to_closure`) and are empty (`null`) while no case has closed, as on a freshly reset demo stack.
- **http**: the real API at `VITE_API_URL` (default `http://localhost:8000`):
  `VITE_API_ADAPTER=http VITE_API_URL=http://localhost:8000 npm run dev`.
  Endpoints that the backend has not shipped yet degrade: `/me` 404 -> coordinator, `/cases/{id}/timeline` 404 -> events from `GET /cases/{id}`, `GET /alerts` 404 -> no alerts, `POST /auth/dev-login` 404 -> no token. Read-model fields a row lacks (`owner`, `due_at`, `overdue`, `escalation_level`, `consent_frozen`, `last_event_at`, `provider`, `pending_handoff`, `last_handoff`, `consent`) get safe defaults, or are derived from the event log on `GET /cases/{id}`; the real `GET /cases/{id}` nests them under `read_model`, which the adapter lifts. The owner may be a string (actor or name) or the A14 object `{actor, display_name, role}`. The metrics endpoint is still pending. The API allows the local web origins (5173, 4173, 4175) with CORS, including the `Authorization` header (`CORS_ALLOW_ORIGINS`, E8).

### Against the real stack (E8)

The http adapter is exercised end to end by `make test-e2e-live` (see Tests). What that walk changed on the web side, all in the files named:

- **Payloads** (`pages/CaseDetailPage.tsx`): `accept_ownership` sends `{}` (the owner is the caller; `owner_role` was a 422), `escalate` sends `{rung, state, target}` (`target_role` was a 422), `reopen` takes a reason from the taxonomy (a select: `new_finding`, `evidence_inadequate`, `closed_in_error`, `patient_request`, `other`), `mark_lost_contact` sends `failed_attempts` (an input, at least 3), `reassign` sends the new owner's real `role:user_id` (`api.actorFor` logs the demo user in to learn the opaque id, the page never builds an actor), `clinician_review` and `close` send `signed_by: Practitioner/<own user_id>` (`SignOffPanel`, read-only, from `GET /me`).
- **Display names**: the log holds `role:opaque_id`; the `actors` map of `GET /cases/{id}` and `/timeline` is registered in `lib/derive.ts` (`registerActors`) so the timeline, drafts and owner read "Dr. Layla Haddad".
- **Patient login**: the real API needs `patient_ref` for a patient and a patient cannot look it up, so `loginPatientFor(caseId)` (called by the patient page) reads it from the case with a staff login of its own that does not touch the session, remembers it in `localStorage` (`sc.patient_ref`) and logs in as that patient. Switching to the patient role from a case page opens that case's patient view. Demo only; the mock needs none of this.
- **Sim time**: the header reads `GET /health` (public, has `sim_time`); `/metrics/closure` is staff-only and gave a clinician or a patient "unavailable".
- **`risk_score`** (D8 to D10): the API fills it for every staff role and returns `null` for a patient (`api/app/routers/cases.py`, `_sees_risk`; it is also null if the model file cannot be scored, which never breaks the worklist). The worklist orders by it only after overdue (`src/lib/worklist.ts`: overdue first, then risk, then oldest case), and the worklist and case page show it as a bar (`RiskBar`, "orders list only"); a `null` or missing value is shown as nothing and sorts as 0. It feeds nothing else. The model is trained on simulator output only and is a demonstration of the ordering pattern, not a validated model ([risk-score-card.md](../docs/governance/risk-score-card.md)). The mock adapter's scores are hand-set fixture values (`FIXTURE_RISK` in `src/api/fixtures.ts`), not model output.
- **Colonoscopy evidence**: "Record colonoscopy result" (owners of the case) calls `POST /cases/{id}/confirmatory-result`, which writes a synthetic `Procedure` and `DiagnosticReport` to HAPI and returns the reference. It fills the confirmatory-result field at `confirmatory_booked` and the evidence field of the sign-off panel; `close` then carries `Procedure/<id>`, which the API checks against HAPI (and, since A24, only a complete colonoscopy or a CT colonography is accepted; an incomplete record shows the amber "colonoscopy record is incomplete" banner).
- **Non-owner clinicians** no longer get "request handoff to my provider" (only the owner may request a handoff; the API answers 403). The page says "Ask the current owner (X) to hand it off to <your provider>".
- **`lost_contact`** now offers "Record patient contacted" again (the pathway's `lost_contact --contact_patient--> patient_contacted`).
- **Supervisor role** (`supervisor` in the role switcher, backend role `supervisor`): the only role the API lets move the clock. Its header has "Advance clock (days)" (`POST /clock/advance`, http adapter only). It may also escalate, re-route and accept the supervisor rung.

### Auth (http adapter)

The backend requires `Authorization: Bearer <token>`. The token comes from `POST /auth/dev-login {role, name, provider?}` (response `{token, token_type, user_id, role, display_name, provider?}`; `{access_token}` is also accepted). `role` is a **backend** role: the UI's roles map by `BACKEND_ROLE` in `contract.ts` (`owner` and `clinician` log in as `primary_care_owner`, `specialist` as `specialist_owner`, `coordinator`, `supervisor` and `patient` as themselves). `patient_ref` is sent for the patient login only (see above). `provider` is sent for the clinician roles only: it is the organisation they act for and decides which handoff requests they may answer. The http adapter logs in before the first render (as the remembered role, default coordinator), **again on every role switch in the header**, and once more if a request gets a 401 (then it retries that request once). Requests issued during a switch wait for the new token. The names and providers are the demo logins in `src/api/identities.ts`. The actor of every event is the token's identity: `POST /cases/{id}/events` answers 422 to a body that contains `actor`, so the http adapter never sends one (the mock uses the actor the UI passes, `role:name` with a backend role).

No external network calls at runtime: fonts are bundled (Noto Sans Arabic via `@fontsource`, bundled by Vite), everything else is the system font stack.

## The contract

`src/api/contract.ts` is the single source of truth: every request/response shape, the event vocabulary, payload conventions, and `BACKEND:` notes. Both adapters implement `ApiClient`. Key points for the backend (event names and payloads follow the engine's canonical vocabulary, ticket A2):

- **Events the UI posts** that are not main-path transitions must be appended without changing state: `handoff_requested {to_provider}`, `handoff_accepted` / `handoff_rejected {reason}` (the receiving clinician), `reassign {owner}` (coordinator, from `referral_rejected`), `escalate {rung: reminder|supervisor|coordinator, target_role}`, `escalation_accepted {rung}`, `callback_requested`, `consent_updated` (any non-empty subset of the six booleans `channel_sms`, `channel_whatsapp`, `channel_phone`, `channel_letter`, `share_with_specialist`, `withdrawn`), `mark_lost_contact {}`, and `reopen {reason}` (a clinician, closed cases only).
- **Events the backend writes** and the UI only displays: `handoff_rejected {reason: timeout, bounced: true}` (the scheduler's bounce after 3 working days), `message_drafted {draft_id, provider, fallback_used, prompt_hash, language}` (**no text**), `message_approved {draft_id}`, `message_rejected {draft_id, reason}` followed by `message_sent {draft_id, notification_id, channel, language, purpose}`, `review_requested {reason: consent_withdrawn}`, `mark_overdue {state, due_at}`, `watchdog_flagged {reason: idle|scheduler_down, idle_days?}`.
- **Drafts** (D4, D5): `POST /cases/{id}/drafts {purpose, channel, language}` -> `{draft_id, text, text_ar, text_en (the other is null), language, provider, fallback_used, abstention_reason, prompt_hash}`. The draft text is only on `GET /cases/{id}/drafts`, so both the timeline and the drafts panel load it there (an event payload never carries text, and text in one is ignored). `POST /drafts/{id}/approve` has no body; the answer `{draft_id, approved_by, approved_at, sent, blocked_reason, notification_id}` is shown as "Sent" or "Approved but blocked: consent | contact | case_state". `POST /drafts/{id}/reject {reason: inaccurate|tone|wrong_language|not_needed|other_with_note, note?}` (A16) marks the draft and writes `message_rejected {draft_id, reason}` as the rejecting human; the note is required with `other_with_note`, refused with any other reason, and stays on the draft row (never in the event). Only the owner of the case (or a supervisor) decides; a coordinator can request but not approve, and the panel says why.
- **Read model** on `GET /cases` and `GET /cases/{id}`: `owner` (string, actor, or the A14 object `{actor, display_name, role}`; normalised to `owner` / `owner_actor` / `owner_role`), `due_at` (was `sla_due_at`; `breach_due_at` is accepted), `overdue`, `escalation_level` (0-3), `consent_frozen`, `last_event_at`, `provider`, `pending_handoff {to_provider, requested_by, from_owner, requested_at}`, `last_handoff {outcome, to_provider, by, at, reason?, bounced?}`, optional `risk_score`; on the detail also `consent`, `consent_history`, `review_reason`. `overdue_days` is gone: the UI computes it from `due_at` and the sim clock. Filters `?state=&owner=&overdue=true&flagged=true` are optional (the UI re-filters and re-sorts client side).
- **Asked of the backend**: `watchdog_flagged: {reason, idle_days?, at} | null` on the `GET /cases` rows (worklist marker and the dashboard panel; `?flagged=true`); `GET /alerts -> [{kind: "scheduler_down", since, cleared_at}]` (dashboard banner); `GET /cases/{id}/timeline` items `{kind, at, ...}` with kinds `event | sla_started | sla_breached | escalation | bounce | watchdog` (field names beyond `kind` and `at` are a guess, every renderer treats them as optional).
- **Actors** are `role:name` with a backend role (`coordinator:amal`, `primary_care_owner:dr_ali`, `specialist_owner:dr_s`, `system:scheduler`, `system:notifier`, `system:consent`, `model:template`) or a bare `watchdog`. `system`, `model`, `watchdog` and `scheduler` are shown with an "automated" chip. Only a clinician (an owner role) signs off or reopens; no automated actor can close.
- **Owner scoping (A5)**: a clinician acts only on a case they own. On someone else's case the UI disables the action with the reason and tells them to ask the current owner to hand the case off (only the owner or a supervisor may post `handoff_requested`; the API answers 403 to anyone else, so the page offers no button). The clinician at the receiving provider of a pending request gets Accept / Decline buttons.
- Sign-off posts `clinician_review` (only if the case is still at `confirmatory_completed` or `reopened`) then `close` with `{evidence_ref, signed_by}`.

### What the UI shows for the new vocabulary

- **Overdue**: the worklist and case page use `overdue` + `due_at`. If a server omits `overdue`, `GET /cases/{id}` derives it from the latest `mark_overdue` that no later state change has superseded.
- **Watchdog**: `watchdog_flagged` renders as a red "Nobody is looking at this" chip in the worklist, a banner on the case page and a red timeline entry. It clears when a state change or a human event follows.
- **Escalation**: `escalation_level` shows as "Level N" in the worklist. An `escalate` stays "waiting for a human" until `escalation_accepted`; the case page has an Accept escalation button (coordinator/owner).
- **Consent frozen**: chip in the worklist, banner on the case page (with "flagged for human review" when `review_reason` is set); "Record patient contacted", the draft request and approval, and new hand-offs are disabled with the reason. Rejecting a draft stays possible. (The mock freezes consent on `consent_updated {withdrawn: true}` and adds `review_requested` as `system:consent`; against the real backend `consent_frozen` is authoritative.) A coordinator can record the patient's withdrawal or restoration from the case page.
- **Hand-offs**: "Waiting for acceptance" (banner and panel) while `pending_handoff` is set; a scheduler bounce (`last_handoff.bounced`, state `referral_rejected`) is a separate red banner, "Hand-off bounced: no response in 3 working days", with the re-route action for a coordinator (`reassign`); ordinary rejections keep the taxonomy label.
- **Reopen**: shown on closed cases only; enabled for the clinician role and needs a reason. **Mark lost contact**: coordinator/owner, any open case.
- **Hand-off rejections** show the taxonomy reason as a label ("No capacity (no slot in time)"); an unknown code is shown as-is.

### Draft review (C10)

The "Patient message drafts" panel on the case page: a request form (purpose, channel, language; the language defaults to the one the patient last answered in), then one card per draft from `GET /cases/{id}/drafts`: provider and the "template fallback used" badge, the abstention reason in plain words (the raw code stays in the tooltip), the short prompt hash (full hash in the tooltip), who generated it, the text in its own language and direction, and the status: waiting for the owner, **Approved by X** with **Sent** or **Approved but blocked: consent | contact | case_state** (from the approve answer; after a reload, an approved draft with no `message_sent` says "Approved, no message sent yet"), or **Rejected by X: reason**. Rejecting needs a reason from a fixed list (a select: inaccurate, wrong tone, wrong language, not needed, other) plus a note box that is enabled, and required, only for Other (at most 200 characters); it writes `message_rejected`, which the timeline shows. A coordinator can request but not decide: the panel says so once, inline, and links both buttons to that note. A clinician who does not own the case is told who does. While consent is frozen the request and the approval are disabled with the reason; rejecting stays possible.

### Dashboard: nobody is looking, and the scheduler (C9)

Below the charts, "Cases nobody is looking at" lists `GET /cases?flagged=true` (open cases with a watchdog flag, longest idle first, each with the red marker, the idle time, the owner and a link). Above them, a red banner (`role="alert"`) shows while `GET /alerts` has a `scheduler_down` alert with `cleared_at: null`; a cleared one shows as "running again". The alerts are re-read every 10 s (`ALERT_POLL_MS`), so a stopped scheduler shows up within 90 s (T-C16; 70 s measured on the real stack). With the mock adapter a demo button ("Simulate scheduler down") raises and clears the alert; it does not exist on the http adapter. Against the real stack T-C16 is `e2e-live/scheduler-banner.spec.ts` (`make test-e2e-live`).

## Roles

Header role switcher (coordinator / owner / specialist / clinician / supervisor / patient): `GET /me` gives the default, the demo override is stored in `localStorage` (`sc.role`) and switching logs in again (see Auth). Permissions are a UI mirror in `src/app/AppContext.tsx` (`PERMISSIONS`); disabled actions always say why. Only the clinician role can sign off. Real RBAC is a backend concern.

## Patient page, i18n and RTL

- Strings: `src/i18n/strings.ts`. **Every Arabic string is marked `TODO: native-speaker review`**; they were written by engineering and must be reviewed before use with patients. English is written at roughly grade-6 level (short sentences).
- The toggle sets `lang` and `dir` on the page root and on `<html>` (restored on leave). Names are wrapped in bidi isolates. CSS uses logical properties (`inline-start`, `padding-inline-start`).
- "I understand" posts `patient_acknowledge` (only enabled when the case is at `patient_contacted`, the only state where the engine accepts it). "I don't understand this" posts `callback_requested`, which shows as a banner on the coordinator's case page. Consent changes post `consent_updated` immediately.

## PWA notes

- `public/manifest.webmanifest` (`start_url: /patient`) and `public/sw.js`, registered only in production builds. Test with `npm run build && npm run preview`.
- The service worker precaches the shell and caches same-origin static assets at runtime; navigations are network-first with the cached `index.html` as the offline fallback, so any `/patient/:caseId` route boots offline. API responses are deliberately not cached by the service worker. The patient page keeps the **last loaded case in `localStorage`** and renders it with an "offline" banner when the API is unreachable.
- Arabic font files are cached the first time Arabic is shown; before that, offline Arabic uses the system font.
- Actions taken offline are not queued (the patient sees "That did not work").

- `e2e-live/` (Playwright, `make test-e2e-live`, config `playwright.live.config.ts`): the same browser against the real stack. It builds an http-adapter bundle into `dist-live/`, serves it on :4175 and needs the compose stack up and seeded (`make up`, `make demo-seed`); without them it skips with the reason. It creates its own cases and advances the sim clock, so run `make demo-reset` afterwards.
  - `flow.spec.ts`: the whole flow as the demo's cast: coordinator worklist and acknowledge; owner accepts (no `owner` in the body); a non-owner clinician is told to ask the owner; the owner has an Arabic draft approved and Sent; patient acknowledges on the patient page (`patient_ref` from the case); handoff to Corniche Gastro Unit accepted by the specialist; booking with an appointment date; a supervisor advances the clock 60 days and the sweep marks the case overdue and escalates (level 3), the coordinator accepts; the specialist records the colonoscopy (`Procedure` exists in HAPI), completes the confirmatory test, signs off with `Procedure/<id>` and their own `Practitioner/<user_id>`; reopen with a taxonomy reason; another clinician gets 403.
  - `extras.spec.ts`: mark lost contact with `failed_attempts`, contact again, a declined handoff and the coordinator's re-route (`reassign.owner` is the real actor).
  - `scheduler-banner.spec.ts`: T-C16. Stops the scheduler container, the dashboard banner appears within 90 s (70 s measured: the 60 s heartbeat limit plus a watchdog interval plus the 10 s poll), restarts it, the banner clears (18 s measured). About 3 minutes; always restarts the scheduler.
- `e2e/` (Playwright, `make web-e2e`, alias `make test-e2e`):
  - `closure.spec.ts`: T-C14 in English and in Arabic (find the overdue case, see why, escalate, request a draft in that language, the coordinator cannot approve, the owner approves, Sent, the patient page in that language, evidence and sign-off, closed with a human actor); consent withdrawal freezing drafting with the reason; a frozen pending draft; the bounced hand-off (banner, timeline, worklist chip, re-route) versus an ordinary rejection; a non-owner clinician's "request handoff to my provider" and "waiting for acceptance"; the Arabic patient flow at 375 px (RTL, no horizontal scroll); the dashboard panel and scheduler banner.
  - `a11y.spec.ts`: axe-core (WCAG 2.0/2.1 A and AA) on the worklist, the case page (as coordinator and as owner, with a bounced and a frozen case), the patient page in English and Arabic, and the dashboard (with the scheduler banner), in light and dark; fails on any serious or critical violation (a self-test proves the audit catches a missing alt text and an unnamed button). PWA: the manifest has name, short name, start URL, scope, standalone display, theme colours and 192 and 512 px icons that are all served; a service worker with a fetch handler is active and controls the page.
  - `flows.spec.ts`: the first-pass flows (coordinator, watchdog, reopen, patient, dashboard badge, offline reload).
- Playwright does not need a download if a Chromium headless shell is already in `~/Library/Caches/ms-playwright` (macOS) or `~/.cache/ms-playwright` (Linux, CI) (`playwright.config.ts` picks the newest one; override with `PW_CHROMIUM_PATH`). Otherwise `npx playwright install chromium`.
- Screenshots (`web/screenshots/`, light and dark): captured against the live stack (http adapter, after `make demo-reset`), so actors show opaque ids and roles and the header adapter badge reads `http`, not `mock`. `SCREENSHOTS=1 npx playwright test e2e/screenshots.spec.ts` regenerates them from the mock adapter instead (fixture cases and fixture dashboard values; the header adapter badge reads `mock`), which is the offline fallback.
