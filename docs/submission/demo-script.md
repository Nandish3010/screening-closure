## How the live beats relate to `scenario.py`

`scenario.py` runs from the start of the story, in one go, and refuses to run unless the simulation clock is at its start and the case is at `result_received`; it has no way to start in the middle. So nothing on stage can be a "scenario step". The only scripted part is run **before going on stage**: `make demo-scenario UNTIL=owner_accepted`, which takes the named patient's case through `result_received`, `acknowledged` and `owner_accepted` (a lab acknowledgement and Dr. Haddad accepting ownership). Every beat after that is a UI action, and each beat below names the scenario step it mirrors, so a rehearsal can use `make demo-reset && make demo-scenario UNTIL=<step>` to get to the same place. The differences between the live beats and the script, all imposed by the engine and the web app:

- **The catch has to be staged in a particular order.** The sweep plans an obligation only for the state the case is in when it runs. If the case changes state between the clock jump and the scheduler restart (for example the patient acknowledges), the overdue flag and the escalation never fire. So the order is fixed: the scheduler is killed, the patient is recorded as contacted (the state the SLA is measured in), the clock jumps, and nothing else touches the case until the scheduler is back.
- **The escalation ladder follows ADR-014.** An accepted rung stops the ladder, and only the role a rung is addressed to can accept it. The scripted run lets all three rungs fire and has the coordinator accept rung 3. Live, the supervisor advances the clock by 15 days, which is 11 working days: the supervisor rung (3 working days after the due date) is due and the coordinator rung (7) is not, so the supervisor accepts rung 2 and the ladder stops there. The supervisor is also the only role the API lets move the clock (the **Advance clock (days)** control in the supervisor's header).
- **Whole days, not exact hours.** The script moves the clock to exact hours and calls the sweep itself; live, the scheduler container sweeps on its own 10-second loop. Only the script's event log hash is reproducible (T-E9).
- **The cast.** The script has Dr. Rana Farouk (Al Noor Endoscopy Centre) decline and Marina Digestive Health stay silent. Dr. Rana Farouk has no login in the web's role switcher, so live the **Specialist** login (Dr. Karim Nasser, Corniche Gastro Unit) declines, and Al Noor Endoscopy Centre is the provider nobody answers for. The others are the same: Coordinator Maryam Al Suwaidi, Owner Dr. Layla Haddad (Riverside Primary Care), Supervisor Dr. Noura Al Hammadi, and the patient.
- **The closure is on a second case.** The script has the first case continue through a re-routed referral, a second contact and acknowledgement, the booking and the colonoscopy (`patient_reacknowledged`, `booked`, `colonoscopy_done`, `result_recorded`), which takes about ten more role switches. The live demo instead ends the first case's story at the re-route and shows the closure on a second case that was prepared earlier and sits at "Confirmatory completed". The re-route beat says out loud what the engine does next: a re-routed referral goes back to the contact step, so the new owner contacts the patient and the patient acknowledges again before the booking.

## Q&A preparation

**"Is this just a ticket tracker?"**
A ticket tracker records what people type. Here the rules are enforced by the engine: a case cannot close without evidence that resolves in the FHIR store and the closer's own signature, and a property test checks that over thousands of random event sequences (T-A1). Clocks run on a working-day calendar and escalate in order to named people who must accept. Silence is detected: idle cases are flagged and a stopped scheduler raises an alert (T-A30, T-A31). Consent is an append-only ledger that freezes outreach in the engine. Every event is projected to FHIR R4 with Provenance. And the evaluation reports the escalation acted-on rate, 43.5% in the conservative scenario, so we can see whether escalations are acted on rather than assume it (results.md, `escalation_acted_on_rate`).

**"What's real?"**
The engine, the tests, the FHIR projection and the evaluation code are real and run on this laptop. The data is synthetic: a Synthea cohort and a seeded simulator. Of 132 simulator parameters, 88 are assumed, 16 calibrated, 13 sourced and 15 sourced-adjacent (`meta.parameter_status_counts`), and the assumptions table lists 37 limitations ([assumptions-limitations.md](../assumptions-limitations.md)). Put the table on screen, then: "run `make evaluate` yourself, and change any parameter you doubt." Nothing is integrated with Malaffi or a provider today, and no message is really sent.

**"Why not use agents for this?"**
Because the transitions that matter are safety-critical: is this case overdue, who is told next, may it close. They must give the same answer every time, be replayable from the log and be explainable to a regulator line by line. A model can draft a message well, and we use it there, behind a human approval. A model that decides a closure can be wrong in a way that looks right, and the case then leaves every worklist and every timer. Here that is impossible by construction: an automated actor cannot emit `close`, and a model actor can emit only `message_drafted` (T-D2). If the model is down, nothing changes except that the draft comes from a template ([design-choices.md](../design-choices.md)).

**"What about capacity?"**
The model has none, and we say so in the results: escalations cost nothing, and the orchestrated arm raises about 119 per 100 cases in the conservative scenario (205 in the upper range). The completion gains would shrink without the people and colonoscopy slots to act on them. That is why the pilot starts in shadow mode, measures coordinator minutes per case and escalation precision on a sample, and why we size it by the escalation count. A capacity model is future work (L08).

**"Malaffi is HL7 v2, not FHIR."**
Agreed, and our plan assumes it. The official sources we read list Malaffi's minimum dataset as HL7 v2 message types, and no official document confirms a FHIR interface (evidence.md section 8c). FHIR is our internal model. The adapter plan puts an HL7 v2 adapter at the boundary: ORU for results, ADT for demographics, SIU for appointments, the message control id as the idempotency key, and an automated actor that can never close a case. It is a target, not a claim, and the pilot does not depend on it ([malaffi-adapter-plan.md](../governance/malaffi-adapter-plan.md)).

**"ADHICS does not allow cloud for health data."**
The version we read, ADHICS v0.9 control CM 4.2, prohibits cloud for health information unless DoH authorises it; the current V2 is to verify. So our hosting order is: the provider's own approved environment first, a UAE cloud with written DoH authorisation second, nothing else (ADR-026). The stack is containers and Postgres with no cloud-managed service, so it runs unchanged in the provider's data centre. Backups, disaster recovery and remote support stay in the UAE. The model host follows the same order, and without one the template is used.

**"Why these ages and these SLAs?"**
Eligibility of 40 to 75 with an annual FIT is sourced from the UAE National Guideline and DoH IFHAS V10 (evidence.md section 8a). The demo cohort is generated for the same 40 to 75 range, so the cohort and the eligibility rule agree ([data-provenance.md](../data-provenance.md), L02). The 31 working days for the colonoscopy is the national KPI, measured from referral, so our clock starts at referral acceptance (A13). The other SLAs (acknowledge 2, accept 2, contact 5, patient acknowledges 7, book 14, review 5, sign-off 3, re-route 2 working days) are design choices in a short YAML file; the clinician review (H1) will set them, and a change is a config edit and a rerun of `make evaluate`, not code.

| No overdue flag or escalation after the restart | The case changed state between the clock jump and the restart (the sweep plans only for the current state). Do not touch the case in beats 4 to 5. Recover with `make demo-reset`, stage again and use the backup video. |
| The property test is slow or fails to start | Switch to the tab that holds the earlier green run, or the recording, and say so. |
| `close` refused with 422 on the real reference | The `Procedure` does not exist in HAPI. Click **Record colonoscopy result** in the sign-off panel (it is idempotent) and sign off again; say "and that refusal is the point". |
| The second case is missing or in the wrong state | Run `make demo-stage` (step 4; safe to rerun, it continues a part-way case and says when the case is already there), or `make demo-reset` if the case was closed in a rehearsal; if there is no time, end at beat 12 and play the backup video from shot 9. |
| Anything else | Play the backup video from the matching shot. |
