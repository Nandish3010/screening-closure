# Data provenance

All data in this project is synthetic. No real patient, clinician, facility or screening data is used anywhere.

## Synthea version

- Generator: [Synthea](https://github.com/synthetichealth/synthea) (MITRE), release **v3.3.0**.
- Jar: `synthea-with-dependencies.jar` downloaded from
  `https://github.com/synthetichealth/synthea/releases/download/v3.3.0/synthea-with-dependencies.jar`
  (182,655,376 bytes).
- Pinned sha256 (`tools/synthea/SHA256SUMS`, checked on every run):
  `8ba04f7d73abadd5a377e41edf24c5c83935a1cb07c6d982cd5db731ef1cf445`.
- The jar is treated as untrusted input. It is downloaded and executed only inside the `synthea`
  compose container (`eclipse-temurin:17-jre`, profile `tools`), whose only host mount is `./data`
  (gitignored). Before running, the script checks that the jar is a valid archive containing
  `App.class` (`unzip -l`) and that its hash matches the pin.

## Seed

- Synthea: `SYNTHEA_SEED=20261017` (population seed `-s` and clinician seed `-cs`).
- FIT result generator and case ids: seed `20261017` (`simulator/generate_results.py --seed`).
- Reference and end date for Synthea: 2026-01-05, the date of `SIM_CLOCK_START`, so "aged 40-75" means
  aged 40-75 on the simulation start date and the cohort does not depend on the wall clock.

Exact command (run inside the container by `tools/synthea/run.sh`):

```
java -jar synthea-with-dependencies-v3.3.0.jar \
  -s 20261017 -cs 20261017 -r 20260105 -e 20260105 -p 300 -a 40-75 \
  --exporter.years_of_history=5 \
  --exporter.fhir.export=true \
  --exporter.hospital.fhir.export=true \
  --exporter.practitioner.fhir.export=true \
  --exporter.fhir.use_us_core_ig=false \
  --exporter.baseDirectory=/data/synthea/out \
  Massachusetts
```

`-r`/`-e` are not in the original brief: without them Synthea uses the current date, so the same seed
would give a different cohort on different days. (`-r` takes `YYYYMMDD`, not epoch milliseconds.)

## FIT results (simulator)

Synthea does not produce FIT results for this pathway, so they are generated by `simulator/generate_results.py`:

- Eligible: patients aged 40-75 (completed years, inclusive) on `SIM_CLOCK_START`, not deceased by then.
- Each eligible patient gets one seeded draw (`random.Random("<seed>|<Synthea patient uuid>")`); positive if the draw is below `fit_positivity_rate`. Negatives are not written to HAPI.
- Per positive: one `Observation` (LOINC `29771-3`, `valueCodeableConcept.text = "Positive"`, no SNOMED, `status=final`) and one `DiagnosticReport` (`status=final`, same code, `result` -> the Observation, conclusion "Positive FIT. Confirmatory colonoscopy recommended."). `effectiveDateTime` is a seeded uniform draw over the 14 days before `SIM_CLOCK_START`.
- LOINC display: checked against the HL7 terminology server (tx.fhir.org, LOINC 2.82). The current display of `29771-3` is "Hemoglobin [Presence] in Stool from gastrointestinal lower by Immunoassay"; older LOINC releases used "Hemoglobin.gastrointestinal [Presence] in Stool by Immunoassay". The code is unchanged. Re-verify against loinc.org before any external submission.
- Resource ids are `uuid5` of (seed, patient, kind), and case ids are `uuid5` of the report id, so reruns create nothing new.

## Simulator, simulation clock and cached model outputs

Three more kinds of derived data exist beyond the cohort and the FIT results. None is real. Each is listed with how it is produced, whether a rerun gives the same result, and what it cannot show. The assumptions behind them are in [assumptions-limitations.md](assumptions-limitations.md).

|---|---|---|---|---|---|

Outputs are `docs/results/results.json` and `results.md`. | Parameters from `simulator/params.yaml` (138 parameters: 87 assumed, 16 calibrated, 13 sourced, 14 sourced-adjacent, 8 empirical), seed 20261017, 20 replications of 2,000 cases, 360 days of follow-up. Language, channel, responsiveness and the messy cases (wrong contact, provider switch, duplicate result, conflicting acknowledgement, consent withdrawn) are simulator draws, not cohort attributes. | Yes. `make evaluate` gives byte-identical `results.json` for the same seed, parameters and pathway file (`make evaluate-check`). The `generated_at` line in `results.md` is the only content that changes. | Built. Parameter values are mostly placeholders, see below. | Not calibrated to any Abu Dhabi data. The 16 calibrated values were tuned to a US completion curve. Confidence intervals reflect simulation noise only. No capacity model. |

It starts at `SIM_CLOCK_START` (2026-01-05) and moves only when a supervisor advances it, or back to the start on reset, which is refused once any event is dated after the start (SEC-1, ADR-029). It orders the worklist only. |

Parameter status in the simulator, in five words. `sourced`: taken from a public document that measured the same quantity. `sourced-adjacent`: from a document that measured a related quantity or another setting. `empirical`: fitted by a script in `tools/calibration/` from an open dataset that was downloaded (see External datasets below). `calibrated`: tuned so the baseline reproduces a published curve. `assumed`: no public source found. Sources, access notes and caveats are in [evidence.md](evidence.md).

## External datasets

Ticket B18 (calibration of simulator parameters from open data). These are the only non-synthetic files the project has downloaded. They are aggregate tables, except the no-show file, which holds appointment records of a Brazilian clinic network (no names; a patient id, age, sex, neighbourhood and appointment dates). The owner approved the downloads.

**Handling.** Downloaded files are untrusted input. They are kept only under `data/external/<source>/` (one directory per file, covered by the `data/` rule in `.gitignore`), are never executed or unpacked to disk, and are read only by the scripts in `tools/calibration/` (stdlib-only parsers for zip/XML, the legacy OLE2 `.xls` format and text, with size limits), always run as `python3 -I`. `make calibrate-fetch` downloads and records; `make calibrate-fit` fits; `make calibrate-check` re-runs the tests and the fits from the local files and fails if a fitted value or an `empirical` leaf of `params.yaml` differs. The manifest `data/external/MANIFEST.json` is ignored with the data; a copy is committed as `tools/calibration/manifest.json` (it also records what was not downloaded and why).

## What is synthetic

Everything: patients (names, addresses, identifiers including the Synthea-generated pseudo SSNs and passport numbers), encounters, conditions, medications, practitioners, hospitals, and every FIT Observation, DiagnosticReport and case.

## What is real

Nothing in the records. Synthea's statistical models are derived from published epidemiology and census data for the US (and Massachusetts), but no individual's data is used or reconstructable. Hospital and practitioner names come from Synthea's bundled lists of US facilities and are not linked to this project's data. The LOINC code is a real public terminology code; only its use here is synthetic.

## Known limitations

The full list, with where each gap bites and how to remove it, is [assumptions-limitations.md](assumptions-limitations.md). The ones that concern this cohort:

- Synthea needs a US state: names, addresses, phone numbers, geography, facilities, insurance and care patterns are Massachusetts / US. There are no Arabic names and no UAE demographics, languages, or health-system structure.
- The cohort is 40-75 by construction, so it does not reflect a real screening-eligible population's age mix or a real invitation/uptake process.
- Synthea does not model FIT screening for this pathway; the FIT positivity rate (7%) is a simulator parameter (sourced-adjacent, cut-off dependent) and is not a Synthea output. Which patients are positive is unrelated to their clinical history (a positive patient is not more likely to have a colorectal condition in the record).
- Deceased patients are generated and loaded (Synthea exports them) but are excluded from FIT generation.
- One result per patient; no repeat testing, negative result records, or non-responders.

## Reproduction

```
make up                      # stack: postgres, HAPI FHIR, api, ...
make demo-seed               # synthea (if no output) -> load HAPI -> generate FIT results -> create cases
```

Step by step:

```
make synthea                                   # generate data/synthea/out/fhir (container only)
.venv/bin/python simulator/load_cohort.py      # refuses if HAPI already holds Patients (--force to override)
.venv/bin/python simulator/generate_results.py # writes data/results/manifest.json
.venv/bin/python simulator/create_cases.py
```

A full reset is `make reset && make demo-seed`. `make demo-seed-clean` deletes the generated files in `data/`
(`data/synthea/out`, `data/results`) but keeps the cached jar. Knobs: `SYNTHEA_SEED`, `SYNTHEA_POPULATION`,
`SYNTHEA_VERSION`, `SYNTHEA_REFERENCE_DATE`, `FHIR_BASE_URL`, `API_URL`, `SIM_CLOCK_START`.

Reproducibility scope: with the same Synthea version, seed, population and reference date the generator is deterministic;
FIT selection is a pure function of the seed and each patient's Synthea UUID, independent of HAPI's id assignment.
