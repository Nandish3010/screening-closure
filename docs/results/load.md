Generated by `make test-load` (`tools/load/time_sweep.py`). Do not edit by hand. All data are synthetic.

**Target: the 100,000-case sweep under 5 s. Single process (`SWEEP_WORKERS=1`): 20.38 s (not met). Through `POST /scheduler/sweep` with 4 workers (the API default): 6.76 s (not met). Through `POST /scheduler/sweep` with 10 workers: 5.21 s (not met).**

## Cold start (scenario `backlog`)

No sweep has run since the cases were created, for example after a long scheduler outage, so every breach and every rung is pending and the sweep must append all of them. Each append is its own transaction that locks the case, re-reads its log and re-verifies the replay (the engine's safety property), so this case is bound by the appends, not by reading.

## Optimisation history

Two optimisations, both in `api/app/sweep.py` and `api/app/store_pg.py`, no behaviour change (`make test` and `make test-db` pass unchanged). (1) The events the scheduler plans for one case (a breach and its first escalation rung) are appended in one transaction, `PostgresEventStore.append_many`: one row lock, one log read and replay and one commit instead of one of each per event; if the batch is refused for any reason the sweep falls back to appending one by one. (2) `run_sweep_parallel` / `shard=(k, n)`: the open cases are split into disjoint slices by a stable hash of the case id and swept by separate processes, each with its own connection pool, because replaying every case is CPU-bound Python. Before is the single-process sweep at commit 960e628, the base of this branch; after is the same call on this branch. Same machine, seed and sweep time. Timings vary by about 10% from run to run on a shared laptop.

A first run, on a busy machine and before the base had moved, measured 48 s for the 100,000-case single-process sweep. It did not reproduce on the quiet reruns (17 to 26 s) and is not used here.

A17 (this branch): `POST /scheduler/sweep` now runs `run_sweep_parallel` on a long-lived pool of worker processes (`SweepPool` in `api/app/sweep.py`, used by `api/app/routers/scheduler.py`). `SWEEP_WORKERS` sets the size, default min(4, cpus); `SWEEP_WORKERS=1`, or any store that is not Postgres, keeps the single-process `run_sweep`. The pool is created on the first sweep (about a second) and kept; the rows with Workers 4 and 10 in the first table are the route itself, called in process on a warm pool, so they include the service-token check and the JSON response. Idempotency and no duplicate events across shards are asserted on the route in `api/tests/test_sweep_parallel_pg.py`, and a sweep killed part-way is covered by `api/tests/test_chaos_kill_sweep.py`.

Is 100,000 under 5 s now met in the real route? Not reliably, and not at the default of 4 workers. Five runs on this shared 10-core laptop (other jobs running most of the time; Postgres in Docker on the same machine; the last, which is the one in the table above, ran with a load average of about 2), full sweep with the day's 11,276 events, then the re-sweep that emits nothing and is what the 10-second loop mostly does: 4 workers 10.46 s / 5.58 s, 7.56 s / 3.59 s, 7.11 s / 3.92 s, 7.75 s / 4.63 s; 10 workers 8.51 s / 3.36 s, 5.34 s / 2.37 s, 4.99 s / 2.37 s (met once, by 0.01 s, in the run with synchronous_commit=off described below), 10.23 s / 4.34 s; and on the quiet run 6.76 s / 3.41 s at 4 workers and 5.21 s / 2.25 s at 10 (not met by 0.21 s). Neither the single process (20 to 26 s) nor the default pool (best 6.76 s) meets the target for a sweep that appends a day's events at once; 10 workers met it once in five runs. A steady-state sweep (nothing to append) of 100,000 cases takes 2.3 to 4.3 s with 10 workers and 3.4 to 5.6 s with 4, so the 10-second loop keeps up with 100,000 open cases on a quiet machine. The shortfall is CPU, not durability: setting `synchronous_commit=off` for the workers changed the 100,000-case figures by about 5% (inside the noise) and was not adopted.

Why more workers do not scale linearly: replaying every case and appending each event is Python CPU work plus one Postgres transaction per case, and with 10 workers the Python processes, the Postgres backends and the Docker VM share 10 cores. Ideal scaling from the single-process split (read and replay about 10 s, appends about 10.6 s) would give about 2.3 s at 10 workers; the measured best is 5.0 s. Lowering the figure further needs a cheaper append (the store re-reads and re-replays the log inside each append transaction) or skipping cases that cannot be due, both changes to `api/app/store_pg.py` outside this ticket.

## Method

- `tools/load/seed_cases.py` creates the throwaway database `closure_load` on the compose Postgres (host port 5433), applies the engine's migrations through `app.db.run_migrations`, and bulk-inserts cases and their event logs with `COPY`. Every log is produced by the engine's own state machine and replayed once at seeding time. It refuses to touch any database not named `closure_load*`; the dev database is never used.
- `tools/load/time_sweep.py` times the sweep with a fixed sweep time (2026-03-10 08:00 UTC, a Tuesday), the real `PostgresEventStore` and the UAE working-day calendar; with Workers 1 by calling `run_sweep`, with more workers by calling `POST /scheduler/sweep` on the FastAPI app (`RouteSweep`, `SWEEP_WORKERS=N`, pool started before the clock). Seed 20261017, so the data and the emitted-event counts are reproducible; wall times vary with the machine. Postgres runs in Docker on the same machine, so every statement pays a local network hop.
- After each sweep it asserts: emitted events equal the pure planner's expectation; no errors or rejected events; a second sweep emits nothing; no `close` event exists; case logs are gap-free; the event row count grew by exactly the events emitted.
- `make check` runs the 1,000-case size only (no file written); `make test-load` runs all sizes and rewrites this file. The database is dropped at the end unless `KEEP_LOAD_DB=1`.
